## Qué vas a construir

Antes de fiarte de un instrumento, lo revisas. Esta lección trae cuatro cambios pequeños al de
Rukh. Ninguno produce una fila de la tabla, pero deciden si las filas se pueden leer:

- dos configuraciones que miden el propio montaje, no un modelo;
- un presupuesto de nodos en `StockfishOpponent`, para que el rival deje de depender de la carga
  de la máquina;
- una caché partida por familias, para que subir el número de partidas no tire las ya jugadas;
- un hash de los pesos, no del fichero, para reconocer una copia del Hub como el modelo que se
  midió.

Y una deuda de M5: el fichero de prompts del DPO, que nadie podía regenerar.

## Dos configuraciones que no miden un modelo

La lección 1 contó que `medium-elo`, medido dos veces con la misma semilla, dio 1498 y 1558. El
sospechoso natural es el reloj: a 0,1 segundos por jugada, cuántas posiciones explora Stockfish
depende de lo que esté haciendo la máquina. Para comprobarlo hay que correr la escalera cuatro
veces, dos con cada límite, y eso pide dos ficheros de configuración cuyo único trabajo es medir el
instrumento.

## El rival, con presupuesto de nodos

Toda la mecánica del <Term id="limite-por-nodos">límite por nodos</Term> es un argumento nuevo y
una propiedad en `StockfishOpponent`, la clase que M2 escribió para hablar con el motor por <Term id="uci">UCI</Term>.

```python title="src/rukh/infer/game.py"
    def __init__(
        self,
        elo: int = 1400,
        move_time: float = MOVE_TIME_SECONDS,
        path: Path | None = None,
        skill: int | None = None,
        nodes: int | None = None,
    ) -> None:
        from rukh.engine import EngineNotFound, find_stockfish

        binary = path or find_stockfish()
        if binary is None:
            raise EngineNotFound("Stockfish not found; set RUKH_STOCKFISH or run get_stockfish.py")
        self.move_time = move_time
        # A node budget instead of a clock: the search stops after ``nodes`` positions whatever
        # the machine is doing, so the opponent no longer weakens under CPU load (D-068) and two
        # identical runs see the same opponent. 0.1 s is about 200 000 nodes on the reference
        # machine at these settings, which is where `elo_nodes` in the suite starts from.
        self.nodes = nodes
        self.engine = chess.engine.SimpleEngine.popen_uci(str(binary))
        if skill is None:
            self.engine.configure({"UCI_LimitStrength": True, "UCI_Elo": elo})
        else:
            self.engine.configure({"UCI_LimitStrength": False, "Skill Level": skill})

    @property
    def limit(self) -> chess.engine.Limit:
        """How far the opponent searches: a node budget when given, the clock otherwise."""
        if self.nodes is not None:
            return chess.engine.Limit(nodes=self.nodes)
        return chess.engine.Limit(time=self.move_time)

    def choose(self, board: chess.Board) -> chess.Move:
        played = self.engine.play(board, self.limit)
        if played.move is None:
            raise chess.engine.EngineError("Stockfish returned no move")
        return played.move
```

<Src file="src/rukh/infer/game.py" tag="p6" lines="116-152" />

Antes, `choose` construía su límite en línea: `chess.engine.Limit(time=self.move_time)`. Ahora el
límite es una propiedad y `choose` no sabe cuál es. Dos decisiones van dentro.

`nodes=None` por omisión: todas las partidas de M2 a M5 se jugaron por reloj, y un límite por
defecto distinto habría recalibrado en silencio los módulos anteriores. Y la propiedad devuelve uno
u otro, nunca los dos, porque `Limit` acepta ambos campos a la vez y entonces el motor para con **lo
primero** que se cumpla: un presupuesto de nodos con el reloj puesto seguiría dependiendo del reloj.

Que sea una propiedad y no un campo calculado en `__init__` permite el test de más abajo sin
Stockfish instalado: `StockfishOpponent.__new__` construye el objeto sin ejecutar el constructor, se
le ponen los dos atributos a mano y se comprueba qué `Limit` sale. Así corre en la CI.

<Callout kind="mundo-real" title="Un examen con reloj y un examen con preguntas">
  Los dos límites son un examen con tiempo fijo y uno con preguntas fijas. Con una hora de reloj,
  cuántas preguntas contestas depende de si el de al lado tose; con veinte preguntas, contestas
  veinte tardes lo que tardes. El rival por nodos contesta siempre sus 200 000 preguntas. Si eso
  basta para que la escalera repita es otra cuestión, porque `UCI_LimitStrength` aleatoriza por
  debajo; es una hipótesis, y la lección 8 trae la respuesta.
</Callout>

```python title="src/rukh/eval/elo.py"
def play_rungs(
    model: MoveDecoder | None,
    tok: UciTokenizer,
    rungs: Sequence[EloRung],
    games: int,
    cfg: SampleConfig,
    move_time: float = MOVE_TIME,
    max_plies: int | None = None,
    cache: EvalCache | None = None,
    header_elo: int = 1800,
    player: Player | None = None,
    nodes: int | None = None,
) -> list[GameRecord]:
    """Play every rung and return all the game records."""
    records: list[GameRecord] = []
    for rung in rungs:
        records.extend(
            play_rung(
                model,
                tok,
                rung,
                games,
                cfg,
                move_time=move_time,
                max_plies=max_plies,
                cache=cache,
                header_elo=header_elo,
                player=player,
                nodes=nodes,
            )
        )
    return records
```

## La caché, partida en dos familias

El segundo cambio sale de un apunte del backlog de P4.

La <Term id="clave-de-cache">clave de caché</Term> de la suite promete que dos ejecuciones con la
misma clave midieron lo mismo. Había una sola clave para las partidas y los puzles, y con doce
etapas eso salía caro: subir `elo_games` de 20 a 40 tiraba las veinte partidas ya jugadas, aunque la
partida `uci-1500:0` sigue siendo la misma (su semilla es `seed + index`); y forzar la cabecera de
los puzles invalidaba todas las partidas.

```python title="src/rukh/eval/suite.py"
    def cache_fields(self, family: str = "games") -> dict[str, Any]:
        """The settings that change what a cached item of ``family`` means.

        One key per family, not one for the suite: a game is the same game whatever the puzzle
        settings are, and a puzzle attempt does not care how long the engine thinks. Under one
        shared key, raising ``elo_games`` from 20 to 40 threw away the twenty games already
        played although game ``rung:index`` is exactly the same game (its seed is ``seed +
        index``), and forcing the header for a sweep invalidated every game (P4 backlog). The
        number of games is deliberately absent: it changes how many items are read, not what
        any of them is.
        """
        shared: dict[str, Any] = {
            "temperature": self.temperature,
            "top_k": self.top_k,
            "seed": self.seed,
            "block": self.block,
        }
        if family == "games":
            fields = {
                **shared,
                "elo_max_plies": self.elo_max_plies,
                "rungs": [rung.model_dump(mode="json") for rung in self.elo_rungs],
            }
            # The clock and the node budget are two different opponents; only the one in use
            # is in the key, so a run on the clock keeps its games when ``elo_nodes`` appears
            # in the config later with ``null``.
            if self.elo_nodes is not None:
                fields["elo_nodes"] = self.elo_nodes
            else:
                fields["elo_move_time"] = self.elo_move_time
            return fields
        if family == "puzzles":
            fields = dict(shared)
            # Only when it is on: a flag that is off *is* the behaviour every cached attempt was
            # played under, and the key keeps the old name so a sweep's paid-for attempts survive.
            if self.force_header:
                fields["puzzles_use_header"] = True
            return fields
        raise ValueError(f"unknown cache family {family!r}: games or puzzles")
```

<Src file="src/rukh/eval/suite.py" tag="p6" lines="145-183" />

Las tres decisiones son sobre qué no entra en la clave:

- `elo_games` no está: el número de partidas cambia cuántos elementos se leen, no qué es cada uno.
- El reloj entra solo si no hay nodos, y los nodos solo si los hay. Si la clave llevara siempre los
  dos campos, el día que `elo_nodes` apareció con `null` en todas las configuraciones la clave
  habría cambiado y las partidas ya pagadas se habrían tirado.
- `puzzles_use_header` conserva el nombre antiguo aunque el campo se llame `force_header` desde M4.
  Renombrar una clave de caché es invalidarla.

<Callout kind="roto" title="Una sola clave y doce etapas">
  Antes de este cambio, tocar cualquier línea de `configs/eval/greedy.yaml` volvía a jugar las 160
  partidas y los 6 000 puzles de cada etapa: una tarde de reloj para cambiar una cabecera. El
  síntoma no era un error, era la tentación de no tocar la configuración por miedo al coste, y así
  es como un instrumento se queda sin revisar. Pasa igual con la caché de cualquier evaluación cara
  (las llamadas a un juez automático, los embeddings de un corpus): si la clave depende de más cosas
  que el resultado, cada cambio pequeño cuesta como uno grande y la gente deja de hacerlos.
</Callout>

Ante una familia que no conoce, la función levanta `ValueError` en vez de devolver la clave
compartida: una familia mal escrita tiene que ser un error, no una caché vacía que se llena en
silencio.

## La identidad de unos pesos

La evaluación registraba el SHA-256 del fichero que midió. Pero `rukh publish` quita al checkpoint
el estado del optimizador y la cabeza atada antes de subirlo, porque nadie que descargue un modelo
para jugar necesita cientos de megas de momentos de AdamW. Mismos pesos, otro fichero, otro hash, y
la guarda que comprobaba que la card hablaba del fichero medido decía que eran dos modelos.

```python title="src/rukh/eval/cache.py"
def weights_sha(path: Path) -> str:
    """SHA-256 of the tensors under ``model_state``, independent of how the file was written.

    Two files can hold the same weights and differ byte for byte: ``best.pt`` keeps the optimizer
    and the run's provenance, the copy ``rukh publish`` uploads (and ``rukh pull`` brings back)
    does not, and ``torch.save`` is not even stable across versions. What an evaluation measured
    is the weights, so this is the identity a pulled checkpoint shares with the one that was
    evaluated. Names, dtypes, shapes and bytes, in name order; a tied head (``lm_head.weight``
    when it is the embedding under another name) is left out, because the publisher drops it
    and the loader re-ties it, so both files hold the same model.
    """
    import torch

    from rukh.train.checkpoint import TIED_SOURCES

    try:
        payload = torch.load(Path(path), map_location="cpu", weights_only=True)
    except Exception:  # noqa: BLE001 - reward checkpoints carry objects the safe loader refuses
        payload = torch.load(Path(path), map_location="cpu", weights_only=False)
    state = None
    if isinstance(payload, dict):
        # ``model_state`` is ours; ``model`` is nanoGPT's (the Karvonen baseline).
        state = payload.get("model_state") or payload.get("model")
    if not isinstance(state, dict) or not state:
        raise ValueError(f"{Path(path).as_posix()} holds no model_state to hash")
    names = sorted(state)
    for head, embedding in TIED_SOURCES.items():
        if head in state and embedding in state and torch.equal(state[head], state[embedding]):
            names.remove(head)
    digest = hashlib.sha256()
    for name in names:
        tensor = state[name].detach().cpu().contiguous()
        digest.update(f"{name}|{tensor.dtype}|{tuple(tensor.shape)}|".encode())
        raw = tensor.view(torch.int16) if tensor.dtype == torch.bfloat16 else tensor
        digest.update(raw.numpy().tobytes())
    return digest.hexdigest()
```

<Src file="src/rukh/eval/cache.py" tag="p6" lines="54-89" />

Es el <Term id="hash-de-pesos">hash de pesos</Term>. Cada línea tapa una forma de que dos ficheros
con el mismo modelo den hashes distintos, o de que dos modelos distintos den el mismo:

- `sorted(state)`: el orden de inserción del diccionario depende de cómo se construyó el modelo.
- Nombre, `dtype` y forma entran en el digest antes de los bytes; si no, un modelo con dos capas de
  la misma forma permutadas sería «el mismo modelo».
- La cabeza atada se salta solo cuando está atada de verdad. El decoder de M2 comparte la matriz de
  embeddings con la capa de salida (<Term id="tied-embeddings">tied embeddings</Term>); el
  publicador borra la copia y el cargador la vuelve a atar. `torch.equal` comprueba que los dos
  tensores son iguales, para que una cabeza independiente no desaparezca del hash.
- `view(torch.int16)` para bfloat16: `numpy` no conoce ese tipo, y `view` reinterpreta los mismos
  bytes sin copiar ni cambiar un bit.
- El `except Exception` con su `noqa`: `weights_only=True` se niega a deserializar objetos de Python
  arbitrarios, y los checkpoints del reward model de M5 llevan uno. El comentario explica por qué
  aquí un `except` desnudo no es un error.

<Callout kind="mundo-real" title="La misma novela en tapa dura y en bolsillo">
  Distinto lomo, distinto peso, distinto código de barras, y el mismo texto de la primera línea a la
  última. Una guarda que compara códigos de barras dice que son libros distintos; la que compara el
  texto dice que es el mismo libro, y sigue distinguiéndolo de una edición con un capítulo cambiado.
  El hash de tensores no afloja la guarda: acepta otro fichero con los mismos pesos y rechaza pesos
  distintos.
</Callout>

```python title="src/rukh/data/pairs.py"
def build_prompts(pairs: pl.DataFrame, games_dir: Path, block: int = 200) -> pl.DataFrame:
    """Every pair joined back to its game: the moves that led to the position, and the ratings.

    A pair is a FEN, and the decoder cannot read a FEN: it reads the move sequence that reached
    the position, behind the three header tokens. ``game_id`` and ``ply`` say which game and how
    far into it, so the prompt is the first ``ply`` moves of that game and the two Elo columns
    fill the header. This is the file every DPO, GRPO, reward-model and on-policy config reads;
    until it was written here it existed only as a one-off join nobody could rerun.

    A prompt has to fit the decoder's context whole -- three header tokens plus ``ply`` moves,
    at most ``block`` -- because truncating its front would hand the model a position that never
    happened. Pairs deeper than that are dropped and counted, and so is a pair whose game is not
    under ``games_dir``; neither is ever invented.
    """
    parquets = sorted(games_dir.glob("year=*/month=*/games.parquet"))
    if not parquets:
        raise FileNotFoundError(f"no converted games under {games_dir} (run `rukh data uci`)")
    games = (
        pl.scan_parquet([p.as_posix() for p in parquets])
        .select("game_id", "uci", "white_elo", "black_elo")
        # The games carry the id as a signed 64-bit hash; the evaluations, and therefore the
        # pairs, carry it as text. Matching on text loses nothing and refuses nothing.
        .with_columns(pl.col("game_id").cast(pl.String))
    )
    header = 3  # <bos> and the two Elo tokens, exactly what `rukh.infer.game._history` builds
    joined = (
        pairs.lazy()
        .filter(pl.col("ply") + header <= block)
        .join(games, on="game_id", how="inner")
        .collect()
    )
    prefixes = [
        " ".join(str(uci).split()[:ply])
        for uci, ply in zip(joined["uci"], joined["ply"], strict=True)
    ]
    return joined.with_columns(pl.Series("prefix", prefixes, dtype=pl.String)).select(
        PROMPT_COLUMNS
    )
```

<Src file="src/rukh/data/pairs.py" tag="p6" lines="164-201" />

Cinco decisiones:

- `scan_parquet` y no `read_parquet`: el corpus son varios gigabytes por meses, y el plan perezoso
  empuja filtro y columnas hasta el lector (<Term id="predicate-pushdown">predicate
  pushdown</Term>), así que de cada fichero solo se leen cuatro columnas.
- El filtro `ply + header <= block` va en el lado de los pares, el pequeño, antes de cruzar.
- El `cast(pl.String)`: las partidas guardan `game_id` como entero de 64 bits y los pares como
  texto. En `polars`, un cruce entre `Int64` y `String` no falla: devuelve cero filas, y tendrías un
  fichero vacío que parece correcto.
- `header = 3` con nombre y comentario (`<bos>` y los dos tokens de Elo): el día que la cabecera
  cambie hay un sitio donde cambiarlo.
- Los pares demasiado profundos se tiran, no se cortan. Un prompt recortado por delante es una
  posición que nunca se jugó. Mejor menos datos honestos que más datos inventados, la misma regla
  que el `-100` de M3 para las etiquetas que no se sabían.

<Exercise n="02" title="El hash que no distinguiría dos modelos">
