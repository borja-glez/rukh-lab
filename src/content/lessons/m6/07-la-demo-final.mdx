## Qué vas a construir

La demo de M5 tenía una pantalla: cargas un modelo y juegas contra él. La de este hito tiene tres
modos sobre la misma pantalla, y añade lo que faltaba para que la demo sea de quien sigue el curso y
no solo de quien lo escribió.

**Arena**: dos etapas se cargan en dos workers y juegan por parejas con los colores espejados desde
una apertura aleatoria con semilla. El marcador se convierte en una diferencia de Elo con su
intervalo bootstrap, con **la misma aritmética** que `rukh eval match` de M5, y al lado se imprime
cuántas partidas haría falta jugar para que una diferencia de ese tamaño se separara del cero.

**Puzles**: los 150 que exporta `labs/m6/puzzles_export.py`, preguntados como los pregunta el harness
—con el prefijo real de la partida y los Elo de los jugadores— y contados con su mismo criterio: la
línea entera, no la primera jugada.

**Posición compartible**: `?fen=` abre el tablero en una posición, que es lo que permite que una
lección enlace a un puesto concreto.

**Y tu propio modelo**: un campo que acepta el `artifacts/onnx/small/model-int8.onnx` que acabas de
exportar en el lab 5 de M2, sin subirlo a ninguna parte.

El código de esta lección vive en el otro repositorio, `rukh-web`, en el commit
[`b0bf7af`](https://github.com/borja-glez/rukh-web/tree/b0bf7af). Las decisiones están en
`src/lib/`: la aritmética de la arena, el criterio de los puzles, la lectura del fichero local y el
camino de los bytes hasta el worker. Las islas de Preact (`Arena.tsx`, `Puzzles.tsx`) solo orquestan
esas funciones y dibujan el resultado.

export function parseQuery(
  search: string,
  fallback = defaultStageId(detectConditions()),
  encoderFallback = defaultEncoderId(detectConditions()),
): Query {
  const params = new URLSearchParams(search.startsWith('?') ? search.slice(1) : search);
  const requested = params.get('stage') ?? fallback;
  const stage = findStage(requested) ?? findStage(fallback);
  const mock = params.get('mock') === '1' || stage === undefined || stage.kind === 'mock';
  const encoder = findEncoderStage(params.get('encoder') ?? encoderFallback);
  const mode = params.get('mode');
  const vs = params.get('vs');
  return {
    mock,
    stage: mock ? 'mock' : (stage?.id ?? fallback),
    encoder: encoder?.id ?? encoderFallback,
    color: params.get('color') === 'b' ? 'b' : 'w',
    mode: mode !== null && (MODES as readonly string[]).includes(mode) ? (mode as Mode) : 'play',
    fen: validFen(params.get('fen')),
    vs: vs !== null && findStage(vs) ? vs : null,
  };
}

/** `fen` when chess.js accepts it as a position, else null. */
export function validFen(fen: string | null): string | null {
  if (!fen) return null;
  try {
    return new Chess(fen).fen();
  } catch {
    return null;
  }
}

Toda la función tiene la misma forma y es la que conviene copiar: **cada parámetro se valida contra lo
que existe y cae a un valor por defecto cuando no**. Un `?mode=cocina` abre el modo de jugar, un
`?vs=nada` deja la arena sin segunda etapa, y un `?fen=` con basura se ignora. Nunca hay una excepción
ni una pantalla en blanco.

`validFen` valida **construyendo**: le da la cadena a `chess.js` y devuelve el FEN normalizado que
salga, o `null` si el constructor protesta. Escribir una expresión regular para un <Term id="fen">FEN</Term> es un error clásico: el formato tiene seis campos, dos de ellos con reglas
que dependen de la posición, y la librería que va a jugar con él ya sabe decidirlo. Y devolver `new
Chess(fen).fen()` y no el `fen` de entrada normaliza la cadena, así que dos enlaces con la misma
posición escrita de dos formas dan el mismo estado.

`?fen=` no puede hacer daño precisamente por eso: lo que entra en el estado de la página es la salida
de `chess.js` y no el texto del usuario.

## La arena: la aritmética de M5, portada a TypeScript

{/* prettier-ignore */}
```ts title="src/lib/arena.ts"
/**
 * Arena: two stages play each other in the browser, and the difference is read off the games.
 *
 * The arithmetic is `rukh.eval.match` (M5) ported line for line: every opening is played twice
 * with the colours swapped, the score is A's points over both games, the Elo difference is
 * `400·log10(p / (1 - p))` and its interval comes from a bootstrap over the games. A match
 * measures a **difference** and nothing else: there is no third party here whose mood has to be
 * averaged (D-110), and the number is not a strength.
 *
 * Everything here is pure, so `tests/arena.test.ts` can pin the numbers against the Python
 * implementation without a model in sight.
 */
```

<Src file="src/lib/arena.ts" repo="rukh-web" tag="b0bf7af" lines="1-12" />

«Portada línea a línea» es una afirmación fuerte y es la que hace que la arena sirva de algo. Si el
navegador calculara la diferencia de Elo con otra fórmula, o remuestreara de otra forma, el número de
la pantalla no se podría comparar con el +57 (36-79) que publicó M5, y la demo sería una animación
bonita.

«Todo aquí es puro» es la consecuencia práctica: ninguna de estas funciones toca el DOM, ni un worker,
ni una promesa. Por eso `tests/arena.test.ts` puede fijar sus números contra los de la implementación
de Python sin cargar un modelo.

```ts title="src/lib/arena.ts"
/** How many plies the random openings have; six, as `rukh eval match` does by default. */
export const OPENING_PLIES = 6;
/** A game that reaches this many plies without a result counts as a draw, and is marked cut. */
export const MAX_PLIES = 300;

/** A small, seeded PRNG so a run with the same seed plays the same openings. */
export function mulberry32(seed: number): () => number {
  let state = seed >>> 0;
  return () => {
    state = (state + 0x6d2b79f5) >>> 0;
    let t = state;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

/** A random legal opening of `plies` moves in UCI; retried when it ends the game early. */
export function randomOpening(random: () => number, plies = OPENING_PLIES): string[] {
  for (;;) {
    const chess = new Chess();
    const moves: string[] = [];
    for (let i = 0; i < plies; i += 1) {
      const legal = chess.moves({ verbose: true });
      if (legal.length === 0) break;
      const pick = legal[Math.floor(random() * legal.length)];
      chess.move(pick);
      moves.push(`${pick.from}${pick.to}${pick.promotion ?? ''}`);
    }
    if (moves.length === plies && !chess.isGameOver()) return moves;
  }
}

/** `pairs` openings, each to be played twice with the colours swapped. */
export function openingBook(pairs: number, seed: number, plies = OPENING_PLIES): string[][] {
  const random = mulberry32(seed);
  return Array.from({ length: pairs }, () => randomOpening(random, plies));
}
```

<Src file="src/lib/arena.ts" repo="rukh-web" tag="b0bf7af" lines="15-52" />

`mulberry32` es un generador pseudoaleatorio de ocho líneas, y está aquí en vez de `Math.random`
porque **una arena con la misma semilla juega las mismas aperturas**. Sin eso, dos ejecuciones no se
pueden comparar ni siquiera consigo mismas, y la demo no podría enlazarse desde una lección
prometiendo lo que se va a ver. JavaScript no trae un generador con semilla en la plataforma, así que
o se escribe uno o se añade una dependencia por diez líneas.

`randomOpening` con un bucle infinito y un `return` dentro es la forma correcta de un
**rechazo-y-reintento**: si las seis jugadas al azar acaban la partida —mate del pastor incluido—, la
apertura no vale como punto de partida y se sortea otra. Escribirlo con un contador de intentos sería
más defensivo y añadiría un caso imposible que habría que tratar: la probabilidad de que seis jugadas
aleatorias terminen la partida es pequeña, y la de que ocurra mil veces seguidas no es un escenario
del que haya que protegerse.

`openingBook` genera las `pairs` aperturas de **un solo** generador sembrado, no una por semilla. Es
lo que hace que la apertura número cinco de una tirada con semilla 1 sea siempre la misma, y que pedir
más parejas no cambie las anteriores.

<Src file="src/lib/arena.ts" repo="rukh-web" tag="b0bf7af" lines="54-81" />

La propiedad que define el emparejamiento está en el comentario de `index`: el juego `2k` tiene a A
con blancas en la apertura `k`, y el `2k+1` cambia los colores sobre la **misma** apertura. Eso es lo
que saca la ventaja de las blancas de la comparación, y es la razón de que las partidas se cuenten por
parejas.

`cut` se cuenta aparte de las tablas. Una partida que llega a 300 <Term id="ply">plies</Term> sin resultado se anota como
tablas para el marcador, y el número de esas se publica al lado, porque «tablas porque ninguno supo
ganar» y «tablas porque se agotó el contador» no dicen lo mismo del modelo.

`separated` es un booleano que la interfaz usa para decidir si puede afirmar algo. Es la regla de M5
metida en un campo: si el intervalo contiene el cero, no hay diferencia demostrada, y la pantalla lo
dice con palabras y no solo con un color.

```ts title="src/lib/arena.ts"
/** Elo difference that explains a score, clipped away from 0 and 1 as the harness does. */
export function eloDifference(score: number): number {
  const p = Math.min(Math.max(score, 0.001), 0.999);
  return 400 * Math.log10(p / (1 - p));
}

/**
 * Percentile bootstrap of the Elo difference over the games (`samples` resamples, seeded).
 * The same estimator as `rukh.eval.match.bootstrap_interval`: resample games with replacement,
 * recompute the score, convert.
 */
export function bootstrapElo(
  scores: readonly number[],
  samples = 500,
  seed = 0,
): { low: number; high: number } | null {
  if (scores.length < 2) return null;
  const random = mulberry32(seed);
  const draws: number[] = [];
  for (let s = 0; s < samples; s += 1) {
    let total = 0;
    for (let i = 0; i < scores.length; i += 1) {
      total += scores[Math.floor(random() * scores.length)];
    }
    draws.push(eloDifference(total / scores.length));
  }
  draws.sort((a, b) => a - b);
  const at = (q: number) => draws[Math.min(draws.length - 1, Math.floor(q * draws.length))];
  return { low: at(0.025), high: at(0.975) };
}
```

<Src file="src/lib/arena.ts" repo="rukh-web" tag="b0bf7af" lines="83-112" />

El recorte de `p` a `[0,001, 0,999]` es el `eps` de este fichero, y merece pararse. La fórmula del Elo
a partir de una proporción es `400·log10(p / (1 − p))`, y en `p = 1` eso es infinito: un jugador que
gana todas las partidas no tiene una puntuación identificable, solo una cota inferior. Recortar
devuelve un número grande y finito en vez de `Infinity`, que es lo que permite que la interfaz siga
dibujando. Es **exactamente el mismo recorte** que hace el harness de Python, y por eso está aquí y no
en la capa de presentación: si los dos recortaran distinto, los dos números no serían comparables
aunque la fórmula fuera la misma.

El <Term id="bootstrap">bootstrap</Term> es el de M5: se remuestrean las partidas con reemplazo, se
recalcula el marcador, se convierte a Elo, y se toman los percentiles 2,5 y 97,5 de las 500
reconversiones. Lo importante es **qué** se remuestrea: las partidas, no las jugadas. El intervalo que
sale cubre el ruido de haber jugado esas partidas y no otras.

`samples = 500` y no mil: es un bucle de 500 × n operaciones en el hilo principal del navegador, y con
veinte partidas la diferencia entre 500 y 1000 remuestreos son decimales.

```ts title="src/lib/arena.ts"
export function summarize(games: readonly ArenaGame[], seed = 0): ArenaSummary {
  const scores = games.map((game) => game.score);
  const points = scores.reduce((sum, value) => sum + value, 0);
  const score = games.length > 0 ? points / games.length : 0;
  const interval = bootstrapElo(scores, 500, seed);
  return {
    games: games.length,
    score,
    wins: scores.filter((value) => value === 1).length,
    draws: scores.filter((value) => value === 0.5).length,
    losses: scores.filter((value) => value === 0).length,
    cut: games.filter((game) => game.cut).length,
    elo: games.length > 0 ? eloDifference(score) : null,
    low: interval?.low ?? null,
    high: interval?.high ?? null,
    separated: interval !== null && (interval.low > 0 || interval.high < 0),
  };
}

/** The result of a finished game from A's point of view, given who had White. */
export function scoreFor(result: string | null, aWhite: boolean): number {
  if (result === '1-0') return aWhite ? 1 : 0;
  if (result === '0-1') return aWhite ? 0 : 1;
  return 0.5;
}

/** How many games the match needs to call an edge of `elo` points at 95 % (`labs/m5`). */
export function gamesNeeded(elo: number): number {
  const p = 1 / (1 + 10 ** (-Math.abs(elo) / 400));
  const z = 1.959963985;
  return Math.ceil((z * z * p * (1 - p)) / (p - 0.5) ** 2);
}
```

`summarize` se llama después de **cada** partida, no al final, y por eso todos sus campos aguantan
listas de cero y de un elemento. Es lo que permite que la pantalla muestre el marcador creciendo con
su intervalo encogiéndose, que es la mejor forma de aprender de dónde sale un intervalo: se ve cómo
unas cuantas partidas no bastan.

`scoreFor` tiene un `return 0.5` como caso por defecto, que cubre las tablas **y** el `null` de una
partida sin resultado. Eso es coherente con `cut`: una partida cortada cuenta media, y se cuenta
aparte.

Y `gamesNeeded` es la función que convierte la demo en una lección. Es la <Term id="potencia-estadistica">potencia estadística</Term> de `labs/m5/games_needed_match.py`
traída al navegador: dado un tamaño de efecto en Elo, cuántas partidas hay que jugar para que su
intervalo del 95 % se separe del cero. Con `(p − 0,5)²` en el denominador, el coste crece con el
**cuadrado** de la precisión: ver una diferencia de 50 Elo pide unas 185 partidas, y ver una de 11
pide 3 832.

Enseñar ese número al lado de un marcador de veinte partidas es lo que impide leer diez partidas como
un veredicto. Es el mismo trabajo que hace el intervalo, dicho en la unidad en la que duele: partidas
que hay que jugar.

 * Live puzzles: the harness's puzzle criterion (`rukh.eval.puzzles`), in the browser.

 * A puzzle is attempted the way the table measured it (D-053): the model is prompted with the

Tres cosas tienen que coincidir con el harness para que el porcentaje de la pantalla se pueda comparar

/** UCI `e7e8q` as a `Move`. */
export function uciMove(uci: string): Move {
  return {
    from: uci.slice(0, 2),
    to: uci.slice(2, 4),
    promotion: (uci.slice(4, 5) || undefined) as Move['promotion'],
  };
}

/**
 * The game state the puzzle starts from: the real game replayed from the initial position, so
 * the prompt carries the prefix, and the board is the puzzle's FEN. Replaying the prefix must
 * land on that FEN (the first four fields); when it does not, the puzzle is malformed and is
 * skipped rather than attempted from a position the model never reached.
 */
export function puzzleStart(puzzle: Puzzle): GameState | null {
  const chess = new Chess();
  try {
    for (const uci of puzzle.prefix) chess.move(uciMove(uci));
  } catch {
    return null;
  }
  const reached = chess.fen().split(' ').slice(0, 4).join(' ');
  const expected = puzzle.fen.split(' ').slice(0, 4).join(' ');
  if (reached !== expected) return null;
  return {
    start: INITIAL_FEN,
    fen: chess.fen(),
    history: chess.history(),
    turn: chess.turn(),
    over: chess.isGameOver(),
    result: null,
  };
}

/** The moves the model has to find: the odd indices of the line. */
export function expectedMoves(puzzle: Puzzle): string[] {
  return puzzle.moves.filter((_, index) => index % 2 === 1);

Cuatro párrafos con cuatro decisiones, y las cuatro son de esas que se toman una vez y se agradecen

**«La mitad equivocada del objetivo».** La demo servía los modelos que el curso publicó. Pero alguien

la página cargara el modelo de alguien sin que lo pidiera. Perder el modelo al recargar es el precio, y
es pequeño: volver a elegir el fichero es un clic.

grafo cuyos logits no tengan las 2030 jugadas del tokenizador, así que un `.onnx` que no es un decoder

/*
 * Reading `rukh_block` out of the file.
 *
 * `rukh export` writes the context window into the ONNX `metadata_props`, and ORT Web does not
 * expose them (see `contract.ts`), which is why registry stages carry `block` by hand. A file
 * from somebody's disk has no registry entry, so the number has to come from the file.
 *
 * An ONNX file is a protobuf `ModelProto`. Walking its top-level fields is enough: every field is
 * a varint tag followed by either a varint or a length-delimited block, so the graph — the big
 * one — is skipped by advancing past its length without decoding any of it. No protobuf library,
 * no allocation, and it stops as soon as it finds the key.
 */

/** `metadata_props` in `ModelProto`; `key` and `value` in `StringStringEntryProto`. */
const METADATA_PROPS_FIELD = 14;
const KEY_FIELD = 1;
const VALUE_FIELD = 2;
const BLOCK_KEY = 'rukh_block';

interface Cursor {
  bytes: Uint8Array;
  at: number;
}

/** A protobuf varint, or null when it runs off the end or is implausibly long. */
function varint(c: Cursor): number | null {
  let result = 0;
  let shift = 0;
  while (c.at < c.bytes.length) {
    const byte = c.bytes[c.at];
    c.at += 1;
    result += (byte & 0x7f) * 2 ** shift;
    if ((byte & 0x80) === 0) return result;
    shift += 7;
    if (shift > 49) return null;
  }
  return null;
}

Aquí está la pieza más curiosa del hito: **cincuenta líneas que leen un campo de un protobuf sin una
librería de protobuf**.

El problema es concreto. `rukh export` escribe la ventana de contexto en los metadatos del `.onnx`, y
ONNX Runtime Web **no los expone** —eso ya se sabía desde M2, y por eso las etapas del registro llevan
su `block` escrito a mano en el catálogo de la demo. Un fichero que viene del disco de alguien no
tiene entrada en el registro, así que el número tiene que salir del fichero.

Un `.onnx` es un `ModelProto` de protobuf. Y resulta que para leer **un** campo de primer nivel no
hace falta entender el formato entero: cada campo es un tag _varint_ seguido de un valor, y el
tipo de cable del tag dice cuántos bytes ocupa el valor. El grafo —los 232 MB— se salta
avanzando su longitud **sin decodificar nada de él**. Ni librería, ni asignación de memoria, y para en
cuanto encuentra la clave.

La alternativa era añadir `protobufjs` al bundle de la demo: unos cientos de kilobytes para leer un
entero.

`varint` usa `* 2 ** shift` y no `<< shift`. Esa es la línea que hay que mirar dos veces: los
operadores de desplazamiento de JavaScript trabajan sobre 32 bits con signo, así que un
desplazamiento de 32 o más da la vuelta y produce un número equivocado en silencio. Multiplicar por
una potencia de dos en coma flotante es exacto hasta 2⁵³, que cubre cualquier longitud de fichero
real. Y el `shift > 49` es el corte: un varint más largo que eso no es un número plausible en este
formato, y devolver `null` es preferible a seguir leyendo basura.

Todo el lector devuelve `null` en vez de lanzar. Es la decisión de fondo: si el fichero no es lo que
se espera, **no se sabe** el `block`, y quien llama cae al 200 por defecto. Un lector de formato
binario que lanza excepciones ante un byte inesperado convierte un fichero raro en una pantalla roja.

/** The `StringStringEntryProto` at `[at, end)`, as a key/value pair. */
function entry(bytes: Uint8Array, at: number, end: number): { key: string; value: string } | null {
  const c: Cursor = { bytes, at };
  let key = '';
  let value = '';
  const decoder = new TextDecoder();
  while (c.at < end) {
    const tag = varint(c);
    if (tag === null) return null;
    const field = tag >>> 3;
    const wire = tag & 7;
    if (wire !== 2) {
      if (varint(c) === null) return null;
      continue;
    }
    const length = varint(c);
    if (length === null || c.at + length > end) return null;
    const text = decoder.decode(bytes.subarray(c.at, c.at + length));
    c.at += length;
    if (field === KEY_FIELD) key = text;
    else if (field === VALUE_FIELD) value = text;
  }
  return { key, value };
}

`tag >>> 3` es el número de campo y `tag & 7` el tipo de cable: así se codifica un tag de
protobuf, tres bits de tipo y el resto de número. Aquí sí se puede usar `>>>` porque el tag es
pequeño por construcción.

un fichero de 232 MB esa distinción no es cosmética.

La comprobación `c.at + length > end` está en todas las lecturas de longitud, y es la que impide que
un fichero manipulado haga leer fuera del bloque. `Uint8Array` no deja salirse del búfer, así que el
peor caso sería una cadena basura; la guarda hace que sea un `null`.

/** The `rukh_block` the exporter wrote, or null when the file does not carry one. */
export function readBlock(bytes: Uint8Array): number | null {
  const c: Cursor = { bytes, at: 0 };
  while (c.at < bytes.length) {
    const tag = varint(c);
    if (tag === null) return null;
    const field = tag >>> 3;
    const wire = tag & 7;

    if (wire === 0) {
      if (varint(c) === null) return null;
      continue;
    }
    if (wire === 5) {
      c.at += 4;
      continue;
    }
    if (wire === 1) {
      c.at += 8;
      continue;
    }
    if (wire !== 2) return null;

    const length = varint(c);
    if (length === null || c.at + length > bytes.length) return null;
    if (field === METADATA_PROPS_FIELD) {
      const pair = entry(bytes, c.at, c.at + length);
      if (pair && pair.key === BLOCK_KEY) {
        const block = Number.parseInt(pair.value, 10);
        return Number.isInteger(block) && block > 0 && block <= 8192 ? block : null;
      }
    }
    c.at += length;
  }
  return null;
}

Los cuatro tipos de cable están tratados uno por uno: `0` es un varint que se lee y se tira, `5` son
cuatro bytes, `1` son ocho, `2` es un bloque con longitud. Cualquier otro valor no es protobuf válido
y devuelve `null`. El bucle solo entra en `entry` cuando el campo es el 14, `metadata_props`, y para

El rango `block > 0 && block <= 8192` es la última guarda: un `rukh_block` con un valor absurdo se
trata como si no estuviera, y se usa el 200 por defecto. Un `block` de mil millones haría que el
recorte del prompt no recortara nada y la inferencia fallaría dentro del grafo con un error de forma.

El comentario del constructor lo dice de la mejor forma posible: «equivocarse en esto no es
silencioso». Si el `block` sale mal, el prompt se recorta a una longitud equivocada, y el panel
imprime bajo qué `block` está jugando la etapa. Una decisión con un valor por defecto es tolerable
cuando el valor elegido se puede ver.

async function loadSession(request: Extract<DecoderRequest, { type: 'init' }>) {
  /* A local model arrives whole: it was read from disk, so there is nothing to download and no
     progress to report. Everything after this point is identical, including the contract check
     that decides whether these bytes are a Rukh decoder at all. */
  const bytes =
    request.bytes ??
    (await fetchModel(request.url, request.sizeBytes, (loaded, total) =>
      reply({ type: 'progress', id: request.id, loaded, total }),
    ));
  return createSession(bytes);
}
```

<Src file="src/workers/decoder.worker.ts" repo="rukh-web" tag="b0bf7af" lines="64-74" />

Y aquí está todo el cambio del lado del worker: **una línea de `??`**. «Todo lo que viene después es
idéntico, incluida la comprobación del contrato que decide si estos bytes son un decoder de Rukh».

Eso es lo que hace que la función de «tu propio modelo» sea barata y segura a la vez. La validación no
se escribió para esto: existía desde M2 para rechazar una exportación corrupta descargada del Hub, y
protege exactamente igual a un fichero que viene del disco. Un camino nuevo que se une al viejo lo
antes posible hereda todas sus guardas; uno que las duplica hereda la mitad.

<Transfer concept="La frontera donde se unen dos caminos" where="Cualquier entrada nueva a un sistema que ya valida: un fichero subido frente a uno generado, un webhook frente a una llamada interna, un caché frente al origen.">
  Cuando hay que aceptar algo por una vía nueva, la pregunta no es qué validar, sino **en qué punto
  del camino existente empalmar**. Cuanto antes se una, menos código nuevo y menos guardas que
  reescribir; cuanto más tarde, más probable es que la vía nueva se salte una comprobación que nadie
  recuerda que existía.

Aquí el empalme está una línea antes de `createSession`, así que la única diferencia entre un modelo
descargado y uno del disco es de dónde salieron los bytes. Todo lo demás —el contrato, el ancho de
los logits, el informe del panel— es el mismo código. El equivalente en un backend es validar el
cuerpo de una petición en el mismo sitio venga de donde venga, y no una vez por endpoint.

</Transfer>

  // Keep the current ply visible once the list grows past its fixed height. Only the list
  // scrolls, never the page: `scrollIntoView` walks every scrollable ancestor, and on a
  // one-column layout that moved the document by hundreds of pixels *during* a touch, so the
  // click the browser synthesises after `touchend` landed on whatever had slid under the finger
  // (the mode switcher, once it existed). A page must not move because a move was played.
  useEffect(() => {
    const container = list.current;
    const current = container?.querySelector<HTMLElement>('.is-current');
    if (!container || !current) return;
    const box = container.getBoundingClientRect();
    const ply = current.getBoundingClientRect();
    if (ply.top < box.top) container.scrollTop += ply.top - box.top;
    else if (ply.bottom > box.bottom) container.scrollTop += ply.bottom - box.bottom;
  }, [history.length]);
```

<Src file="src/islands/MoveList.tsx" repo="rukh-web" tag="b0bf7af" lines="65-78" />

Este es el bloque más instructivo de la lección y no tiene nada de ajedrez.

`scrollIntoView({ block: 'nearest' })` es una línea razonable que funcionó durante cuatro módulos.
El problema apareció cuando existió el conmutador de modos: la función **recorre todos los ancestros
desplazables**, y en la maquetación de una columna eso movía el documento cientos de píxeles
**durante** un toque. El clic que el navegador sintetiza después del `touchend` caía sobre lo que
hubiera resbalado bajo el dedo, que era el conmutador de modos. Tocar una jugada en el móvil cambiaba
de modo.

El arreglo son seis líneas que hacen a mano lo que la función hacía, pero solo en el contenedor:
medir las dos cajas y mover `scrollTop` lo justo. Y la última frase del comentario es la regla
general: **una página no se mueve porque se haya jugado una jugada**.

<Callout kind="roto" title="Una API cómoda con un alcance más grande del que parece">
  `scrollIntoView` no tiene una opción para «solo este contenedor». La lección transferible no es
  que sea una función mala, es que una API cuyo alcance es «todos los ancestros» produce un fallo
  que no se reproduce hasta que existe un ancestro concreto. Y el síntoma fue el peor posible: un
  clic en un sitio que activaba otro, solo en táctil, solo con la maquetación de una columna, solo
  después de que el conmutador de modos se añadiera cuatro módulos más tarde.
</Callout>

<Exercise n="02" title="Rompe el lector de protobuf de la forma sutil">
  Cambia `result += (byte & 0x7f) * 2 ** shift` por `result |= (byte & 0x7f) << shift`. Los tests
  pasan. ¿Con qué fichero falla, y por qué es peor que un error?

  <Solution>
    Falla con cualquier campo cuya longitud pase de 2³¹, es decir con un grafo de más de 2 GB, y
    también con cualquier varint de cinco bytes o más: `<<` opera sobre 32 bits con signo, así que un
    `shift` de 28 en adelante da la vuelta y produce un entero negativo o pequeño. Lo que sale no es
    una excepción: es una longitud equivocada, con la que el bucle avanza el cursor a un sitio
    arbitrario y sigue leyendo tags que no son tags. El resultado más probable es un `null`
    y un `block` de 200 por defecto que puede ser el correcto por casualidad, así que el error se
    manifiesta como un prompt mal recortado en un modelo concreto. Los tests con ficheros pequeños no
    lo ven, y ahí está la trampa.
  </Solution>
</Exercise>

## Qué has aprendido

Una demo es donde se comprueba si lo que mediste significa algo para alguien que no lo midió. Y para
que lo signifique, lo que la pantalla calcula tiene que ser **el mismo cálculo**: la fórmula del Elo
con el mismo recorte, el bootstrap sobre las mismas unidades, el criterio del puzle con el mismo
prefijo. Un número del navegador que no se puede comparar con la tabla es un adorno.

Las dos decisiones que se llevan fuera son de diseño, no de ajedrez. La primera: cuando una entrada
nueva llega a un sistema que ya valida, se empalma **lo antes posible** con el camino existente, y
entonces hereda las guardas en vez de duplicarlas —una línea de `??` en el worker. La segunda: la
privacidad se construye quitando capacidades, no añadiendo promesas. Sin `fetch` no hay nada que
ensanchar, sin almacenamiento no hay nada que restaurar, y un test que cuenta cero peticiones es una
afirmación comprobable.
