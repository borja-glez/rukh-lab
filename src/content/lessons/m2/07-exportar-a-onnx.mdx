## Qué vas a construir

El fichero que descarga el navegador. `src/rukh/export/` convierte un checkpoint de PyTorch en tres
`.onnx` (fp32, fp16 e int8) y mide si los tres eligen la misma jugada que el original. Al final,
las dos visualizaciones del módulo: el entrenamiento checkpoint a checkpoint y el mapa de atención
de una partida.

El navegador no ejecuta PyTorch. El puente es <Term id="onnx">ONNX</Term>, un formato que describe
el grafo y los pesos y que `onnxruntime-web` ejecuta con WebGPU o con WASM. Es el problema de
cualquier despliegue fuera del entorno de entrenamiento (un móvil, un servidor sin Python, un LLM en
GGUF para tu portátil), y las comprobaciones de esta lección valen para todos.

## `onnx.py`: el grafo

```python title="src/rukh/export/onnx.py"
"""Exporting a ``MoveDecoder`` to ONNX for the browser.

The demo only ever needs the distribution over the *next* move, so the exported graph is not the
model itself but a wrapper whose forward returns the last step only: ``(B, V)`` instead of
``(B, T, V)``, which divides the output tensor by the context length (200) and saves the browser
from slicing a megabyte of logits per move.

``torch.onnx.export`` is tried with the dynamo exporter first (the default since torch 2.9 and
what ``docs/spec/02`` asks for) and falls back to the legacy TorchScript tracer with a warning
when dynamo is unavailable or fails; which path produced the file is recorded in the metadata,
because the two exporters do not emit the same graph and a parity check is only meaningful when
it is known which one ran.

``dynamic_seq`` is not taken on trust. The legacy tracer happily bakes the traced length into
the graph while still being asked for a dynamic axis, and the demo feeds a sequence that grows
by one token per move, so the exported file is **run** at two different lengths and the flag
reports what actually worked. The model's context (``block``) travels with the file as ONNX
metadata, so the browser knows the limit without being told separately.
"""
```

<Src file="src/rukh/export/onnx.py" tag="p2" lines="1-19" />

Tres decisiones, y cada una se paga si se omite:

- **Se exporta un envoltorio, no el modelo.** La demo solo necesita la distribución de la siguiente
  jugada, así que el `forward` exportado devuelve `(B, V)` en vez de `(B, T, V)`: doscientas veces
  menos números por jugada.
- Hay dos exportadores y no dan el mismo grafo. Dynamo es el moderno; TorchScript queda de
  respaldo. Cuál corrió se graba en el fichero, porque una paridad solo significa algo si sabes qué
  grafo comparas.
- **Un eje dinámico declarado es una promesa.** El trazador antiguo hornea la longitud trazada en el
  grafo mientras dice que el eje es dinámico. Como la demo alarga la secuencia una jugada por turno,
  el fallo saltaría en la segunda jugada de la primera partida. Por eso se comprueba ejecutando.

```python title="src/rukh/export/onnx.py"
class LastStepLogits(nn.Module):
    """Wraps a decoder so that ``forward(idx)`` returns only the last step's logits."""

    def __init__(self, model: MoveDecoder) -> None:
        super().__init__()
        self.model = model

    def forward(self, idx: Tensor) -> Tensor:
        logits, _ = self.model(idx)
        return logits[:, -1, :]
```

```python title="src/rukh/export/onnx.py"
@contextlib.contextmanager
def _utf8_console() -> Iterator[None]:
    """Let the exporter print its progress ticks on a legacy Windows code page.

    ``torch.onnx.export(dynamo=True)`` writes check marks to stdout. On Windows the console
    is cp1252 by default, so that raises ``UnicodeEncodeError`` inside the exporter and the
    whole export fails for a reason that has nothing to do with the model. Reconfiguring the
    streams to replace unencodable characters keeps the modern exporter usable; without it
    every Windows export silently falls back to the deprecated TorchScript one, which in turn
    produces an fp16 graph that onnxruntime refuses to load.
    """
    streams = [s for s in (sys.stdout, sys.stderr) if hasattr(s, "reconfigure")]
    previous = [(s, s.encoding, s.errors) for s in streams]
    for stream in streams:
        with contextlib.suppress(Exception):
            stream.reconfigure(errors="replace")
    try:
        yield
    finally:
        for stream, encoding, errors in previous:
            with contextlib.suppress(Exception):
                stream.reconfigure(encoding=encoding, errors=errors)
```

<Src file="src/rukh/export/onnx.py" tag="p2" lines="109-130" />

Un arreglo de Windows con una cadena de consecuencias que enseña. El exportador dynamo imprime
marcas Unicode en su barra de progreso; la consola de Windows es cp1252, así que salta un
`UnicodeEncodeError` dentro del exportador, se cae al antiguo, y ese produce un fp16 que
`onnxruntime` se niega a cargar. Una configuración regional de la consola acaba en un modelo que el
navegador no puede ejecutar. Sustituir los caracteres que no se pueden codificar rompe la cadena en
el primer eslabón.

```python title="src/rukh/export/onnx.py"
def export_onnx(
    ckpt: Path | MoveDecoder,
    out: Path,
    opset: int = DEFAULT_OPSET,
    dynamic_batch: bool = True,
    seq_len: int = 200,
    dynamic_seq: bool = True,
) -> ExportResult:
    """Export the next-move head of a checkpoint to ONNX and report which exporter ran.

    ``ckpt`` may be a checkpoint path or an already-built model (the tests use the latter).
    ``seq_len`` is the length of the example the exporter traces; with ``dynamic_seq`` the graph
    still accepts any length up to the model's block, which is what the demo feeds it as a game
    grows move by move.
    """
    model = ckpt if isinstance(ckpt, MoveDecoder) else _load(Path(ckpt))
    model = model.eval()
    if seq_len > model.cfg.block:
        raise ValueError(f"seq_len={seq_len} is longer than the model's block {model.cfg.block}")
    wrapper = LastStepLogits(model).eval()
    example = torch.zeros((1, seq_len), dtype=torch.long)
    path = target_path(out)
    path.parent.mkdir(parents=True, exist_ok=True)
```

```python title="src/rukh/export/onnx.py"
def sequence_lengths(seq_len: int, block: int) -> list[int]:
    """Two lengths to run the exported file at: the traced one and a different, legal one."""
    other = seq_len + 1 if seq_len < block else max(1, seq_len - 1)
    return sorted({seq_len, other})
```

```python title="src/rukh/export/onnx.py"
def verify_dynamic_seq(path: Path, seq_len: int, block: int) -> bool | None:
    """Run the file at two sequence lengths; None when ``onnxruntime`` is not installed."""
    import numpy as np

    try:
        import onnxruntime as ort
    except ImportError:
        log.warning("onnxruntime is not installed: the dynamic sequence axis was not verified")
        return None
    lengths = sequence_lengths(seq_len, block)
    if len(lengths) < 2:  # pragma: no cover - block of 1 is not a usable model
        return None
    session = ort.InferenceSession(str(path), providers=["CPUExecutionProvider"])
    for length in lengths:
        try:
            session.run(None, {INPUT_NAME: np.zeros((1, length), dtype=np.int64)})
        except Exception as exc:  # noqa: BLE001 - any refusal means the axis is not dynamic
            log.info("the exported graph refused a sequence of %d tokens: %s", length, exc)
            return False
    return True
```

```python title="src/rukh/export/onnx.py"
def set_metadata(path: Path, entries: dict[str, str]) -> dict[str, str]:
    """Write ``metadata_props`` verbatim into a file; empty when ``onnx`` is not installed."""
    try:
        import onnx
    except ImportError:
        log.warning("onnx is not installed: the model metadata (block, vocab) was not written")
        return {}
    model = onnx.load(str(path))
    onnx.helper.set_model_props(model, entries)
    onnx.save(model, str(path))
    # The dynamo exporter writes the weights next to the graph as `<name>.onnx.data` and points
    # the initializers at it. `onnx.load` above pulled them into memory and `onnx.save` wrote
    # them back inline, so the sidecar is now dead weight that would ship to the browser (or be
    # published to the Hub) without ever being read. Drop it, but only once the file really is
    # self-contained.
    sidecar = path.with_suffix(path.suffix + ".data")
    if sidecar.is_file() and not any(
        tensor.data_location == onnx.TensorProto.EXTERNAL for tensor in model.graph.initializer
    ):
        sidecar.unlink()
        log.debug("removed the external-data sidecar %s", sidecar.name)
    return entries
```

## `quantize.py`: la mitad y la cuarta parte

```python title="src/rukh/export/quantize.py"
"""Half precision and dynamic int8 for the two browser backends.

WebGPU runs the fp16 graph (``small`` is about 80 MB that way); the WASM fallback runs the int8
one (about 40 MB), which is the difference between a demo that loads on a phone and one that
does not. Quantization is restricted to ``MatMul`` and ``Gemm``: those are the weights that make
up almost the whole file, and quantizing the rest costs accuracy for nothing.

``onnxconverter_common`` does the fp16 conversion properly (it keeps the graph's inputs and
outputs in float32 and leaves the ops that overflow in fp32). When it is not installed there is
a smaller fallback here that casts the float initializers with ``onnx.numpy_helper`` and puts a
``Cast`` back to float32 in front of the output; ``to_fp16`` reports which of the two ran.
"""
```

```python title="src/rukh/export/quantize.py"
def to_fp16(path: Path, out: Path | None = None) -> QuantizeResult:
    """Convert an fp32 ONNX model to fp16, in place of ``model.onnx``'s sibling by default."""
    import onnx

    source = Path(path)
    target = _sibling(source, FP16_NAME, out)
    target.parent.mkdir(parents=True, exist_ok=True)
    model = onnx.load(str(source))
    try:
        from onnxconverter_common import float16

        converted = float16.convert_float_to_float16(model, keep_io_types=True)
        method = "onnxconverter_common.float16"
    except ImportError:
        converted = _cast_initializers(model)
        method = "onnx.numpy_helper fallback"
        log.warning("onnxconverter_common is not installed; used the initializer-casting fallback")
    onnx.save(converted, str(target))
    return QuantizeResult(
        path=target.as_posix(),
        kind="fp16",
        method=method,
        bytes=target.stat().st_size,
        source_bytes=source.stat().st_size,
    )
```

```python title="src/rukh/export/quantize.py"
def _cast_initializers(model: object) -> object:
    """Fallback fp16 conversion: cast every float initializer and cast the outputs back.

    Only the weights change type. Every float-typed value in the graph is retyped to fp16 and a
    ``Cast`` node is appended so the model still hands the caller float32 logits, which keeps the
    demo's input and output contract identical to the fp32 file.
    """
    import numpy as np
    import onnx
    from onnx import TensorProto, helper, numpy_helper

    graph = model.graph  # type: ignore[attr-defined]
    for initializer in graph.initializer:
        if initializer.data_type != TensorProto.FLOAT:
            continue
        array = numpy_helper.to_array(initializer).astype(np.float16)
        initializer.CopyFrom(numpy_helper.from_array(array, initializer.name))
    for value in list(graph.value_info) + list(graph.input):
        if value.type.tensor_type.elem_type == TensorProto.FLOAT:
            value.type.tensor_type.elem_type = TensorProto.FLOAT16
    for node in graph.node:
        for attribute in node.attribute:
            if attribute.type == onnx.AttributeProto.TENSOR:
                tensor = attribute.t
                if tensor.data_type == TensorProto.FLOAT:
                    array = numpy_helper.to_array(tensor).astype(np.float16)
                    tensor.CopyFrom(numpy_helper.from_array(array, tensor.name))
    for output in graph.output:
        if output.type.tensor_type.elem_type != TensorProto.FLOAT:
            continue
        inner = f"{output.name}_fp16"
        for node in graph.node:
            node.output[:] = [inner if name == output.name else name for name in node.output]
        graph.node.append(
            helper.make_node("Cast", [inner], [output.name], to=int(TensorProto.FLOAT))
        )
    return model
```

## `parity.py`: ¿elige la misma jugada?

```python title="src/rukh/export/parity.py"
"""Parity between PyTorch and ONNX Runtime: the same move, and how far the logits drifted.

The acceptance criterion of ``docs/spec/02`` is the *move*, not the logits: the demo picks an
``argmax`` (or samples from a truncated distribution), so a file that disagrees with PyTorch on
0.1 % of positions is fine and one that agrees on the numbers but not on the move is not. Both
are reported: ``agreement`` is the share of positions where the chosen token matches, and
``max_abs_logit_delta`` is the worst absolute difference seen anywhere in the logits, which is
what tells fp32, fp16 and int8 apart.

The positions are the thousand **validation** prefixes of ``docs/spec/02`` §6, the same ones the
legality and accuracy metrics use: a random legal walk visits positions no human would reach, so
agreeing on them says little about the file the demo will load. ``random_prefixes`` stays for the
case where no validation parquet is around (and for the tests), and which of the two was used is
reported alongside the number.
"""
```

<Src file="src/rukh/export/parity.py" tag="p2" lines="1-15" />

**El criterio es la jugada.** Elegir depende del orden de los logits, no de su valor: un error
numérico grande puede dejar casi todo intacto y uno pequeño voltear justo las decisiones ajustadas.
Por eso se publican los dos números.

Las posiciones son las mil de validación, las mismas de la legalidad y la exactitud. Un paseo
aleatorio visita posiciones a las que ningún humano llega; se queda como respaldo, y la fuente
usada se publica al lado del número.

```python title="src/rukh/export/parity.py"
def random_prefixes(
    tok: UciTokenizer,
    n: int,
    seed: int = 0,
    min_ply: int = 1,
    max_ply: int = 40,
) -> list[list[int]]:
    """Token-id prefixes of random legal games, for a parity check without any dataset.

    Every prefix is a real sequence of legal moves, so the model is asked the kind of question
    the demo asks it, and the walk is seeded so a parity number can be reproduced exactly.
    """
    rng = random.Random(seed)
    prefixes: list[list[int]] = []
    while len(prefixes) < n:
        board = chess.Board()
        ids = [
            tok.bos_id,
            tok.vocab["<w1800>"],
            tok.vocab["<b1800>"],
        ]
        plies = rng.randint(min_ply, max_ply)
        for _ in range(plies):
            moves = list(board.legal_moves)
            if not moves:
                break
            move = rng.choice(moves)
            ids.append(tok.vocab.get(move.uci(), tok.unk_id))
            board.push(move)
        prefixes.append(ids)
    return prefixes
```

```python title="src/rukh/export/parity.py"
def parity_positions(
    tok: UciTokenizer,
    n: int = DEFAULT_N,
    block: int = 200,
    seed: int = 0,
    games: Path | None = None,
) -> tuple[list[list[int]], str, str | None]:
```

```python title="src/rukh/export/parity.py"
def parity(
    ckpt: Path | MoveDecoder,
    onnx_path: Path,
    positions: Sequence[Sequence[int]],
    n: int = DEFAULT_N,
) -> ParityResult:
    """Compare the argmax token and the logits of the checkpoint and the exported file."""
    model = ckpt if isinstance(ckpt, MoveDecoder) else _load(Path(ckpt))
    wrapper = LastStepLogits(model.eval()).eval()
    session = _session(Path(onnx_path))
    used = list(positions)[:n]
    if not used:
        raise ValueError("parity needs at least one position")

    agreed = 0
    worst = 0.0
    mismatches: list[int] = []
    for index, history in enumerate(used):
        idx = np.asarray([list(history)], dtype=np.int64)
        with torch.no_grad():
            reference = wrapper(torch.from_numpy(idx)).numpy()[0].astype(np.float64)
        exported = np.asarray(session.run(None, {INPUT_NAME: idx})[0])[0].astype(np.float64)
        worst = max(worst, float(np.max(np.abs(reference - exported))))
        if int(np.argmax(reference)) == int(np.argmax(exported)):
            agreed += 1
        elif len(mismatches) < MAX_MISMATCHES:
            mismatches.append(index)
    return ParityResult(
        positions=len(used),
        agreement=agreed / len(used),
        max_abs_logit_delta=worst,
        mismatches=mismatches,
    )
```

```python title="src/rukh/export/__init__.py"
def export_all(
    ckpt: Path,
    out: Path,
    opset: int = DEFAULT_OPSET,
    seq_len: int = 200,
    fp16: bool = False,
    int8: bool = False,
    check_parity: bool = False,
    positions: int = 1_000,
    seed: int = 0,
    games: Path | None = None,
) -> ExportBundle:
    """Export, quantize and check one checkpoint in a single pass.

    Parity is measured on validation positions (``games``, or the validation month of P1 when it
    is on disk) and falls back to random legal walks with a warning when there are none.
    """
    from rukh.tokenize.uci_vocab import UciTokenizer
    from rukh.train import load_model

    model, _payload = load_model(Path(ckpt))
    bundle = ExportBundle(onnx=export_onnx(model, out, opset=opset, seq_len=seq_len))
    if fp16:
        bundle.fp16 = to_fp16(Path(bundle.onnx.path))
    if int8:
        bundle.int8 = quantize_int8(Path(bundle.onnx.path))
    # The demo loads the fp16 or the int8 file, not the fp32 one, so the context length has to
    # travel with them too; neither converter promises to keep the metadata of its input.
    for quantized in (bundle.fp16, bundle.int8):
        if quantized is not None and bundle.onnx.metadata:
            set_metadata(Path(quantized.path), bundle.onnx.metadata)
    if check_parity:
        prefixes, source, warning = parity_positions(
            UciTokenizer(), n=positions, block=model.cfg.block, seed=seed, games=games
        )
        bundle.parity_source = source
        bundle.parity_warning = warning
        checks = {"fp32": bundle.onnx.path}
        if bundle.fp16 is not None:
            checks["fp16"] = bundle.fp16.path
        if bundle.int8 is not None:
            checks["int8"] = bundle.int8.path
        bundle.parity = {
            kind: parity(model, Path(path), prefixes, n=positions) for kind, path in checks.items()
        }
    return bundle
```

<Exercise n="01" title="¿Por qué int8 cambia los logits y no la jugada?">
  La diferencia máxima de logits del int8 es más de cien veces la del fp16 (1,75 frente a 0,01404),
  y aun así su paridad de jugada es del 95,40 %. Explica por qué un desastre en los logits se queda
  en un desperfecto moderado en las jugadas, y en qué posiciones esperarías que int8 falle.

  <Solution>
    Int8 representa cada matriz con 256 niveles y una escala por tensor: un error del 0,4 % por
    peso que se acumula en doce capas y desplaza los logits de forma visible. Pero elegir depende
    del orden de los logits, y en la mayoría de posiciones la distancia entre el primero y el
    segundo es mucho mayor que ese ruido. fp16, con 10 bits de mantisa, mete un error unas cien
    veces menor.

Int8 falla donde el margen es pequeño: dos o tres jugadas casi empatadas (aperturas con varias
continuaciones estándar, finales simples donde varias jugadas mantienen la evaluación) o posiciones
en las que el modelo duda en general. Ahí las jugadas suelen ser igual de razonables, así que el
efecto sobre la fuerza probablemente es menor que un 4,6 %. Pero es un «probablemente» que nadie ha
medido, y por eso el 95,40 % se publica como incumplimiento del listón y no como nota al pie.

  </Solution>

La isla recorre los checkpoints de la tirada real: un paso del deslizador, un `step-*.pt`. El
gráfico dibuja las dos pérdidas contra el eje izquierdo y el top-1 contra el derecho; debajo van
los números del checkpoint elegido, con la legalidad sin máscara y el Elo estimado, que en esta
tirada no se midió (sale un guion). El JSON lo produce `labs/m2/replay_export.py`, en la lección 10.

Tres cosas que mirar, en este orden:

1. **Dónde se separan las dos pérdidas.** Mientras van juntas, el modelo generaliza. Donde la de
   validación se aplana y la otra sigue bajando empieza el sobreajuste, y eso decide el `best.pt`.
2. Cuánto compra la segunda mitad. Compara el paso 10 000 con el 20 000: esa diferencia de top-1 es
   lo que valieron veinte minutos de GPU.
3. Cuándo despega la legalidad. Del paso 1 000 al 8 000 pasa de 88,0 % a 99,0 %; sigue hasta el
   final y comprueba que ya no se mueve.

<TrainingReplay client:visible />

Casi todo el descenso ocurre pronto. De la pérdida de validación de 2,6279 en el paso 1 000 a la de
1,5197 en el 20 000, 0,85 caen en los primeros 5 000 pasos y solo 0,26 en los 15 000 restantes. El
top-1 sube 12,2 puntos en los primeros 5 000 pasos, 5,6 en los siguientes, y la segunda mitad
entera (del 10 000 al 20 000) compró 2,4.

En los pasos 1 000 y 2 000 la validación va por debajo de la de entrenamiento, por el motivo del
segundo ejercicio de la lección 3. Se cruzan en el 3 000 y desde ahí el hueco crece: +0,021 en el
10 000, +0,046 en el 15 000 y +0,060 en el 20 000, un 4 % de la pérdida. Hay sobreajuste, pero la
validación todavía baja en los últimos mil pasos, así que el `best.pt` es el último checkpoint. La
lectura obvia es que faltaba entrenar más; la última lección del módulo la pone a prueba y
encuentra otra causa.

La fila de la legalidad es donde se ve emerger el juego. El modelo no tiene tablero ni reglas:
solo ve secuencias de símbolos. En el paso 1 000 propone una jugada imposible en el 12 % de las
posiciones; en el 8 000 respeta las reglas en el 99,0 %. Y ahí se para: hasta el 20 000 solo gana
una posición de 400 (99,25 %), mientras la pérdida de validación baja de 1,6727 a 1,5197 y el top-1
sube de 47,78 % a 51,20 %. **La legalidad satura mucho antes que la pérdida.**

No leas de más la parte plana. Cada punto se midió sobre 400 posiciones, así que el ruido ronda
±1 punto: el 99,75 % del paso 15 000 y el 99,25 % del 20 000 son 399 y 397 posiciones legales. Lo
que significa algo es el tramo de subida.

De ahí sale lo más importante de la sección: **legalidad y fuerza son cosas distintas**. En el paso
8 000 el modelo ya cumple las reglas y juega peor que en el 20 000, con una pérdida un 10 % más alta
y 3,4 puntos menos de top-1. Saber que un alfil va en diagonal no es saber adónde conviene moverlo.
Un LLM aprende pronto a escribir frases gramaticales y JSON bien formado, y mucho después a decir
cosas correctas con ellos. Por eso el ≥ 99 % es un requisito de entrada y la tabla única trae además
top-1, puzles y Elo. El Elo por checkpoint (`--with-elo`) cuesta una noche de partidas y no se midió:
se sabe cuánta imitación compró cada tramo, no cuánta fuerza.

## Ver la atención: AttentionMap

Abajo está la matriz de una cabeza de una capa sobre una partida corta (el mate de Légal, trece
jugadas más los tokens de control). Cada fila es una jugada que mira; cada columna, una jugada
mirada. La mitad superior derecha está vacía: es la máscara causal, que ahora puedes ver en lugar
de creértela. El color es relativo al máximo de la cabeza elegida, así que solo tiene sentido
comparar dentro de una cabeza.

Qué buscar mientras cambias de capa y de cabeza:

- **La subdiagonal encendida.** Justo a la izquierda de la diagonal está «la jugada anterior», el
  vecino más informativo de una secuencia. Suele haber alguna cabeza dedicada a ella; en este
  modelo hay una sola, y la isla abre en ella (capa 9, cabeza 4).
- **Columnas verticales.** Una columna entera encendida es un token al que mira todo el mundo. En
  los Transformers de texto se llama sumidero de atención: la cabeza no tiene nada útil que mirar y
  vuelca su peso en el primer token. Es quien, en una reunión, mira al techo cuando la pregunta no
  va con él; una columna encendida en `<bos>` es el estado de reposo, no un hallazgo.
- **Saltos lejos de la diagonal.** La jugada 12 mirando a la 5, cuando se movió la pieza que ahora
  se captura. Es lo más cerca que se está de ver al modelo «razonar» sobre el tablero, y lo más
  fácil de sobreinterpretar.
- **Diferencias entre capas.** Se suele contar que las primeras capas son locales, las del medio
  estructuradas y las últimas difusas. Compruébalo antes de repetirlo: aquí la mitad no se cumple.

<Callout kind="roto" title="Lo que un mapa de atención no demuestra">
  Es tentador señalar una celda encendida y decir «aquí el modelo ve que el caballo está clavado».
  No lo sabes. Los pesos de atención dicen de dónde se copió información, no qué era ni para qué se
  usó, y hay modelos con atenciones muy distintas y el mismo comportamiento. Vale igual para los
  mapas de atención que «explican» la respuesta de un LLM de texto. Un mapa es una pista y un buen
  instrumento de depuración (una cabeza que mira siempre al mismo sitio suele estar muerta); la
  prueba exige intervenir: cambiar algo y ver si el comportamiento cambia. De eso va la sección
  siguiente.
</Callout>

## Por qué el modelo «aprende el tablero» sin verlo

El modelo nunca ha visto un tablero. Tiene 2 030 símbolos y seis millones de secuencias, y aun así
propone jugadas legales el 99,4 % de las veces, lo que exige saber dónde está cada pieza después de
cuarenta movimientos, incluida la torre que no se mueve desde la jugada 3. Esa información no está
en el token actual: hay que reconstruirla de toda la historia.

La lectura obligatoria del módulo es _Chess-GPT's Internal World Model_ (2024), de Adam Karvonen,
[en su web](https://adamkarvonen.github.io/machine_learning/2024/01/03/chess-world-models.html),
con código y modelos bajo licencia MIT. Un nanoGPT de 50 millones de parámetros, entrenado con 16
millones de partidas en PGN carácter a carácter, llegó a unos 1300 de Elo con un 99,8 % de jugadas
legales en un día de GPU. `small` mide 1359 y 99,4 % con 5,9 millones de partidas, 42 minutos y un
modelo un 22 % más pequeño. Son del mismo orden y con escaleras distintas: sirve para calibrar, no
para ganar.

**Qué se demostró.** El método son las <Term id="probe-lineal">sondas lineales</Term>: se congela el
modelo, se toman las activaciones de una capa intermedia y se entrena una regresión lineal (una
matriz, sin capas ocultas) para predecir qué pieza hay en cada una de las 64 casillas. Acierta casi
siempre: el tablero está en las activaciones de forma linealmente legible, aunque nadie se lo
enseñara.

Una sonda lineal es como una nota final ponderada: tanto por el examen, tanto por las prácticas,
sumado. No calcula nada por su cuenta. Si con una suma ponderada de las activaciones ya sale «hay un
caballo en f3», el tablero estaba escrito en ellas. Una sonda con capas ocultas podría estar
calculándolo ella, y no demostraría nada sobre el modelo.

La segunda parte convierte la correlación en algo más fuerte. Karvonen interviene: empuja las
activaciones en la dirección que la sonda asocia a «hay una pieza en esta casilla», como si la
borrase del tablero interno, y las jugadas del modelo cambian de forma coherente con el tablero
editado. La representación no solo está ahí: el modelo la usa.

Qué no se demostró, que importa más para tu criterio:

- Que el modelo tenga reglas. Puede haber aprendido las regularidades que produce el tablero sin la
  regla que las genera, y solo la regla generaliza a posiciones raras.
- Que busque o calcule. Hay una única pasada hacia delante con un número fijo de operaciones. Ese es
  seguramente el techo del enfoque, y el motivo de que el modelo de DeepMind que llegó a 2895 sin
  búsqueda (Ruoss et al., 2024) necesitara 270 millones de parámetros y diez millones de partidas
  anotadas por Stockfish.
- Que cualquier representación sea recuperable. Una sonda encuentra lo linealmente legible; que no
  encuentre algo no significa que no esté.
- Nada sobre nuestra tokenización (una jugada por token, no PGN por carácter). Es una hipótesis
  hasta que la midas, y por eso M3 monta sondas sobre nuestro propio encoder.
- Y una trampa lógica: el tablero es función determinista de la lista de jugadas, así que la
  información está por fuerza en la entrada. Lo sorprendente es que el modelo la haya destilado en
  forma explícita y lineal: esa es la frontera entre memorizar la secuencia y modelar el dominio.

<Callout kind="mundo-real" title="Por qué esto es la discusión de los LLM en miniatura">
  «¿Los modelos de lenguaje entienden o solo predicen la siguiente palabra?» En texto es difícil de
  responder, porque no hay un estado del mundo con el que contrastar las activaciones. En ajedrez
  sí: el tablero es objetivo, pequeño y verificable, y por eso este dominio se ha convertido en un
  banco de pruebas de interpretabilidad. Cuando en A1 discutas si un LLM «sabe» algo, tendrás una
  intuición anclada en un experimento tuyo.
</Callout>
