## Qué vas a construir

Hasta aquí el pipeline ha tratado las partidas como cadenas. Este paso las abre: recorre 300 000
partidas jugada a jugada, se queda con cada **posición**, las deduplica contando cuántas veces se vio
cada una y cruza el resultado con las 395 millones de posiciones que Lichess publica evaluadas por <Term id="stockfish">Stockfish</Term>.

Ese cruce es contra 42 GB de parquet remoto que no vamos a descargar: se empuja el filtro al origen y
solo viajan las filas que coinciden. De aquí salen las etiquetas del encoder de M3 y, gratis, los
pares de preferencia para el DPO de M5. Son tres ficheros.

## `positions.py`: de partidas a posiciones

```python title="src/rukh/data/positions.py"
"""Positions from the UCI games: normalized 4-field FEN, phase, deduplicated with a count.

``fen4`` is ``pieces turn castling en-passant`` (the key of
``Lichess/chess-position-evaluations``); move counters are dropped so the same position from
different games collapses into one row with ``n_seen`` occurrences. The first occurrence wins
the ``game_id``/``ply``/``last_move``/``result`` columns.
"""

from __future__ import annotations

from collections.abc import Iterator
from pathlib import Path

import pyarrow as pa
import pyarrow.parquet as pq
from pydantic import Field

from rukh.config import BaseConfig
from rukh.data.db import DuckDbConfig
from rukh.data.db import connect as db_connect
from rukh.data.manifest import FileHash, Manifest
from rukh.data.parallel import run_batches
from rukh.data.uci import resolve_workers, sha256_file
from rukh.paths import resolve

OPENING_MAX_PLY = 10
MIDDLEGAME_MIN_PIECES = 14
BATCH_GAMES = 5_000
POSITIONS_FILE = "positions.parquet"
PARTS_DIR = "parts"
POSITION_SCHEMA = pa.schema(
    [
        ("seq", pa.int64()),
        ("fen4", pa.string()),
        ("game_id", pa.int64()),
        ("ply", pa.int16()),
        ("last_move", pa.string()),
        ("result", pa.string()),
        ("phase", pa.string()),
    ]
)
```

El docstring define **`fen4`**, el concepto de toda la lección. Un <Term id="fen">FEN</Term>
completo tiene seis campos: piezas, turno, enroques, casilla al paso, el contador de la regla de las
cincuenta jugadas y el número de jugada. Los dos últimos son contadores, no posición: el mismo
tablero en la jugada 20 de una partida y en la 24 de otra tiene distinto FEN completo.

Quitarlos colapsa en una fila las partidas que llegan a la misma posición, con `n_seen` contando
cuántas veces se vio, y el ahorro es todo el coste del paso siguiente. Además, `fen4` es la clave con
la que Lichess publica sus evaluaciones: sin esta normalización no habría join.

Las constantes de fase son convenciones del proyecto, por eso van al manifiesto. Lo que se les pide
es que "final" signifique lo mismo en los pares de preferencia y en las tablas por fase de M3 y M5.

```python title="src/rukh/data/positions.py"
def fen4(board: object) -> str:
    """First four FEN fields, built without the move counters python-chess would format.

    The en-passant square is written only when the capture is legal, which is the convention
    of ``Lichess/chess-position-evaluations``.
    """
    import chess

    ep = chess.SQUARE_NAMES[board.ep_square] if board.has_legal_en_passant() else "-"  # type: ignore[attr-defined]
    turn = "w" if board.turn else "b"  # type: ignore[attr-defined]
    return f"{board.board_fen()} {turn} {board.castling_xfen()} {ep}"  # type: ignore[attr-defined]


def phase(ply: int, n_pieces: int) -> str:
    """``opening`` up to ply 10, ``middlegame`` with 14+ pieces afterwards, else ``endgame``."""
    if ply <= OPENING_MAX_PLY:
        return "opening"
    return "middlegame" if n_pieces >= MIDDLEGAME_MIN_PIECES else "endgame"
```

<Src file="src/rukh/data/positions.py" tag="p1" lines="56-73" />

La línea que hay que leer dos veces es la del `ep`. `board.ep_square` está puesto siempre que el
último movimiento fue un peón dos casillas, aunque ninguna captura al paso sea legal;
`has_legal_en_passant()` solo es cierto cuando la captura se puede hacer de verdad.

<Callout kind="roto" title="La cobertura que baja unos puntos y nadie sabe por qué">
  Lichess escribe la casilla al paso solo cuando la captura es legal. Un `fen4` construido con
  `ep_square` coincide con el suyo en casi todas las posiciones y discrepa en las que tienen un peón
  recién avanzado dos casillas sin nadie que lo capture, que son muchas: le pasa a `e2e4` en la
  primera jugada de cada partida.

El `SEMI JOIN` se salta esas posiciones en silencio y la cobertura sale unos puntos más baja, sin
error ni traza. Es el fallo más caro de un pipeline de datos: **una clave que casi casa**. Pasa igual
al cruzar por un correo con mayúsculas distintas o por una URL con o sin barra final. Cuando cruces
por una clave construida, coge veinte filas del origen ajeno y comprueba que tu clave coincide con la
suya carácter a carácter; un test de esta lección hace eso.

</Callout>

La cadena se construye a mano en vez de cortar `board.fen().split()[:4]` porque esto corre
veintitrés millones de veces, y por lo mismo las piezas se cuentan con `chess.popcount` sobre el
bitboard y no construyendo un diccionario por posición.

```python title="src/rukh/data/positions.py"
def walk_game(game_id: int, uci: str, result: str) -> Iterator[tuple[str, int, int, str, str, str]]:
    """Yield ``(fen4, game_id, ply, last_move, result, phase)`` after every move."""
    import chess

    board = chess.Board()
    for ply, token in enumerate(uci.split(), start=1):
        move = chess.Move.from_uci(token)
        board.push(move)
        yield fen4(board), game_id, ply, token, result, phase(ply, chess.popcount(board.occupied))


def walk_rows(rows: list[tuple[int, str, str]]) -> dict[str, list[object]]:
    """Walk a batch of ``(game_id, uci, result)``; module-level for the spawn pool."""
    out: dict[str, list[object]] = {name: [] for name in POSITION_SCHEMA.names if name != "seq"}
    for game_id, uci, result in rows:
        for fen, gid, ply, last_move, res, ph in walk_game(game_id, uci, result):
            out["fen4"].append(fen)
            out["game_id"].append(gid)
            out["ply"].append(ply)
            out["last_move"].append(last_move)
            out["result"].append(res)
            out["phase"].append(ph)
    return out
```

<Src file="src/rukh/data/positions.py" tag="p1" lines="76-98" />

`walk_rows` es otra vez una función de módulo, el punto de entrada del pool de `spawn`, y construye
un diccionario de columnas porque esa es la forma que Arrow guarda en memoria. La columna `seq` (la
posición global de cada fila) no la puede calcular el worker, que no sabe cuántos lotes le
precedieron: se añade al escribir.

```python title="src/rukh/data/positions.py"
def iter_games(games: Path, n_games: int) -> Iterator[list[tuple[int, str, str]]]:
    """Batches of ``(game_id, uci, result)``, read from the parquet in row groups."""
    reader = pq.ParquetFile(games)
    remaining = n_games
    for batch in reader.iter_batches(batch_size=BATCH_GAMES, columns=["game_id", "uci", "result"]):
        if remaining <= 0:
            return
        rows = list(
            zip(
                batch.column("game_id").to_pylist(),
                batch.column("uci").to_pylist(),
                batch.column("result").to_pylist(),
                strict=True,
            )
        )[:remaining]
        remaining -= len(rows)
        yield rows
```

<Src file="src/rukh/data/positions.py" tag="p1" lines="101-117" />

`iter_games` pide tres columnas de las diez, y como el parquet es columnar solo lee esas tres del
disco. Al llegar a `n_games`, el `return` corta el generador y no se lee un grupo de filas más.

```python title="src/rukh/data/positions.py"
def write_parts(games: Path, parts_dir: Path, cfg: PositionsConfig) -> int:
    """Walk the games into ``parts_dir/part-NNNN.parquet`` (all positions, not deduplicated)."""
    parts_dir.mkdir(parents=True, exist_ok=True)
    for old in parts_dir.glob("part-*.parquet"):
        old.unlink()
    workers = resolve_workers(cfg.workers)
    batches = iter_games(games, cfg.n_games)
    return _write_parts(parts_dir, run_batches(walk_rows, batches, workers), 0)


def _write_parts(parts_dir: Path, results: Iterator[dict[str, list[object]]], seq: int) -> int:
    for index, columns in enumerate(results):
        n = len(columns["fen4"])
        table = pa.table({"seq": list(range(seq, seq + n)), **columns}, schema=POSITION_SCHEMA)
        pq.write_table(table, parts_dir / f"part-{index:04d}.parquet", compression="zstd")
        seq += n
    return seq
```

<Src file="src/rukh/data/positions.py" tag="p1" lines="120-136" />

`write_parts` borra los trozos viejos antes de empezar, para que una ejecución corta después de una
larga no herede los sobrantes.

La decisión central es escribir en trozos y deduplicar después. Deduplicar sobre la marcha pediría un
diccionario con veintitrés millones de FEN en el proceso padre, varios gigas en un solo hilo; dejar
que DuckDB agrupe desde disco no gasta memoria y usa todos los núcleos.

```python title="src/rukh/data/positions.py"
def dedupe(
    parts_dir: Path, out: Path, max_positions: int, duckdb_cfg: DuckDbConfig | None = None
) -> int:
    """Group the parts by ``fen4`` (first occurrence wins, ``n_seen`` counted) with DuckDB."""
    glob = (parts_dir / "part-*.parquet").as_posix()
    con = db_connect(duckdb_cfg)
    try:
        con.execute(
            f"""
            COPY (
              SELECT fen4,
                     arg_min(game_id, seq) AS game_id,
                     arg_min(ply, seq) AS ply,
                     arg_min(last_move, seq) AS last_move,
                     arg_min(result, seq) AS result,
                     arg_min(phase, seq) AS phase,
                     count(*) AS n_seen
              FROM read_parquet('{glob}')
              GROUP BY fen4
              ORDER BY min(seq)
              LIMIT {int(max_positions)}
            ) TO '{out.as_posix()}' (FORMAT PARQUET, COMPRESSION ZSTD)
            """
        )
        row = con.execute(f"SELECT count(*) FROM read_parquet('{out.as_posix()}')").fetchone()
    finally:
        con.close()
    return int(row[0]) if row else 0
```

<Src file="src/rukh/data/positions.py" tag="p1" lines="139-166" />

`arg_min(game_id, seq)` es "el `game_id` de la fila con el `seq` más pequeño del grupo": la primera
aparición gana. La posición tras `1.e4` la vieron cien mil partidas, y se guardan los datos de la
primera; lo que importa es el FEN, y `n_seen` dice cuántas eran. El `ORDER BY min(seq)` antes del
`LIMIT` hace determinista el tope: sin él, dos ejecuciones darían dos conjuntos distintos.

```python title="src/rukh/data/positions.py"
def month_parquet(uci_dir: Path, month: str) -> Path:
    year, mm = month.split("-")
    return uci_dir / f"year={year}" / f"month={mm}" / "games.parquet"


def run(cfg: PositionsConfig) -> Manifest:
    """Walk up to ``n_games`` of ``month`` and write ``out_dir/positions.parquet`` + manifest."""
    games = month_parquet(resolve(cfg.uci_dir), cfg.month)
    out_dir = resolve(cfg.out_dir)

    n_distinct = dedupe(parts_dir, out, cfg.max_positions, cfg.duckdb)
    manifest = Manifest(

        months=[cfg.month],
        filters={
            "n_games": cfg.n_games,
            "max_positions": cfg.max_positions,
            "phase": {
                "opening_max_ply": OPENING_MAX_PLY,
                "middlegame_min_pieces": MIDDLEGAME_MIN_PIECES,
            },
        },
        counts={"positions": n_positions, "distinct": n_distinct},
        files=[FileHash(path=POSITIONS_FILE, sha256=sha256_file(out), bytes=out.stat().st_size)],
    )
    (out_dir / "manifest.json").write_text(manifest.model_dump_json(indent=2) + "\n", "utf-8")
    return manifest
```

## `scoring.py`: una sola convención para ordenar líneas

Las evaluaciones de Lichess vienen en formato <Term id="multi-pv">multi-PV</Term>: varias filas por
posición, una por línea analizada, y hay que decidir cuál es la mejor. Esa decisión la toman dos
consumidores, la consolidación de `evals.py` en SQL y los pares de la lección siguiente en Python, y
tienen que tomarla igual.

```python title="src/rukh/data/scoring.py"
"""One scoring convention for every multi-PV consumer (consolidation and DPO pairs).

``cp`` and ``mate`` in ``Lichess/chess-position-evaluations`` are from White's point of view.
A mate is worth ``MATE_SCORE - mate`` (so a mate in 1 beats a mate in 5) and a line is judged
from the side to move, which negates the score for Black.

Lines are ranked best first by: a mate *for the side to move*, then depth, then the score for
the side to move, then the move string as a tie-break. ``evals`` consolidates with the SQL
expressions below and ``pairs`` ranks with ``line_rank_key``; both orderings must stay
identical, which is why they live in one module.
"""

from __future__ import annotations

MATE_SCORE = 10_000
BEST_LINE_DOC = "deepest; mate for the mover first; then best cp for the side to move"

# SQL counterparts used by ``rukh.data.evals`` (``sign`` is ``mover_sign`` of the FEN turn).
SCORE_WHITE_SQL = f"""
CASE WHEN mate IS NOT NULL
     THEN CASE WHEN mate > 0 THEN {MATE_SCORE} - mate ELSE -{MATE_SCORE} - mate END
     ELSE cp END
"""
RANK_ORDER_SQL = (
    "(mate IS NOT NULL AND sign * mate > 0) DESC, depth DESC, sign * score_white DESC, move"
)
```

<Src file="src/rukh/data/scoring.py" tag="p1" lines="1-26" />

Dos convenciones. `cp` y `mate` vienen siempre desde el punto de vista de las blancas: un
`cp: -300` es ventaja de tres peones para las negras, mueva quien mueva. Y un mate en `n` vale
`MATE_SCORE - mate`, así que un mate en 1 (9 999) supera a uno en 5 (9 995) y ambos a cualquier
ventaja material. Es 10 000 y no infinito para que la columna siga siendo entera.

Lo raro del módulo es que las cadenas de SQL viven junto a sus equivalentes en Python. Con el `CASE`
en `evals.py` y el `sorted` en `pairs.py`, la misma regla quedaría en dos lenguajes y dos ficheros,
sin nada que avise cuando una cambie.

```python title="src/rukh/data/scoring.py"
def mover_sign(turn: str) -> int:
    """``+1`` when White is to move, ``-1`` for Black."""
    return 1 if turn == "w" else -1


def score_white(cp: int | None, mate: int | None) -> int | None:
    """Centipawns from White's point of view; a mate in ``n`` is ``+/-(10000 - n)``."""
    if mate is not None:
        return MATE_SCORE - mate if mate > 0 else -MATE_SCORE - mate
    return None if cp is None else int(cp)


def score_mover(cp: int | None, mate: int | None, turn: str) -> int | None:
    """``score_white`` seen from the side to move: unchanged for White, negated for Black."""
    white = score_white(cp, mate)
    return None if white is None else mover_sign(turn) * white


def line_rank_key(
    cp: int | None, mate: int | None, depth: int | None, move: str, turn: str
) -> tuple[bool, int, int, str]:
    """Sort key (ascending) reproducing ``RANK_ORDER_SQL``: the best line sorts first."""
    sign = mover_sign(turn)
    white = score_white(cp, mate)
    if white is None:
        raise ValueError("a line without cp and without mate cannot be ranked")
    mates_for_mover = mate is not None and sign * mate > 0
    # DuckDB orders NULL depths last, so an unknown depth ranks below any known one.
    return (not mates_for_mover, -(depth if depth is not None else -1), -sign * white, move)
```

<Src file="src/rukh/data/scoring.py" tag="p1" lines="29-57" />

`line_rank_key` reproduce `RANK_ORDER_SQL` término a término:

1. Mate a favor del que mueve, primero (`sign * mate > 0`). En Python va como `not mates_for_mover`
   porque el orden es ascendente y `False < True`.
2. Profundidad, de mayor a menor: una línea a profundidad 40 es más fiable que una a 12 aunque
   prometa menos. El `-1` imita a DuckDB, que pone los `NULL` al final.
3. La puntuación desde el que mueve, de mayor a menor.
4. La cadena de la jugada, como desempate.

El cuarto término da un orden total. Sin él, dos líneas empatadas quedan como el motor quiera, y dos
ejecuciones pueden elegir distinta "mejor línea" sin que nadie se entere.

  Lo ideal es una sola implementación. Cuando una mitad corre en el motor de datos y la otra en la
  aplicación, lo realista es ponerlas en el mismo fichero, una debajo de otra, con un test que las

## `evals.py`: el join viaja a los datos

```python title="src/rukh/data/evals.py"

Each remote file ``data_00NN.parquet`` is semi-joined with the local positions by ``fen`` and
```

```python title="src/rukh/data/evals.py"
def parse_files(spec: str, n_files: int) -> list[int]:
    """``"0-19"``, ``"3"`` or ``"0,2,5-7"`` into a sorted list of file indices."""
    indices: set[int] = set()
    for part in spec.split(","):
        part = part.strip()
        if not part:
            continue
        if "-" in part:
            lo, hi = part.split("-", 1)
            indices.update(range(int(lo), int(hi) + 1))
        else:
            indices.add(int(part))
    bad = [i for i in indices if i < 0 or i >= n_files]
    if bad:
        raise ValueError(f"file index out of range 0-{n_files - 1}: {bad}")
    return sorted(indices)


def _source(cfg: EvalsConfig, index: int) -> str:
    """Remote parquet for file ``index`` (tests monkeypatch this to a local file)."""
    return cfg.remote_pattern.format(dataset=cfg.dataset, index=index)


def part_path(out_dir: Path, index: int) -> Path:
    return out_dir / f"part-{index:02d}.parquet"
```

```python title="src/rukh/data/evals.py"
def fetch_part(cfg: EvalsConfig, index: int, positions: Path, out_dir: Path) -> tuple[Path, bool]:
    """Semi-join one remote file with the positions; ``(path, fetched)`` (False = existed)."""
    target = part_path(out_dir, index)
    if target.is_file():
        return target, False
    tmp = target.with_suffix(".parquet.tmp")
    con = connect(cfg.duckdb)
    try:
        con.execute(
            f"""
            COPY (
              SELECT e.fen, e.line, e.depth, e.knodes, e.cp, e.mate
              FROM read_parquet('{_source(cfg, index)}') e
              SEMI JOIN read_parquet('{positions.as_posix()}') p ON e.fen = p.fen4
            ) TO '{tmp.as_posix()}' (FORMAT PARQUET, COMPRESSION ZSTD)
            """
        )
    finally:
        con.close()
    tmp.replace(target)
    return target, True
```

<Src file="src/rukh/data/evals.py" tag="p1" lines="66-86" />

Esta consulta es la lección. Un **`SEMI JOIN`** devuelve las filas de la izquierda que tienen alguna
coincidencia a la derecha, sin traer columnas de la derecha ni duplicar filas: "de este fichero
remoto, dame las evaluaciones cuyo FEN tenemos".

Lo barato es lo que el motor hace con eso. Un parquet está partido en grupos de filas, y cada grupo
guarda el mínimo y el máximo de cada columna. DuckDB lee primero solo la columna `fen`, descarta los
grupos que no pueden contener ninguna coincidencia (el <Term id="predicate-pushdown">predicado empujado al origen</Term>) y solo entonces baja las filas que quedan. Es como
buscar en un archivo de cajas etiquetadas "de la A a la F": no abres las que no pueden tener lo que
buscas.

Dos líneas lo hacen resumible. Una parte ya escrita no se vuelve a pedir, y cada parte se escribe a
un `.tmp` que se renombra al terminar. El renombrado es atómico, así que el nombre definitivo solo
existe si la parte está completa: un Ctrl-C a mitad de la parte 7 no deja un parquet truncado que la
siguiente ejecución dé por hecho.

```python title="src/rukh/data/evals.py"
def consolidate(
    out_dir: Path, positions: Path, duckdb_cfg: DuckDbConfig | None = None
) -> dict[str, int]:
    """Best line per FEN plus ``pvs``, joined back with the positions' metadata."""
    parts = (out_dir / "part-*.parquet").as_posix()
    target = out_dir / EVAL_FILE
    con = connect(duckdb_cfg)
    try:
        con.execute(
            f"""
            CREATE TEMP TABLE lines AS
            SELECT fen,
                   split_part(line, ' ', 1) AS move,
                   depth, knodes, cp, mate,
                   CASE WHEN split_part(fen, ' ', 2) = 'w' THEN 1 ELSE -1 END AS sign,
                   {SCORE_WHITE_SQL} AS score_white
            FROM read_parquet('{parts}')
            WHERE line IS NOT NULL AND line <> ''
            """
        )
        con.execute(
            f"""
            CREATE TEMP TABLE ranked AS
            SELECT *, sign * score_white AS score_mover,
                   row_number() OVER (PARTITION BY fen ORDER BY {RANK_ORDER_SQL}) AS rk
            FROM lines
            """
        )
        con.execute(
            f"""
            COPY (
              SELECT p.fen4 AS fen, p.game_id, p.ply, p.last_move, p.result, p.phase, p.n_seen,
                     b.move AS best_move, b.cp, b.mate, b.depth, b.knodes,
                     pv.pvs
              FROM read_parquet('{positions.as_posix()}') p
              JOIN ranked b ON b.fen = p.fen4 AND b.rk = 1
              JOIN (
                SELECT fen,
                       list(struct_pack(move := move, cp := cp, mate := mate, depth := depth)
                            ORDER BY rk) AS pvs
                FROM ranked GROUP BY fen
              ) pv ON pv.fen = p.fen4
              ORDER BY p.game_id, p.ply
            ) TO '{target.as_posix()}' (FORMAT PARQUET, COMPRESSION ZSTD)
            """
        )
        total = con.execute(
            f"SELECT count(*) FROM read_parquet('{positions.as_posix()}')"
        ).fetchone()
        covered = con.execute(
            f"SELECT count(*) FROM read_parquet('{target.as_posix()}')"
        ).fetchone()
        n_lines = con.execute("SELECT count(*) FROM lines").fetchone()
    finally:
        con.close()
    return {
        "positions": int(total[0]) if total else 0,
        "evaluated": int(covered[0]) if covered else 0,
        "lines": int(n_lines[0]) if n_lines else 0,
    }
```

<Src file="src/rukh/data/evals.py" tag="p1" lines="89-148" />

La consolidación son tres sentencias. La primera crea `lines`: una fila por línea analizada, con su
primera jugada, el bando que mueve leído del propio FEN y la puntuación de `scoring.py`. La segunda
numera las líneas de cada FEN en el orden de `scoring.py`, así que `rk = 1` es la mejor.

La tercera escribe el fichero: despliega la mejor línea en columnas (`best_move`, `cp`, `mate`...) y
agrupa todas las líneas en una columna `pvs`, de mejor a peor. Esa columna ya está descargada, no
cuesta casi nada y contiene un dataset entero de preferencias. El `JOIN` con nuestras posiciones
añade `game_id`, `ply`, `phase` y demás, que M3 y la lección siguiente necesitan.

Los conteos dan la `coverage` del manifiesto, la fracción de nuestras posiciones con evaluación. Es
el número que hay que mirar tras la primera ejecución, y el que baja si el `fen4` no casa.

```python title="src/rukh/data/evals.py"
def run(cfg: EvalsConfig, files: str | None = None) -> Manifest:
    """Fetch the requested parts (skipping existing ones), consolidate and write the manifest."""
    positions = resolve(cfg.positions)
    out_dir = resolve(cfg.out_dir)
    out_dir.mkdir(parents=True, exist_ok=True)
    indices = parse_files(files or f"0-{cfg.n_files - 1}", cfg.n_files)
    fetched: list[int] = []
    for index in indices:
        _, was_fetched = fetch_part(cfg, index, positions, out_dir)
        if was_fetched:
            fetched.append(index)
    counts = consolidate(out_dir, positions, cfg.duckdb)
    present = sorted(int(p.stem.split("-")[1]) for p in out_dir.glob("part-*.parquet"))
    target = out_dir / EVAL_FILE
    manifest = Manifest(
        dataset=cfg.dataset,
        months=[],
        filters={
            "positions": Path(cfg.positions).as_posix(),
            "files_present": present,
            "files_fetched_now": fetched,
            "n_files": cfg.n_files,
            "coverage": round(counts["evaluated"] / counts["positions"], 4)
            if counts["positions"]
            else 0.0,
            "best_line": BEST_LINE_DOC,
            "mate_score": MATE_SCORE,
        },
        counts=counts,
        files=[FileHash(path=EVAL_FILE, sha256=sha256_file(target), bytes=target.stat().st_size)],
    )
    (out_dir / "manifest.json").write_text(manifest.model_dump_json(indent=2) + "\n", "utf-8")
    return manifest
```

Has convertido un corpus de partidas en un catálogo de posiciones con una clave que casa con la de
