## Qué vas a construir

Dos conjuntos de datos que el curso usa mucho y que casi no cuestan nada, porque alguien ya hizo el
trabajo caro.

El primero es el **banco de puzles**: seis millones de posiciones tácticas de Lichess, filtradas por
calidad, repartidas en tres tramos de dificultad y partidas en entrenamiento y test con una clave
determinista. Su conjunto de test sostiene la tabla única de M2 a M6, así que no puede cambiar por el
camino.

El segundo son los <Term id="par-de-preferencia">pares de preferencia</Term> para el <Term id="dpo">DPO</Term> de M5: decenas de miles de tríos "posición, jugada buena, jugada mala" que
salen de la columna `pvs` de la lección anterior sin ejecutar Stockfish. Lo único delicado es el
signo. Son dos ficheros.

<Callout kind="guia" title="Qué tecleas y qué traes">

- **Tecleas**: `src/rukh/data/puzzles.py` y `pairs.py`, y los tests `test_puzzles.py` y
  `test_pairs.py` (este, plegado).
- **Traes del repo**: nada.
- **Referencia**: `p1`.

</Callout>

Los tramos viven en una constante y no en la configuración porque definen el banco de test: si se

```python title="src/rukh/data/puzzles.py"
class PuzzlesConfig(BaseConfig):
    """Remote dataset, quality filters and split sizes."""

    dataset: str = "Lichess/chess-puzzles"
    remote_glob: str = "hf://datasets/{dataset}/**/*.parquet"
    out_dir: str = "data/puzzles"
    max_rating_deviation: int = Field(default=100, ge=0)
    min_plays: int = Field(default=100, ge=0)
    n_test: int = Field(default=2_000, ge=1)
    n_train: int = Field(default=50_000, ge=1)
    seed: int = 42
    duckdb: DuckDbConfig = Field(default_factory=DuckDbConfig)


def band(rating: int) -> str | None:
    """Difficulty band for ``rating``; ``None`` below 1000."""
    for name, lo, hi in BANDS:
        if rating >= lo and (hi is None or rating < hi):
            return name
    return None
```

<Src file="src/rukh/data/puzzles.py" tag="p1" lines="24-43" />

Los filtros de calidad no son obvios. `RatingDeviation` es la incertidumbre de Lichess sobre la
dificultad del puzle: con desviación 300, la dificultad declarada es poco más que una suposición.
`NbPlays >= 100` pide cien intentos para que la tasa de acierto signifique algo. Juntos tiran buena
parte del catálogo, a cambio de que el tramo "2000+" tenga puzles que de verdad son de 2000+.
Cualquier conjunto etiquetado por personas o por votos tiene la misma pregunta pendiente: cuántas
opiniones hacen falta para fiarse de la etiqueta.

```python title="src/rukh/data/puzzles.py"
def _source(cfg: PuzzlesConfig) -> str:
    """Remote parquet glob (tests monkeypatch this to a local file)."""
    return cfg.remote_glob.format(dataset=cfg.dataset)


def load_filtered(cfg: PuzzlesConfig) -> pl.DataFrame:
    """Read the puzzles that pass the quality filters with DuckDB (predicate pushdown)."""
    con = connect(cfg.duckdb)
    try:
        table = con.execute(
            f"""
            SELECT PuzzleId AS puzzle_id, FEN AS fen, Moves AS moves, Rating AS rating,
                   Themes AS themes
            FROM read_parquet('{_source(cfg)}')
            WHERE RatingDeviation <= {cfg.max_rating_deviation}
              AND NbPlays >= {cfg.min_plays}
              AND Rating >= 1000
            """
        ).arrow()
    finally:
        con.close()
    return pl.from_arrow(table)  # type: ignore[return-value]
```

<Src file="src/rukh/data/puzzles.py" tag="p1" lines="46-67" />

Otra vez el <Term id="predicate-pushdown">predicado empujado al origen</Term>: cinco columnas de
once y el filtro en el `WHERE`. El `SELECT … AS` pasa a `snake_case` en el mismo sitio donde se lee,
así que nadie más tiene que acordarse de que Lichess escribe `PuzzleId`.

```python title="src/rukh/data/puzzles.py"
def split_key(puzzle_id: str, seed: int) -> int:
    """Stable 64-bit order key: ``blake2b(seed:puzzle_id)``."""
    digest = hashlib.blake2b(f"{seed}:{puzzle_id}".encode(), digest_size=8).digest()
    return int.from_bytes(digest, "little", signed=False)


def split_frame(frame: pl.DataFrame, cfg: PuzzlesConfig) -> pl.DataFrame:
    """Assign ``band`` and ``split``: per band, first ``n_test`` by key then up to ``n_train``."""
    keyed = frame.with_columns(
        pl.col("rating").map_elements(band, return_dtype=pl.String).alias("band"),
        pl.col("puzzle_id")
        .map_elements(lambda p: split_key(p, cfg.seed), return_dtype=pl.UInt64)
        .alias("key"),
        pl.col("themes").cast(pl.List(pl.String)),
    ).filter(pl.col("band").is_not_null())
    keyed = keyed.sort(["band", "key"]).with_columns(
        pl.int_range(pl.len()).over("band").alias("rank")
    )
    return (
        keyed.with_columns(
            pl.when(pl.col("rank") < cfg.n_test)
            .then(pl.lit("test"))
            .when(pl.col("rank") < cfg.n_test + cfg.n_train)
            .then(pl.lit("train"))
            .otherwise(None)
            .alias("split")
        )
        .filter(pl.col("split").is_not_null())
        .select("puzzle_id", "fen", "moves", "rating", "themes", "band", "split")
    )
```

<Src file="src/rukh/data/puzzles.py" tag="p1" lines="70-99" />

La partición se hace por una clave y no al azar. `split_key` es `blake2b(f"{seed}:{puzzle_id}")`, y
eso da algo que un `random.shuffle` no da: **es estable cuando el dataset crece**. Si Lichess publica
cien mil puzles nuevos y repites el paso, los que estaban en test siguen en test, porque su clave no
depende de los demás. Con un barajado, cada ejecución reparte de nuevo y el banco de test de M6 no es
el de M2. La semilla va dentro del hash: cambiarla da una partición alternativa entera, y
concatenar texto no desborda como sumar.

<Callout kind="teoria" title="Qué es polars, en SQL">
  **polars** es una librería de tablas en memoria (un _dataframe_), escrita en Rust: la usas como
  usarías un `SELECT` sobre una tabla local. Cada `pl.col(...)` es una expresión, no un valor, y
  `split_frame` se traduce casi palabra por palabra: `with_columns(... .alias("band"))` es `SELECT
  *, … AS band`; `pl.int_range(pl.len()).over("band")` es `ROW_NUMBER() OVER (PARTITION BY band
  ORDER BY key) - 1`, y `pl.when().then().otherwise()` es un `CASE WHEN`. `map_elements` es la
  excepción: llama a una función de Python fila a fila, lento pero inevitable para un hash. La
  versión perezosa, `pl.scan_parquet(...)… .collect()`, no lee nada hasta el `collect()`; antes
  planifica la consulta entera y solo trae las columnas y filas que hacen falta, como el{' '}
  <Term id="predicate-pushdown">predicado empujado</Term> de DuckDB.
</Callout>

Después se ordena por `(band, key)`, se numera dentro de cada tramo y se reparte: los `n_test`
primeros a test, los `n_train` siguientes a entrenamiento y el resto fuera. Salir del mismo orden
garantiza que los dos conjuntos sean disjuntos, y descartar el sobrante deja el tamaño publicado
acotado: 2 000 de test y hasta 50 000 de entrenamiento por tramo.

```python title="src/rukh/data/puzzles.py"
def run(cfg: PuzzlesConfig) -> Manifest:
    """Download, filter, split and write ``out_dir/puzzles.parquet`` plus the manifest."""
    out_dir = resolve(cfg.out_dir)
    out_dir.mkdir(parents=True, exist_ok=True)
    frame = split_frame(load_filtered(cfg), cfg)
    target = out_dir / PUZZLES_FILE
    frame.write_parquet(target.as_posix(), compression="zstd")
    counts = {
        f"{b}/{s}": int(n)
        for b, s, n in frame.group_by("band", "split").len().sort("band", "split").iter_rows()
    }
    manifest = Manifest(
        dataset=cfg.dataset,
        months=[],
        filters={
            "max_rating_deviation": cfg.max_rating_deviation,
            "min_plays": cfg.min_plays,
            "bands": [b for b, _, _ in BANDS],
            "n_test": cfg.n_test,
            "n_train": cfg.n_train,
            "seed": cfg.seed,
            "split_by": "blake2b(seed:PuzzleId)",
        },
        counts=counts,
        files=[
            FileHash(path=PUZZLES_FILE, sha256=sha256_file(target), bytes=target.stat().st_size)
        ],
    )
    (out_dir / "manifest.json").write_text(manifest.model_dump_json(indent=2) + "\n", "utf-8")
    return manifest
```

## `pairs.py`: preferencias gratis

El DPO de M5 necesita tríos: una posición, una respuesta preferida y una rechazada. La columna `pvs`
de la lección anterior ya los tiene: varias líneas por posición, de mejor a peor, con su valor. La
primera jugada de la mejor es la elegida; la de una suficientemente peor, la rechazada.

```python title="src/rukh/data/pairs.py"
"""DPO pairs from the multi-PV evaluations: best first move versus a clearly worse one.

The lines are ranked with ``rukh.data.scoring``, the same ordering and mate convention the
``evals`` consolidation uses, so ``chosen`` is always the consolidated ``best_move``. The
margin is measured from the side to move (for Black a lower ``cp`` is better). Both moves are
checked for legality with python-chess. One pair per FEN, balanced by phase.
"""

from __future__ import annotations

import logging
from pathlib import Path

import polars as pl
import pyarrow.parquet as pq
from pydantic import Field

from rukh.config import BaseConfig
from rukh.data.manifest import FileHash, Manifest
from rukh.data.scoring import (
    BEST_LINE_DOC,
    MATE_SCORE,
    line_rank_key,
    score_mover,
    score_white,
)
from rukh.data.uci import sha256_file
from rukh.paths import resolve

LOGGER = logging.getLogger(__name__)
PAIRS_FILE = "pairs.parquet"
PHASES = ("opening", "middlegame", "endgame")
BATCH_ROWS = 50_000
```

<Src file="src/rukh/data/pairs.py" tag="p1" lines="36-43" />

`min_delta_cp: 100` es un peón entero. Con un margen menor saldrían más pares y peores: veinte
centipeones a profundidad 20 son ruido del motor, y preferir una línea sobre otra por eso es enseñar
ruido.

```python title="src/rukh/data/pairs.py"
def rank_lines(fen: str, pvs: list[dict[str, object]]) -> list[tuple[str, int, int]]:
    """``(move, score_white, score_mover)`` for every scored line, best line first."""
    turn = fen.split()[1]
    scored: list[tuple[tuple[bool, int, int, str], str, int, int]] = []
    for pv in pvs:
        move = pv.get("move")
        cp, mate, depth = pv.get("cp"), pv.get("mate"), pv.get("depth")
        white = score_white(cp, mate)  # type: ignore[arg-type]
        if not move or white is None:
            continue
        key = line_rank_key(cp, mate, depth, str(move), turn)  # type: ignore[arg-type]
        scored.append((key, str(move), white, score_mover(cp, mate, turn)))  # type: ignore[arg-type]
    scored.sort(key=lambda item: item[0])
    return [(move, white, mover) for _, move, white, mover in scored]
```

<Src file="src/rukh/data/pairs.py" tag="p1" lines="46-59" />

`rank_lines` ordena con `line_rank_key`, la misma regla que la consolidación, así que la elegida es
siempre el `best_move` del paso anterior. Devuelve los dos valores: desde las blancas, para guardar
el `cp` con el convenio de Lichess, y desde el que mueve, para medir el margen.

```python title="src/rukh/data/pairs.py"
def make_pair(
    fen: str, pvs: list[dict[str, object]], min_delta_cp: int
) -> dict[str, object] | None:
    """``chosen``/``rejected`` for one FEN or ``None`` when no line is bad enough or illegal."""
    import chess

    scored = rank_lines(fen, pvs)
    if len(scored) < 2:
        return None
    chosen, cp_chosen, best_mover = scored[0]
    rejected: tuple[str, int, int] | None = None
    for move, white, mover in scored[1:]:
        if move != chosen and best_mover - mover >= min_delta_cp:
            rejected = (move, white, mover)
            break
    if rejected is None:
        return None
    try:
        board = chess.Board(f"{fen} 0 1")
    except ValueError:
        return None
    legal = {m.uci() for m in board.legal_moves}
    if chosen not in legal or rejected[0] not in legal:
        return None
    return {
        "fen": fen,
        "chosen": chosen,
        "rejected": rejected[0],
        "cp_chosen": cp_chosen,
        "cp_rejected": rejected[1],
    }
```

<Src file="src/rukh/data/pairs.py" tag="p1" lines="62-92" />

La primera decisión: el margen se mide desde el que mueve (`best_mover - mover`). Para las blancas
coincide con el convenio de Lichess; para las negras está negado.

<Callout kind="roto" title="El signo que construye un dataset perfectamente al revés">
  Con el margen medido desde las blancas (`cp_chosen - cp_rejected >= 100`), el dataset saldría bien
  en las posiciones de las blancas e **invertido en las de las negras**, porque para ellas un `cp`
  más bajo es mejor.

No da ningún síntoma: mismas filas, jugadas legales, margen medio esperado, y la mitad de los pares
correctos. El DPO aprende tan contento a mejorar con blancas y a empeorar con negras, y tres módulos
después ves un modelo que no mejora sin que nada apunte a este `>=`. Lo atrapa en un minuto mirar
diez pares con turno de negras: `cp_chosen` tiene que ser menor que `cp_rejected`. El mismo tropiezo
espera en cualquier dato de preferencias que mezcle una métrica donde menos es mejor (una latencia,
un error) con otra donde más es mejor.

</Callout>

La segunda: las dos jugadas se verifican legales aunque vengan de un motor, porque cuesta
microsegundos (el `" 0 1"` repone los contadores que python-chess necesita para montar el tablero).

La tercera: un solo par por posición, y la rechazada es la **menos mala** de las que están
suficientemente mal. La peor de todas daría pares demasiado fáciles (distinguir la mejor jugada de
una catástrofe enseña poco), y varios pares por posición la ponderarían sin querer.

```python title="src/rukh/data/pairs.py"
def build_pairs(evals: Path, min_delta_cp: int) -> pl.DataFrame:
    """One pair per FEN, reading the evaluations parquet batch by batch."""
    reader = pq.ParquetFile(evals)
    rows: list[dict[str, object]] = []
    for batch in reader.iter_batches(batch_size=BATCH_ROWS, columns=["fen", "phase", "pvs"]):
        records = zip(
            batch.column("fen").to_pylist(),
            batch.column("phase").to_pylist(),
            batch.column("pvs").to_pylist(),
            strict=True,
        )
        for fen, ph, pvs in records:
            pair = make_pair(fen, pvs, min_delta_cp)
            if pair is not None:
                pair["phase"] = ph
                rows.append(pair)
    schema = {
        "fen": pl.String,
        "chosen": pl.String,
        "rejected": pl.String,
        "cp_chosen": pl.Int32,
        "cp_rejected": pl.Int32,
        "phase": pl.String,
    }
    return pl.DataFrame(rows, schema=schema)
```

El `schema` explícito del final hace falta: si no sale ningún par (una cobertura mala en el join),

```python title="src/rukh/data/pairs.py"
def phase_counts(frame: pl.DataFrame) -> dict[str, int]:
    """Rows per phase, always with the three keys."""
    return {ph: int(frame.filter(pl.col("phase") == ph).height) for ph in PHASES}


def balance(frame: pl.DataFrame, max_per_phase: int, seed: int) -> pl.DataFrame:
    """Same number of pairs per phase: the smallest phase count, capped at ``max_per_phase``."""
    counts = phase_counts(frame)
    n = min(min(counts.values()), max_per_phase)
    if n == 0:
        return frame.clear()
    parts = [
        frame.filter(pl.col("phase") == ph).sample(n=n, seed=seed, shuffle=True) for ph in PHASES
    ]
    return pl.concat(parts)
```

<Src file="src/rukh/data/pairs.py" tag="p1" lines="122-136" />

`phase_counts` devuelve siempre las tres claves, aunque valgan cero, para que nadie tenga que
acordarse de un `.get()`. `balance` iguala las fases al tamaño de la más pequeña, los finales (las
partidas de 1800 a ritmo rápido se deciden antes). Sin equilibrar, el conjunto sería casi todo
aperturas y el modelo alineado con él no habría visto un final. Se muestrea con semilla en vez de
coger las primeras, que serían las de las primeras partidas.

```python title="src/rukh/data/pairs.py"
def run(cfg: PairsConfig) -> Manifest:
    """Build, balance and write ``out_dir/pairs.parquet`` plus the manifest."""
    evals = resolve(cfg.positions_eval)
    out_dir = resolve(cfg.out_dir)
    out_dir.mkdir(parents=True, exist_ok=True)
    raw = build_pairs(evals, cfg.min_delta_cp)
    candidates = phase_counts(raw)
    empty = [ph for ph, n in candidates.items() if n == 0]
    if empty:
        LOGGER.warning(
            "no DPO candidates for %s: the balanced output is empty (candidates %s). "
            "Check the coverage of %s.",
            ", ".join(empty),
            candidates,
            evals,
        )
    balanced = balance(raw, cfg.max_per_phase, cfg.seed)
    target = out_dir / PAIRS_FILE
    balanced.write_parquet(target.as_posix(), compression="zstd")
    counts = phase_counts(balanced)
    counts["candidates"] = int(raw.height)
    manifest = Manifest(
        dataset="Lichess/chess-position-evaluations",
        months=[],
        filters={
            "min_delta_cp": cfg.min_delta_cp,
            "max_per_phase": cfg.max_per_phase,
            "seed": cfg.seed,
            "mate_score": MATE_SCORE,
            "cp_point_of_view": "white",
            "best_line": BEST_LINE_DOC,
            "legality": "python-chess",
            "candidates_by_phase": candidates,
            "empty_phases": empty,
        },
        counts=counts,
        files=[FileHash(path=PAIRS_FILE, sha256=sha256_file(target), bytes=target.stat().st_size)],
    )
    (out_dir / "manifest.json").write_text(manifest.model_dump_json(indent=2) + "\n", "utf-8")
    return manifest
```

<Src file="src/rukh/data/pairs.py" tag="p1" lines="139-178" />

El `LOGGER.warning` es la única traza del pipeline, y está donde hace falta: si una fase se queda a
cero, `balance` devuelve un dataframe vacío y el paso terminaría en verde con un parquet sin filas. El
aviso, y el manifiesto por si se pierde, dicen qué fase faltó. Los `counts` llevan además
`candidates`, el total antes de equilibrar: si es 69 246 y las fases quedan en 4 629, es que los
finales eran 4 629.

<Callout kind="mundo-real" title="El dataset que sale de los residuos de otro">
  La columna `pvs` se guardó porque no costaba nada, y de ella sale un conjunto de preferencias que
  habría costado millones de llamadas a un motor. **Los datos de preferencia más baratos son los que
  ya produjo un sistema que tenía que ordenar algo**: los clics sobre una lista de resultados, la
  propuesta que eligió un revisor, la respuesta que un usuario copió. Antes de montar una campaña de
  anotación, pregunta qué está tirando a la basura el sistema que ya tienes.
</Callout>

Un par está definido por un FEN, que un modelo de secuencias de jugadas no sabe leer. Reconstruir el
prefijo de jugadas que llevó a cada posición se hace en M5, donde se necesita.

def _remote(path: Path) -> None:

def test_score_mover_sign_and_mate() -> None:
    assert score_mover(150, None, "w") == 150
    assert score_mover(150, None, "b") == -150
    assert score_mover(None, 2, "w") == 9_998
    assert score_mover(None, 2, "b") == -9_998
    assert score_mover(None, -1, "b") == 9_999
    assert score_mover(None, None, "w") is None


def test_make_pair_white_and_black_perspective() -> None:
    pair = make_pair(WHITE, [_pv("g1f3", 40), _pv("b1c3", 30), _pv("f2f4", -70)], 100)
    assert pair is not None
    assert (pair["chosen"], pair["rejected"]) == ("g1f3", "f2f4")
    assert (pair["cp_chosen"], pair["cp_rejected"]) == (40, -70)
    # For Black a lower cp is better: -20 beats 90 by 110.
    pair = make_pair(BLACK, [_pv("e7e5", -20), _pv("c7c5", -10), _pv("f7f5", 90)], 100)
    assert pair is not None
    assert (pair["chosen"], pair["rejected"]) == ("e7e5", "f7f5")
    assert (pair["cp_chosen"], pair["cp_rejected"]) == (-20, 90)


def test_make_pair_margin_and_mates() -> None:
    assert make_pair(WHITE, [_pv("g1f3", 40), _pv("b1c3", -50)], 100) is None
    pair = make_pair(WHITE, [_pv("g1f3", None, 2), _pv("b1c3", 300)], 100)
    assert pair is not None and pair["chosen"] == "g1f3" and pair["cp_chosen"] == 9_998
    pair = make_pair(BLACK, [_pv("e7e5", None, -3), _pv("c7c5", -400)], 100)
    assert pair is not None and pair["chosen"] == "e7e5" and pair["cp_chosen"] == -9_997
    assert pair["rejected"] == "c7c5"
    # A mate in 1 outranks a mate in 5, but the margin between them is only 4 centipawns.
    assert make_pair(WHITE, [_pv("g1f3", None, 5), _pv("b1c3", None, 1)], 100) is None
    # Depth outranks the score: the deepest line is chosen, a shallow better one is no pair.
    assert make_pair(WHITE, [_pv("g1f3", 900, depth=12), _pv("b1c3", 40, depth=30)], 100) is None
    pair = make_pair(WHITE, [_pv("g1f3", 40, depth=30), _pv("b1c3", -400, depth=12)], 100)
    assert pair is not None and pair["chosen"] == "g1f3" and pair["rejected"] == "b1c3"
    assert make_pair(WHITE, [_pv("g1f3", 40)], 100) is None

def _evals_parquet(path: Path) -> None:
    board = chess.Board()
    fens, phases, pvs = [], [], []
    moves = "e2e4 e7e5 g1f3 b8c6 f1b5 a7a6 b5a4 g8f6 e1g1 f8e7 f1e1 b7b5 a4b3 d7d6 c2c3 e8g8"
    for ply, move in enumerate(moves.split(), start=1):
        board.push_uci(move)
        legal = [m.uci() for m in list(board.legal_moves)[:3]]
        sign = 1 if board.turn == chess.WHITE else -1
        fens.append(" ".join(board.fen().split()[:4]))
        phases.append("opening" if ply <= 10 else "middlegame" if ply <= 13 else "endgame")
        pvs.append([_pv(legal[0], sign * 60), _pv(legal[1], sign * 20), _pv(legal[2], -sign * 90)])
    pl.DataFrame({"fen": fens, "phase": phases, "pvs": pvs}).write_parquet(path.as_posix())

<Exercise n="01" title="Comprueba el signo de los pares de las negras">
  Con `data/pairs/pairs.parquet` generado, escribe una consulta que se quede con los pares en los que
  le toca mover a las negras y compruebe la relación entre `cp_chosen` y `cp_rejected`. ¿Cuál tiene
  que ser? Después escribe la misma consulta para las blancas. ¿Qué consulta única comprobaría las
  dos a la vez? (Se ejecutan como en la lección anterior: en `consulta.sql`, con
  `uv run python -c "import duckdb, pathlib; print(duckdb.sql(pathlib.Path('consulta.sql').read_text()))"`.)

<Solution>
  El turno está en el segundo campo del FEN: `split_part(fen, ' ', 2) = 'b'`. Para las negras,
  `cp_chosen < cp_rejected` en todos los pares, porque los `cp` están desde el punto de vista de las
  blancas y para las negras menos es mejor. Para las blancas, `cp_chosen > cp_rejected`.

La consulta única usa el signo del que mueve, que es lo que hace `mover_sign`:

```sql
SELECT count(*) AS mal
FROM read_parquet('data/pairs/pairs.parquet')
WHERE (CASE WHEN split_part(fen, ' ', 2) = 'w' THEN 1 ELSE -1 END)
      * (cp_chosen - cp_rejected) < 100
```

Tiene que dar cero: el margen, medido desde el que mueve, es siempre de al menos cien centipeones.
Guárdate la consulta: es la que ejecutarías el día que el DPO de M5 no mejore nada.

</Solution>
