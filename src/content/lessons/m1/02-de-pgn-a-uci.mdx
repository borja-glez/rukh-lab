## Qué vas a construir

El primer paso del pipeline: `rukh data uci`. Entra el <Term id="parquet">parquet</Term> que M0
descargó, con las jugadas escritas como en los libros y llenas de comentarios de reloj, y sale un
parquet por mes con una columna `uci` que un tokenizador puede leer sin saber nada de ajedrez. En
medio hay seis millones de partidas que se reproducen jugada a jugada sobre un tablero de verdad,
tres procesos de trabajo por cada núcleo que te sobre y una conexión de <Term id="duckdb">DuckDB</Term> configurada
para que no te llene el disco del sistema.

Son tres ficheros y 382 líneas: `src/rukh/data/uci.py` (la conversión), `src/rukh/data/parallel.py`
(el reparto entre procesos) y `src/rukh/data/db.py` (la conexión). Están aquí enteros, tal como
están en el repositorio en el tag `p1`, con su enlace a GitHub y las líneas exactas debajo de
cada bloque. Y después los dos ficheros de test que fijan el contrato: uno comprueba que el enroque
y la promoción salen bien, y el otro que el pool no se traga un mes entero en memoria antes de
escribir la primera fila.

## `uci.py`: el fichero que convierte

Empieza por la cabecera, que es donde están los esquemas y las seis expresiones regulares de la
limpieza.

```python title="src/rukh/data/uci.py"
"""SAN movetext to UCI: cleaning, legality check and ply filter, one parquet per month.

Every game is replayed with python-chess; a game with an unparsable or illegal move is
dropped (``illegal``), as are games shorter than ``min_plies`` (``short``) or longer than
``max_plies`` (``long``). Batches of ``BATCH_GAMES`` rows are converted in a ``spawn``
process pool (Windows-safe: every worker entry point is a module-level function).
"""

from __future__ import annotations

import hashlib
import os
import re
from collections.abc import Iterator
from pathlib import Path

import pyarrow as pa
import pyarrow.parquet as pq
from pydantic import Field

from rukh.config import BaseConfig
from rukh.data.manifest import FileHash, Manifest
from rukh.data.parallel import run_batches
from rukh.paths import resolve

BATCH_GAMES = 20_000
RAW_COLUMNS = [
    "Site",
    "movetext",
    "WhiteElo",
    "BlackElo",
    "Result",
    "TimeControl",
    "UTCDate",
    "ECO",
    "month",
]
OUT_SCHEMA = pa.schema(
    [
        ("game_id", pa.int64()),
        ("uci", pa.string()),
        ("n_plies", pa.int16()),
        ("white_elo", pa.int16()),
        ("black_elo", pa.int16()),
        ("result", pa.string()),
        ("time_control", pa.string()),
        ("utc_date", pa.date32()),
        ("eco", pa.string()),
        ("month", pa.string()),
    ]
)
RESULTS = ("1-0", "0-1", "1/2-1/2")

_COMMENT_RE = re.compile(r"\{[^}]*\}")
_VARIATION_RE = re.compile(r"\([^()]*\)")
_NAG_RE = re.compile(r"\$\d+")
_MOVE_NUMBER_RE = re.compile(r"\b\d+\.(\.\.)?")
_RESULT_RE = re.compile(r"(1-0|0-1|1/2-1/2|\*)\s*$")
_ANNOTATION_RE = re.compile(r"[!?]+$")
```

El `OUT_SCHEMA` se declara a mano y no se deja deducir a pyarrow, y eso es una decisión con dos
consecuencias. La primera son los tipos: `n_plies`, `white_elo` y `black_elo` son `int16` porque
ninguno pasa de 32 767, y ahorrar seis bytes por columna en seis millones de filas se nota en un
fichero que se lee entero en cada época. La segunda es que **el orden de las columnas es parte del
contrato**: el paso `tokenize` lee por nombre, pero un test comprueba la lista completa, así que
añadir una columna en medio falla en la CI y no tres módulos después.

`RESULTS` tiene tres valores y no cuatro. Las partidas sin resultado (`*`, abandonadas sin
reclamar) se descartan antes de tocar el tablero: el tokenizador necesita un token de resultado al
final de la secuencia, y no hay ninguno para "no se sabe".

Las regexes merecen una mirada porque cada una corresponde a una parte del `movetext` de Lichess,
que es más sucio de lo que parece:

```text
1. e4 { [%eval 0.3] [%clk 0:05:00] } e5 { [%clk 0:05:00] } 2. Nf3 $1 1... Nc6 1/2-1/2
```

Hay comentarios entre llaves con la evaluación y el reloj, anotaciones numéricas (`$1`), números de
jugada en dos formas (`2.` y `1...`), el resultado al final y, en partidas exportadas de un
análisis, variantes entre paréntesis.

### Limpiar, reproducir, identificar

```python title="src/rukh/data/uci.py"
def clean_movetext(movetext: str) -> str:
    """Strip ``{...}`` comments (``%clk``, ``%eval``), variations, NAGs, move numbers, result."""
    text = _COMMENT_RE.sub(" ", movetext)
    while _VARIATION_RE.search(text):
        text = _VARIATION_RE.sub(" ", text)
    text = _NAG_RE.sub(" ", text)
    text = _RESULT_RE.sub(" ", text.strip())
    text = _MOVE_NUMBER_RE.sub(" ", text)
    return " ".join(text.split())


def san_to_uci(movetext: str) -> tuple[str, int] | None:
    """Replay the cleaned SAN with python-chess; ``None`` when any move is illegal."""
    import chess

    board = chess.Board()
    moves: list[str] = []
    for san in clean_movetext(movetext).split():
        san = _ANNOTATION_RE.sub("", san)
        if not san:
            continue
        try:
            move = board.parse_san(san)
        except ValueError:
            return None
        moves.append(move.uci())
        board.push(move)
    return " ".join(moves), len(moves)


def game_id(site: str) -> int:
    """Signed 64-bit id: the first 8 bytes (little-endian) of ``sha256(Site)``."""
    return int.from_bytes(hashlib.sha256(site.encode("utf-8")).digest()[:8], "little", signed=True)
```

<Src file="src/rukh/data/uci.py" tag="p1" lines="72-104" />

Tres funciones y tres decisiones.

El `while` de `clean_movetext` está porque **los paréntesis anidan**. Una variante dentro de otra
(`(1. e4 e5 (1... c5))`) no la borra una expresión regular no recursiva: `_VARIATION_RE` casa solo
los paréntesis que no contienen otros, así que la primera pasada se lleva los de dentro y la segunda
los de fuera. Con una sola pasada quedaría `(1. e4 e5 )` en el texto y `parse_san` moriría en el
primer paréntesis huérfano.

El orden de las sustituciones tampoco es libre: el resultado se quita **antes** que los números de
jugada, porque `_RESULT_RE` está anclado al final de la cadena (`\s*$`) y si los números
desaparecieran primero, `1/2-1/2` seguiría ahí pero con el `1.` de la primera jugada convertido en
espacio, y el ancla dejaría de casar lo que se espera.

`san_to_uci` reproduce la partida sobre un `chess.Board()` de verdad en vez de traducir cadenas, y
esa es la pieza que hace que la conversión sea correcta. `Nf3` no dice de qué casilla viene el
caballo; solo la posición de ese instante lo sabe. `O-O` se escribe `e1g1` en UCI, que es el
movimiento del rey; `e8=Q+` es `e7e8q`, con la pieza en minúscula y sin el `+`. Nada de eso se puede
hacer con expresiones regulares, y una implementación que lo intente produce ficheros que parecen
bien hasta que el modelo emite jugadas imposibles.

El `_ANNOTATION_RE` se aplica **dentro del bucle**, jugada a jugada, y no en la limpieza general:
`Bb5!?` es una jugada legal con una opinión pegada, no una jugada distinta, y quitar los signos de
toda la cadena de golpe correría el riesgo de tocar algo que no es una anotación.

Y devuelve `None` en vez de lanzar. Es deliberado y tiene un motivo operativo: esto corre dentro de
un pool de procesos, y una excepción por una partida corrupta se llevaría por delante el lote de
veinte mil en el que iba.

`game_id` es el otro detalle que parece contabilidad. El id de una partida son los primeros ocho
bytes de `sha256(Site)` interpretados como entero de 64 bits con signo. Podría ser `hash(site)`, y
sería un error: el `hash()` de Python está sembrado al azar en cada proceso desde 3.3, así que dos
workers del mismo pool darían ids distintos para la misma partida, y dos ejecuciones distintas
darían dos reparticiones distintas. M3 parte entrenamiento y validación por este id, y un reparto
que no se puede reproducir no es un reparto.

<Callout kind="teoria" title="`signed=True` no es un descuido">
  El id puede ser negativo, y está bien: el tipo de la columna es `int64` de Arrow, que es con
  signo, y guardar el mismo número sin signo obligaría a un `uint64` que ni parquet ni polars
  manejan igual de bien. Lo único que se le pide a un id es que sea estable y que no choque; el
  signo no interviene en ninguna de las dos cosas.
</Callout>

### El lote: de filas crudas a columnas

```python title="src/rukh/data/uci.py"
def convert_rows(
    rows: list[dict[str, object]], min_plies: int, max_plies: int
) -> dict[str, object]:
    """Convert one batch of raw rows (dicts with ``RAW_COLUMNS``) into output columns + counts.

    Module-level so ``multiprocessing`` can pickle it under the ``spawn`` start method.
    """
    out: dict[str, list[object]] = {name: [] for name in OUT_SCHEMA.names}
    counts = {"rows": 0, "kept": 0, "illegal": 0, "short": 0, "long": 0}
    for row in rows:
        counts["rows"] += 1
        result = str(row["Result"])
        converted = san_to_uci(str(row["movetext"])) if result in RESULTS else None
        if converted is None:
            counts["illegal"] += 1
            continue
        uci, n_plies = converted
        if n_plies < min_plies:
            counts["short"] += 1
            continue
        if n_plies > max_plies:
            counts["long"] += 1
            continue
        counts["kept"] += 1
        out["game_id"].append(game_id(str(row["Site"])))
        out["uci"].append(uci)
        out["n_plies"].append(n_plies)
        out["white_elo"].append(_parse_elo(row["WhiteElo"]))
        out["black_elo"].append(_parse_elo(row["BlackElo"]))
        out["result"].append(result)
        out["time_control"].append(row["TimeControl"])
        out["utc_date"].append(_parse_date(row["UTCDate"]))
        out["eco"].append(row["ECO"])
        out["month"].append(row["month"])
    return {"columns": out, "counts": counts}
```

Aquí está el filtro que M0 dejó pendiente. En M0 la consulta de DuckDB filtraba por Elo, por ritmo
y por terminación, pero **no** por longitud, y el manifiesto lo anotaba como
`min_plies_deferred`. El motivo es que contar <Term id="ply">plies</Term> exige haber parseado el
`movetext`, y eso no se hace en SQL. Se hace aquí, con la partida ya reproducida.

Los cinco contadores no son telemetría: son el manifiesto. `rows` leídas, `kept` conservadas,
`illegal` descartadas por una jugada imposible, `short` por debajo de `min_plies`, `long` por
encima de `max_plies`. Suman exactamente las leídas, así que cualquier fila que desaparezca tiene
una casilla que lo explica. En la ejecución de referencia, de 6 000 000 de partidas quedaron
5 896 388, con 103 251 cortas, 361 largas y **cero ilegales**, que es el número que había que
mirar: Lichess valida las partidas al guardarlas, así que un solo ilegal habría significado que la
limpieza del `movetext` estaba rompiendo algo.

Fíjate en el orden del `if`: una partida ilegal se cuenta como ilegal aunque además fuera corta. Los
contadores son excluyentes por construcción, con el primer motivo que aparece, y eso es lo que
permite sumarlos.

La función está **a nivel de módulo** a propósito, y el docstring lo dice. Es la restricción que
gobierna todo este fichero y conviene entenderla una vez.

<Callout kind="roto" title="`spawn` no serializa un `lambda`, ni un método, ni una clausura">
  En Linux, `multiprocessing` arranca los procesos con `fork`: el hijo hereda la memoria del padre y
  cualquier función vale como punto de entrada. En Windows y en macOS moderno arranca con `spawn`:
  el hijo es un intérprete nuevo que **reimporta el módulo** y recibe la función por
  `pickle`, es decir, por su nombre completo. Una función definida dentro de otra, un `lambda` o un
  método de una instancia no tienen nombre importable y fallan con
  `AttributeError: Can't pickle local object`.

Por eso `convert_rows` y `convert_batch` están al nivel del módulo y reciben sus parámetros en la
tupla del trabajo en vez de capturarlos. Es la clase de restricción que no se descubre leyendo:
se descubre cuando el código que funcionaba en la CI de Linux no arranca en la máquina de
desarrollo.

</Callout>

```python title="src/rukh/data/uci.py"
def _parse_elo(value: object) -> int | None:
    """A missing or unparsable rating is ``None``; the column stays nullable int16."""
    if value is None:
        return None
    try:
        return int(value)  # type: ignore[call-overload]
    except (TypeError, ValueError):
        return None


def _parse_date(value: object) -> object:
    from datetime import date

    if value is None or isinstance(value, date):
        return value
    text = str(value).replace(".", "-")
    try:
        return date.fromisoformat(text)
    except ValueError:
        return None


def convert_batch(args: tuple[list[dict[str, object]], int, int]) -> dict[str, object]:
    """Worker entry point: ``(rows, min_plies, max_plies)`` into columns and counts."""
    rows, min_plies, max_plies = args
    return convert_rows(rows, min_plies, max_plies)
```

`_parse_elo` devuelve `None` en vez de un cero o un `-1` cuando falta el Elo. La columna es un
`int16` **anulable**, y eso es lo correcto: un cero sería un Elo, y el muestreo por tramos de M4
crearía un tramo `<w0600>` lleno de partidas sin dato. Un `None` se propaga como nulo hasta que
alguien decide qué hacer con él.

`_parse_date` hace el `import` de `datetime` dentro de la función. No es por velocidad —`datetime`
es barato— sino porque es la única parte del fichero que lo necesita y el módulo ya arrastra
pyarrow; es el mismo criterio que la CLI de M0. El `replace(".", "-")` está porque Lichess escribe
`2025.01.01` y `date.fromisoformat` quiere guiones.

`convert_batch` es una línea de desempaquetado y existe solo para tener **un punto de entrada con
nombre** que acepte un único argumento, que es lo que `apply_async` sabe mandar.

### Leer, repartir, escribir

```python title="src/rukh/data/uci.py"
def iter_batches(src: Path) -> Iterator[list[dict[str, object]]]:
    reader = pq.ParquetFile(src)
    columns = [c for c in RAW_COLUMNS if c in reader.schema_arrow.names]
    for batch in reader.iter_batches(batch_size=BATCH_GAMES, columns=columns):
        rows = batch.to_pylist()
        for row in rows:
            for name in RAW_COLUMNS:
                row.setdefault(name, None)
        yield rows


def resolve_workers(workers: int) -> int:
    return workers if workers > 0 else max(1, (os.cpu_count() or 2) - 1)


def convert_month(src: Path, dst: Path, cfg: UciConfig) -> dict[str, int]:
    """Convert ``src`` (raw parquet) into ``dst`` (UCI parquet); returns the counts."""
    dst = Path(dst)
    dst.parent.mkdir(parents=True, exist_ok=True)
    totals = {"rows": 0, "kept": 0, "illegal": 0, "short": 0, "long": 0}
    workers = resolve_workers(cfg.workers)
    jobs = ((rows, cfg.min_plies, cfg.max_plies) for rows in iter_batches(Path(src)))
    with pq.ParquetWriter(dst, OUT_SCHEMA, compression="zstd") as writer:
        write_results(writer, run_batches(convert_batch, jobs, workers), totals)
    return totals
```

`iter_batches` lee el parquet por grupos de 20 000 filas con `iter_batches` de pyarrow, no con un
`read_table`. Un mes son unos 2,9 millones de partidas con su `movetext` completo: leerlo entero son
varios gigas en RAM antes de convertir la primera. Y la intersección `[c for c in RAW_COLUMNS if c
in reader.schema_arrow.names]` con el `row.setdefault(name, None)` de después es lo que hace que el
paso funcione tanto con el parquet que escribió `fetch` (que tiene la columna `month`) como con uno
descargado de Lichess sin ella.

`convert_month` monta el generador de trabajos y se lo da a `run_batches`. Fíjate en que
`jobs` es un **generador**, no una lista: los lotes se construyen a medida que el pool los pide, y
eso es lo que hace falta para que la cadena entera funcione con memoria acotada. Que se cumpla o no
depende del fichero siguiente.

```python title="src/rukh/data/uci.py"
def write_results(
    writer: pq.ParquetWriter, results: Iterator[dict[str, object]], totals: dict[str, int]
) -> None:
    for result in results:
        counts: dict[str, int] = result["counts"]  # type: ignore[assignment]
        for key, value in counts.items():
            totals[key] += value
        columns: dict[str, list[object]] = result["columns"]  # type: ignore[assignment]
        if columns["game_id"]:
            writer.write_table(pa.table(columns, schema=OUT_SCHEMA))


def month_dirs(raw_dir: Path) -> list[tuple[str, Path]]:
    """``(YYYY-MM, games.parquet)`` for every ``year=YYYY/month=MM`` under ``raw_dir``."""
    found: list[tuple[str, Path]] = []
    for path in sorted(Path(raw_dir).glob("year=*/month=*/games.parquet")):
        year = path.parents[1].name.split("=", 1)[1]
        mm = path.parent.name.split("=", 1)[1]
        found.append((f"{year}-{mm}", path))
    return found


def sha256_file(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as fh:
        for chunk in iter(lambda: fh.read(1 << 20), b""):
            digest.update(chunk)
    return digest.hexdigest()
```

`write_results` consume los resultados en orden y escribe cada lote en el `ParquetWriter` abierto.
El `if columns["game_id"]` evita escribir un grupo de filas vacío: un lote donde ninguna partida
pasó los filtros existe, y pyarrow escribiría un grupo de cero filas que después hay que saltar al
leer.

`month_dirs` saca el mes del nombre del directorio (`year=2025/month=01`) y no de una columna.
Es lo mismo que hacía la consulta de M0 con `hive_partitioning = false`: la ruta es el dato, y
partirla a mano es más honesto que dejar que una librería la interprete.

```python title="src/rukh/data/uci.py"
def run(cfg: UciConfig) -> Manifest:
    """Convert every month under ``raw_dir`` and write ``out_dir/manifest.json``."""
    raw_dir = resolve(cfg.raw_dir)
    out_dir = resolve(cfg.out_dir)
    months = month_dirs(raw_dir)
    if not months:
        raise FileNotFoundError(f"no year=*/month=*/games.parquet under {raw_dir}")
    raw_manifest_path = raw_dir / "manifest.json"
    raw_manifest = (
        Manifest.model_validate_json(raw_manifest_path.read_text("utf-8"))
        if raw_manifest_path.is_file()
        else None
    )
    counts: dict[str, int] = {}
    details: dict[str, dict[str, int]] = {}
    files: list[FileHash] = []
    for month, src in months:
        rel = src.relative_to(raw_dir)
        dst = out_dir / rel
        totals = convert_month(src, dst, cfg)
        counts[month] = totals["kept"]
        details[month] = totals
        files.append(
            FileHash(path=rel.as_posix(), sha256=sha256_file(dst), bytes=dst.stat().st_size)
        )
    filters: dict[str, object] = {
        "min_plies": cfg.min_plies,
        "max_plies": cfg.max_plies,
        "legal_only": True,
        "conversion": details,
    }
    if raw_manifest is not None:
        filters["raw"] = raw_manifest.filters
    manifest = Manifest(
        dataset=raw_manifest.dataset if raw_manifest else "Lichess/standard-chess-games",
        months=[m for m, _ in months],
        filters=filters,
        counts=counts,
        files=files,
    )
    out_dir.mkdir(parents=True, exist_ok=True)
    (out_dir / "manifest.json").write_text(manifest.model_dump_json(indent=2) + "\n", "utf-8")
    return manifest
```

<Src file="src/rukh/data/uci.py" tag="p1" lines="229-271" />

El `run` final es fontanería con una idea dentro: **el manifiesto nuevo se cuelga del viejo**. Si
`data/raw/manifest.json` existe, sus filtros entran en el manifiesto de `data/uci/` bajo la clave
`raw`, y el nombre del dataset de origen se hereda en vez de escribirse a mano. Así, el manifiesto
del último paso de la cadena lleva dentro la <Term id="manifiesto">procedencia</Term> completa: de
qué volcado de Lichess salió, con qué filtros se descargó, con qué filtros se convirtió y el sha256
de cada fichero resultante. Es lo que después va, literal, a la <Term id="model-card">dataset card</Term> de Hugging
Face, y es lo que permite decir "este modelo se entrenó con estas partidas exactamente".

`sha256_file` lee en trozos de 1 MiB con `iter(lambda: fh.read(1 << 20), b"")`, el idioma de
Python para "llama a esto hasta que devuelva el centinela". Un `read()` entero de un parquet de
480 MB es memoria que no hace falta gastar.

<Transfer concept="Procedencia encadenada" where="Cualquier cadena de transformaciones cuyo resultado alguien va a usar para decidir: un ETL, un índice vectorial, un conjunto de evaluación.">
  La regla es que **cada paso registra sus filtros y los del paso anterior**. Cuesta una clave en un
  JSON y responde la única pregunta que importa cuando un número no cuadra: qué había dentro.

El modo de fallo que evita es concreto. Sin procedencia encadenada, dentro de tres meses tendrás un
parquet de seis millones de filas y no sabrás si el filtro de Elo era 1800 o 2000, ni si el mes de
validación es el que crees. Y lo descubrirás cuando dos resultados discrepen, que es el momento en
que el coste de averiguarlo se multiplica.

## `parallel.py`: el pool que no se adelanta

Este fichero existe por un fallo concreto, y se entiende mejor sabiendo cuál.

```python title="src/rukh/data/parallel.py"
"""Bounded fan-out over a ``spawn`` process pool.

``multiprocessing.Pool.imap`` drains its input iterable as fast as it can, so feeding it a
generator of 20 000-game batches pulls a whole month into memory before the first result comes
back. ``run_batches`` keeps at most ``2 * workers`` batches in flight: a new job is submitted
only when an older one has been consumed, so the feeder advances at the speed of the writer.
"""

from __future__ import annotations

import multiprocessing
from collections import deque
from collections.abc import Callable, Iterable, Iterator
from typing import Protocol


class AsyncResult[R](Protocol):
    """What ``imap_bounded`` needs from ``Pool.apply_async``."""

    def get(self) -> R: ...


class Pool(Protocol):
    """What ``imap_bounded`` needs from ``multiprocessing.Pool`` (tests use a fake)."""

    def apply_async[R](
        self, func: Callable[..., R], args: tuple[object, ...]
    ) -> AsyncResult[R]: ...
```

<Src file="src/rukh/data/parallel.py" tag="p1" lines="1-28" />

Los dos `Protocol` no son ceremonia de tipos: son lo que permite que el test de más abajo pruebe la
lógica de la cola con un pool falso que ejecuta los trabajos en el sitio, sin lanzar un solo
proceso. `imap_bounded` solo necesita dos métodos del pool de verdad, y declararlos así los deja por
escrito.

```python title="src/rukh/data/parallel.py"
def imap_bounded[J, R](
    pool: Pool,
    func: Callable[[J], R],
    jobs: Iterable[J],
    max_in_flight: int,
) -> Iterator[R]:
    """``pool.imap`` with backpressure: never more than ``max_in_flight`` jobs are queued."""
    if max_in_flight < 1:
        raise ValueError("max_in_flight must be at least 1")
    pending: deque[AsyncResult[R]] = deque()
    for job in jobs:
        pending.append(pool.apply_async(func, (job,)))
        if len(pending) >= max_in_flight:
            yield pending.popleft().get()
    while pending:
        yield pending.popleft().get()
```

<Src file="src/rukh/data/parallel.py" tag="p1" lines="31-46" />

Dieciséis líneas que son la razón de ser del fichero. `Pool.imap` de la biblioteca estándar
**vacía su iterable de entrada tan rápido como puede**: no espera a que haya un worker libre, va
encolando. Con un generador que produce lotes de 20 000 partidas, eso significa que el mes entero se
materializa en memoria antes de que vuelva el primer resultado, y el proceso muere por falta de RAM
mucho antes de escribir una fila.

`imap_bounded` invierte quién manda. Se encola un trabajo, y **en cuanto hay `max_in_flight`
pendientes se espera al más antiguo** con `popleft().get()`. Ese `get()` bloquea, el bucle `for job
in jobs` no avanza mientras bloquea, y el generador de lotes deja de producir. El alimentador va al
ritmo del escritor.

<Callout kind="teoria" title="Contrapresión, y por qué `2 * workers`">
  El nombre general de esto es _backpressure_: el consumidor lento frena al productor rápido en vez
  de acumular trabajo entre los dos. El límite lo pone `run_batches` en `2 * workers`, y el factor
  dos es el compromiso: con `max_in_flight = workers` cada vez que un worker acaba se queda parado
  hasta que el escritor consume su resultado, así que la mitad del tiempo hay núcleos ociosos; con
  un límite grande vuelve el problema de la memoria. Dos lotes por worker —uno calculándose, uno
  esperando— mantiene el pool lleno con un techo de memoria fijo y conocido.
</Callout>

La `deque` y no una lista: `popleft()` de una lista es O(n) porque desplaza todo lo demás. Con
ciento cincuenta lotes en vuelo da igual, pero es el tipo correcto y no cuesta nada.

```python title="src/rukh/data/parallel.py"
def run_batches[J, R](func: Callable[[J], R], jobs: Iterable[J], workers: int) -> Iterator[R]:
    """Map ``func`` over ``jobs``; serially with one worker, else in a bounded spawn pool.

    ``func`` and the jobs must be picklable: every worker entry point is a module-level
    function (Windows starts processes with ``spawn``).
    """
    if workers <= 1:
        yield from map(func, jobs)
        return
    ctx = multiprocessing.get_context("spawn")
    with ctx.Pool(workers) as pool:
        yield from imap_bounded(pool, func, jobs, 2 * workers)
```

<Src file="src/rukh/data/parallel.py" tag="p1" lines="49-60" />

`workers <= 1` no crea pool: hace `map` y devuelve. Eso no es una optimización, es lo que hace los
tests posibles. Un test que lance un pool de `spawn` en Windows paga varios segundos de arranque de
intérprete por caso, y los tests `unit` de este proyecto tienen que tardar segundos en total; con
`workers=1` la ruta serie corre en milisegundos y prueba la conversión. Que la ruta paralela también
funciona lo comprueba un test aparte, uno solo.

`ctx = multiprocessing.get_context("spawn")` fija el método de arranque **explícitamente**, en vez
de heredar el de la plataforma. Así el código se comporta igual en Linux y en Windows, y una función
que no se puede serializar falla en la CI y no en la máquina de desarrollo del único que usa
Windows.

## `db.py`: una conexión configurada, no la de fábrica

```python title="src/rukh/data/db.py"
"""One configured DuckDB connection for the whole pipeline.

Every step joins or groups files far larger than RAM, so a default connection is a foot-gun:
DuckDB spills to the system temp directory (often a small system drive) and, without a memory
limit, competes with the worker processes. ``connect`` sets ``temp_directory`` to
``<data>/duckdb-tmp`` (created on demand, gitignored), ``memory_limit`` and ``threads`` on
every connection.

from pathlib import Path
from typing import TYPE_CHECKING

from pydantic import Field

from rukh import paths
from rukh.config import BaseConfig

if TYPE_CHECKING:
    import duckdb

TMP_DIRNAME = "duckdb-tmp"

    """Settings applied to every DuckDB connection (``duckdb:`` in ``pipeline.yaml``)."""

    memory_limit: str = "32GB"
    threads: int = Field(default=0, ge=0)
    """``0`` = ``cpu_count()``."""
```

Cincuenta y una líneas para lo que parece una línea (`duckdb.connect()`), y el docstring dice por

```python title="src/rukh/data/db.py"
def temp_directory() -> Path:
    """``<data_dir>/duckdb-tmp``, created if missing: spills stay on the data drive."""
    tmp = paths.data_dir() / TMP_DIRNAME
    tmp.mkdir(parents=True, exist_ok=True)
    return tmp


def connect(cfg: DuckDbConfig | None = None) -> duckdb.DuckDBPyConnection:
    """An in-memory DuckDB connection with the spill directory, memory limit and threads set."""
    import duckdb

    settings = cfg or DuckDbConfig()
    con = duckdb.connect()
    con.execute("SET temp_directory = ?", [temp_directory().as_posix()])
    con.execute("SET memory_limit = ?", [settings.memory_limit])
    con.execute("SET threads = ?", [settings.threads or (os.cpu_count() or 4)])
    return con
```

<Src file="src/rukh/data/db.py" tag="p1" lines="35-51" />

`temp_directory` es el importante. Cuando una consulta no cabe en memoria, DuckDB **vuelca a disco**,
y por defecto vuelca al directorio temporal del sistema: en Windows, el `AppData\Local\Temp` del
usuario,
que suele estar en el SSD del sistema y suele ser el disco pequeño. El <Term id="semi-join">semi join</Term> de las
evaluaciones puede volcar decenas de gigas. Apuntando el
volcado a `<data>/duckdb-tmp` —que está en el mismo disco que los datos, y en el `.gitignore`— el
que se llena, si se llena, es el disco donde ya has decidido que caben los datos.

`memory_limit` por defecto en 32 GB de los 64 de la máquina de referencia: la otra mitad es para los
procesos de trabajo del pool de `parallel.py`, que corren a la vez. Sin límite, DuckDB toma como
presupuesto el 80 % de la RAM del sistema y los dos se pelean.

Y los tres ajustes se pasan **con parámetros** (`con.execute("SET memory_limit = ?", [...])`) en vez
de interpolar el valor en la cadena. Aquí el valor viene de un YAML del propio repositorio, así que
no hay un atacante; el motivo es que un `memory_limit` con un espacio de más escrito por
interpolación da un error de sintaxis de SQL en vez de un error sobre el valor.

<Callout kind="mundo-real" title="El ajuste que nadie configura">
  De los tres, el que se olvida siempre es el directorio de volcado, porque el síntoma no menciona
  la base de datos: un `No space left on device` (o un Windows que empieza a avisar de que el disco
  el disco del sistema está lleno) a la hora y media de una consulta, con el disco de datos medio
  vacío. Cualquier motor que procese más de lo que le cabe en RAM tiene un ajuste equivalente
  —`spark.local.dir`, `TMPDIR`, `sort_buffer_size`—, y ponerlo donde están los datos es gratis.
</Callout>

Ese directorio se añade al `.gitignore` en el mismo hito, junto a `.tmp/`, y los dos van **sin barra
inicial** a diferencia de `/data/`: un volcado de DuckDB puede aparecer en cualquier subdirectorio
desde el que se lance una consulta, y un parquet temporal de treinta gigas que se cuela en `git
status` es la clase de susto que se evita con dos líneas.

## El test del pool: cómo se prueba la contrapresión

```python title="tests/unit/test_parallel.py"
"""Tests for rukh.data.parallel: the feeder never runs ahead of the consumer."""

from __future__ import annotations

from collections.abc import Callable, Iterator

import pytest

from rukh.data.parallel import imap_bounded, run_batches
from rukh.data.uci import convert_batch

pytestmark = pytest.mark.unit


class _Immediate:
    def __init__(self, value: object) -> None:
        self.value = value

    def get(self) -> object:
        return self.value


class _FakePool:
    """Runs the job at submission time, so only the queue bound is under test."""

    def __init__(self) -> None:
        self.submitted = 0

    def apply_async(self, func: Callable[..., object], args: tuple[object, ...]) -> _Immediate:
        self.submitted += 1
        return _Immediate(func(*args))


def _counted(n: int, seen: list[int]) -> Iterator[int]:
    for i in range(n):
        seen.append(i)
        yield i


def test_imap_bounded_keeps_the_queue_short() -> None:
    seen: list[int] = []
    pool = _FakePool()
    produced: list[int] = []
    for value in imap_bounded(pool, lambda x: x * 2, _counted(50, seen), max_in_flight=4):
        # The feeder is at most ``max_in_flight`` batches ahead of the consumer.
        assert len(seen) - len(produced) <= 4
        produced.append(value)
    assert produced == [i * 2 for i in range(50)]
    assert pool.submitted == 50
    with pytest.raises(ValueError):
        next(imap_bounded(pool, lambda x: x, [1], 0))
```

<Src file="tests/unit/test_parallel.py" tag="p1" lines="1-51" />

`_FakePool` ejecuta el trabajo en el momento de enviarlo, así que el resultado está listo cuando
`get()` se llama y **lo único que queda bajo prueba es el tamaño de la cola**. El truco está en
`_counted`: el generador apunta en `seen` cada valor que produce, así que comparar `len(seen)` con
`len(produced)` dentro del bucle mide exactamente cuánto se ha adelantado el alimentador. La
aserción `<= 4` es la promesa del fichero, comprobada en cada iteración y no al final.

```python title="tests/unit/test_parallel.py"
def _row(movetext: str) -> dict[str, object]:
    return {
        "Site": "https://lichess.org/x",
        "movetext": movetext,
        "WhiteElo": 1900,
        "BlackElo": 1850,
        "Result": "1-0",
        "TimeControl": "300+0",
        "UTCDate": "2025.01.01",
        "ECO": "C60",
        "month": "2025-01",
    }


def test_run_batches_bounds_a_real_spawn_pool() -> None:
    """With ``workers`` processes the generator stays within ``2 * workers + 1`` batches."""
    workers = 2
    materialised: list[int] = []

    def jobs() -> Iterator[tuple[list[dict[str, object]], int, int]]:
        for index in range(12):
            materialised.append(index)
            yield [_row("1. e4 e5 2. Nf3 Nc6")], 0, 300

    consumed = 0
    for result in run_batches(convert_batch, jobs(), workers):
        consumed += 1
        assert len(materialised) - consumed <= 2 * workers + 1
        assert result["counts"]["kept"] == 1  # type: ignore[index]
    assert consumed == 12


def test_run_batches_is_serial_with_one_worker() -> None:
    assert list(run_batches(lambda x: x + 1, [1, 2, 3], workers=1)) == [2, 3, 4]
```

<Src file="tests/unit/test_parallel.py" tag="p1" lines="54-87" />

Y este lanza el pool de `spawn` de verdad con dos procesos y comprueba la misma propiedad sobre
él, con un margen de uno (`2 * workers + 1`) porque el trabajo que se está enviando cuenta. Es el
único test del fichero que cuesta segundos, y paga: la aserción que importa —que doce lotes no se
materialicen los doce— no se puede comprobar con un pool falso, porque con uno falso el orden es
trivialmente correcto.

## Qué has aprendido

El primer paso del pipeline, entero: qué tiene dentro el `movetext` de Lichess y en qué orden hay que
quitárselo, por qué la conversión a UCI pasa por un tablero de verdad y no por expresiones
regulares, por qué el id de una partida es un hash y no un `hash()`, y qué hay que hacer para que un
pool de procesos no se trague un mes en memoria antes de escribir una fila.

tests/unit/test_parallel.py` pasa los once casos en menos de diez segundos.
