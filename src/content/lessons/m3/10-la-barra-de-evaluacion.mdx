Lección 10 de 11 del módulo «El encoder». Viene de «Exportar el encoder» y sigue en «Los labs».

## Qué vas a construir

La mitad del módulo que vive en el navegador: la barra de evaluación junto al tablero, la alerta de
error, y el **segundo** trabajador que las alimenta mientras el decoder sigue eligiendo su jugada en
el primero.

Todo el código de esta lección es del repositorio `rukh-web`, en el commit `be932c9`, que es la
fotografía de la demo al cerrar este hito. Son unas 650 líneas y traen cuatro problemas que el lado
de Python no tiene: una implementación del tokenizador que **tiene que dar los mismos ids** que la de
Python, un fichero descargado que hay que comprobar antes de creerse, dos modelos compitiendo por la
GPU, y una barra que tiene que ser legible sin ver sus colores.

El registro de M2 gana una lista propia para el encoder, y eso es una decisión: **no es una etapa más
del decoder**. Un `kind: 'encoder'` dentro de `STAGES` habría hecho que el selector del modelo
ofreciera la barra como si fuera un jugador.

El comentario de los tamaños dice que son **provisionales** y de dónde saldrá el número real. La
lección 9 acaba de medirlo: 30,6 MB en fp16 y 18,3 en int8, así que el 15 de aquí es una estimación
optimista que el controlador tiene que corregir. Que el fichero diga que es una estimación y dónde se
corrige es lo que permite darse cuenta.

Y los tamaños **solo alimentan el texto del consentimiento y el respaldo de la barra de progreso**,
nunca la descarga. Es la precaución obvia: un número mal puesto no puede truncar un fichero.

El **encoder de juguete** versionado en `public/test/` es la idea más útil de este bloque, y es
copiable tal cual. Es un modelo de una capa y ocho dimensiones —unos cien kilobytes— con **el contrato
de verdad**: la misma entrada, las mismas dos salidas, el sigmoide dentro del grafo y los mismos
metadatos `rukh_*`. Lo escribe la misma función que escribe el fichero publicado.

Con eso, la suite de extremo a extremo recorre el camino real —el trabajador, la creación de la
sesión, la comprobación del contrato, la inferencia— sin descargar treinta megabytes. La alternativa
habitual es un doble que finge la respuesta, y un doble no comprueba nada del contrato.

## El tokenizador, dos veces

```ts title="src/lib/chess-lm/squares.ts"
// The `squares` input scheme of the encoder: a FEN as 69 fixed token ids. TypeScript twin of
// `rukh/src/rukh/models/squares.py` — the ids have to be the *same* ids, so the layout, the
// vocabulary order and every edge case are mirrored rather than re-invented:
//
//   0        <cls>            pooling anchor
//   1..64    the 64 squares   piece or <empty>, file-major (a1, a2, ..., a8, b1, ..., h8)
//   65       side to move     turn:w / turn:b
//   66       castling rights  one token with the 16 KQkq combinations
//   67       en passant       ep:none or the file (ep:a ... ep:h)
//   68       halfmove clock   clock:0 ... clock:3, the bucketed 50-move counter
//
// `fixtures/squares.json` is generated from the Python module itself and `tests/squares.test.ts`
// replays every case: if this file and Python ever disagree, the encoder would be fed a position
// it was not trained on and the evaluation bar would be quietly wrong.

/** The pieces, in the order the Python vocabulary lists them. */
export const PIECES = 'PNBRQKpnbrqk';

/** Castling rights in the order a FEN field is normalised to. */
export const CASTLING_ORDER = 'KQkq';

export const FILES = 'abcdefgh';

const N_SQUARES = 64;

/** Length of every `squares` sequence: 1 + 64 + 4. No padding is ever needed. */
export const SQUARE_TOKENS = 69;

/** Upper edges (exclusive) of the halfmove-clock buckets. */
export const CLOCK_EDGES = [6, 25, 50] as const;
```

Aquí está el problema estructural de la demo, y es el mismo que tuvo M1 con el tokenizador de jugadas:
**el modelo se entrena en Python y se ejecuta en el navegador**, así que la conversión de posición a
enteros existe dos veces. Si las dos implementaciones divergen en un solo id, al encoder se le está
dando una posición que no es la que ve el tablero, y la barra se equivoca **en silencio**: no hay
excepción, no hay forma mal, solo un número plausible sobre otra posición.

La defensa no es leer los dos ficheros con cuidado. Es un **fixture generado desde el módulo de
Python** (`fixtures/squares.json`) y un test que lo reproduce. Es la única técnica que escala: mientras
el fixture se regenere, la divergencia es un test rojo y no un bug de producción.

```ts title="src/lib/chess-lm/squares.ts"
/** The 16 castling combinations in a fixed order: `-`, `K`, `Q`, `KQ`, `k`, ... */
export function castlingStrings(): string[] {
  const out: string[] = [];
  for (let mask = 0; mask < 16; mask += 1) {
    let rights = '';
    for (let bit = 0; bit < CASTLING_ORDER.length; bit += 1) {
      if ((mask >> bit) & 1) rights += CASTLING_ORDER[bit];
    }
    out.push(rights || '-');
  }
  return out;
}

/** The token list in id order; see the module header for the layout it serves. */
export function buildSquareVocab(): string[] {
  return [
    '<pad>',
    '<mask>',
    '<cls>',
    '<empty>',
    ...PIECES,
    'turn:w',
    'turn:b',
    ...castlingStrings().map((rights) => `castle:${rights}`),
    'ep:none',
    ...FILES.split('').map((file) => `ep:${file}`),
    ...Array.from({ length: CLOCK_EDGES.length + 1 }, (_, index) => `clock:${index}`),
  ];
}

export const SQUARE_VOCAB: string[] = buildSquareVocab();

export const SQUARE_IDS: ReadonlyMap<string, number> = new Map(
  SQUARE_VOCAB.map((token, index) => [token, index]),
);

export const SQUARE_VOCAB_SIZE = SQUARE_VOCAB.length;

function idOf(token: string): number {
  const id = SQUARE_IDS.get(token);
  if (id === undefined) throw new Error(`unknown square token ${token}`);
  return id;
}

export const PAD_ID = idOf('<pad>');
export const MASK_ID = idOf('<mask>');
export const CLS_ID = idOf('<cls>');
export const EMPTY_ID = idOf('<empty>');
```

El vocabulario **se construye**, igual que en Python, y con la misma estructura línea a línea. Eso es
deliberado: dos implementaciones que se leen en paralelo se pueden comparar a ojo cuando hace falta, y
una que construya la lista de otra manera —ordenando, o con un objeto literal— haría imposible ese
repaso aunque diera el mismo resultado.

`idOf` lanza si el token no existe, y se usa para calcular las cuatro constantes al cargar el módulo.
Es una comprobación que corre **una vez, al importar**: si alguien rompe el vocabulario, la página
falla al arrancar y no en la primera evaluación.

```ts title="src/lib/chess-lm/squares.ts"
/** Index of the halfmove-clock bucket of `halfmove` (see `CLOCK_EDGES`). */
export function clockBucket(halfmove: number): number {
  if (!Number.isInteger(halfmove) || halfmove < 0) {
    throw new Error(`the halfmove clock cannot be negative, got ${halfmove}`);
  }
  return CLOCK_EDGES.reduce((count, edge) => count + (halfmove >= edge ? 1 : 0), 0);
}

/** The 64 square ids, file-major, from the piece-placement field of a FEN. */
function placementIds(placement: string): number[] {
  const ranks = placement.split('/');
  if (ranks.length !== 8) {
    throw new Error(`a FEN placement needs 8 ranks, got ${ranks.length}: ${placement}`);
  }
  const ids = new Array<number>(N_SQUARES).fill(EMPTY_ID);
  for (let row = 0; row < 8; row += 1) {
    const rank = 7 - row; // the placement is written from rank 8 down to rank 1
    let file = 0;
    for (const char of ranks[row]) {
      // Divergence from Python, on malformed input only: `str.isdigit()` there also says yes to
      // '0' and to non-ASCII digits ('٣', '²'), where this says no and reports an unknown piece.
      // Python then raises too ('0' leaves the rank short, `int('²')` throws), so no FEN is
      // accepted on one side and refused on the other — only the message differs.
      if (char >= '1' && char <= '9') {
        file += Number(char);
      } else if (PIECES.includes(char)) {
        if (file >= 8) throw new Error(`rank ${rank + 1} of ${placement} is too long`);
        ids[file * 8 + rank] = idOf(char);
        file += 1;
      } else {
        throw new Error(`unknown piece ${char} in ${placement}`);
      }
    }
    if (file !== 8) {
      throw new Error(`rank ${rank + 1} of ${placement} covers ${file} files, not 8`);
    }
  }
  return ids;
}
```

Ese comentario de cuatro líneas es el mejor ejemplo de documentación honesta de toda la demo.
**Declara una divergencia con Python, delimita exactamente dónde ocurre y demuestra que no importa.**

El detalle: `str.isdigit()` de Python también dice sí al `'0'` y a dígitos no ASCII como `'٣'` o
`'²'`; la comparación `char >= '1' && char <= '9'` de TypeScript no. Así que en un FEN corrupto con
esos caracteres las dos implementaciones toman caminos distintos.

Y la parte que lo convierte en aceptable: **las dos acaban lanzando**. Con `'0'`, Python suma cero
columnas y la fila se queda corta, así que su `file != 8` salta; con `'²'`, el `int()` revienta. Aquí
salta el «unknown piece». Ningún FEN se acepta en un lado y se rechaza en el otro; solo cambia el
mensaje. Documentar **la equivalencia observable** en vez de prometer identidad es lo correcto cuando
dos lenguajes no tienen las mismas primitivas.

Y `ids[file * 8 + rank]` es la misma transposición de la lección 4, con el mismo peligro: escribirla
al revés produce un tablero válido y distinto.

```ts title="src/lib/chess-lm/squares.ts"
/** Token id of a FEN castling field, normalised to the `KQkq` order. */
function castlingId(field: string): number {
  if (field === '-' || field === '') return idOf('castle:-');
  for (const char of field) {
    if (!CASTLING_ORDER.includes(char)) {
      throw new Error(`unsupported castling field ${field} (Chess960 is out of scope)`);
    }
  }
  const rights = [...CASTLING_ORDER].filter((right) => field.includes(right)).join('');
  return idOf(`castle:${rights}`);
}

/**
 * The `SQUARE_TOKENS` ids of a FEN; four fields (`fen4`) or the full six are accepted.
 *
 * Throws on a malformed FEN: the encoder must never be fed a position that was silently
 * repaired into a different one.
 */
export function fenToTokens(fen: string): number[] {
  const fields = fen.trim().split(/\s+/).filter(Boolean);
  if (fields.length < 4) {
    throw new Error(`a FEN needs at least 4 fields, got ${fields.length}: ${fen}`);
  }
  const [placement, turn, castling, ep] = fields;
  if (turn !== 'w' && turn !== 'b') {
    throw new Error(`the side to move must be 'w' or 'b', got ${turn}`);
  }
  // Second divergence from Python, again only where no real FEN goes. `Number()` is not `int()`:
  // the `Number.isInteger` guard below keeps them in step on '1.5' (refused on both sides), but
  // '1e2' and '0x10' are read here as 100 and 16 while `int()` raises on them. A FEN whose
  // halfmove clock is written like that is malformed either way; it buckets instead of throwing.
  const halfmove = fields.length > 4 ? Number(fields[4]) : 0;
  if (!Number.isInteger(halfmove)) {
    throw new Error(`the halfmove clock must be an integer, got ${fields[4]}`);
  }
  let epToken: string;
  if (ep === '-' || ep === '') {
    epToken = 'ep:none';
  } else if (ep.length === 2 && FILES.includes(ep[0]) && (ep[1] === '3' || ep[1] === '6')) {
    epToken = `ep:${ep[0]}`;
  } else {
    throw new Error(`unknown en-passant square ${ep}`);
  }
  return [
    CLS_ID,
    ...placementIds(placement),
    idOf(`turn:${turn}`),
    castlingId(castling),
    idOf(epToken),
    idOf(`clock:${clockBucket(halfmove)}`),
  ];
}
```

La segunda divergencia documentada, y otra vez con su delimitación: `Number('1e2')` da 100 y
`int('1e2')` lanza. La guarda `Number.isInteger` mantiene las dos en paso en el caso que sí puede
aparecer (`'1.5'`, rechazado en las dos), y el caso que solo se comporta distinto es un FEN cuyo reloj
está escrito en notación científica, que no existe.

El `fen.trim().split(/\s+/).filter(Boolean)` es más tolerante que el `fen.split()` de Python con el
espaciado, y eso sí es una diferencia a favor: un FEN con espacios dobles copiado de un sitio se
tokeniza igual en los dos lados porque `split()` de Python sin argumentos también colapsa espacios.

Los dos rangos son la parte que casi nadie escribe: **cada cabeza tiene un rango que su propia
activación puede producir**. El `tanh` no puede salir de `[-1, 1]` y una probabilidad no puede salir
de `[0, 1]`. Un número fuera de ahí no es un modelo malo: es un fichero que no es el que la barra
espera, o una salida leída del sitio equivocado.

```ts title="src/lib/contract.ts"
/**
 * The contract of a freshly created encoder session: its single input and how many tokens that
 * input takes, the two outputs by name, their declared width when ORT gives a fixed one, and the
 * `block` the registry declares for the stage.
 *
 * The input side matters as much as the output side. `inputFeeds` builds one tensor and hands it
 * to `inputNames[0]`, so a graph with two inputs would be fed one and left to guess the other;
 * and `squares` is not a context window that can be cropped but a fixed layout of 69 slots, so a
 * file that declares another length is not the encoder this bar tokenizes for — the registry's
 * number is what we *asked* for, the file says what it *takes*. The exporter writes the length
 * as a fixed axis (`rukh_dynamic_seq=False`), so it is usually there to be read; when it is
 * symbolic the registry's number stands and the worker still checks every sequence it sends.
 */
export function readEncoderContract(session: SessionLike, block: number): EncoderContract {
  if (!Number.isInteger(block) || block < MIN_BLOCK) {
    throw new Error(`El contexto declarado para el encoder (${block}) no es utilizable.`);
  }
  const missing = ENCODER_OUTPUTS.filter((name) => !session.outputNames.includes(name));
  if (missing.length > 0 || session.outputNames.length !== ENCODER_OUTPUTS.length) {
    throw new Error(
      `Este fichero no es el encoder de la barra: se esperaban las salidas ` +
        `${ENCODER_OUTPUTS.join(' y ')} y trae ${session.outputNames.join(', ') || 'ninguna'}. ` +
        `Borra los modelos descargados y vuelve a intentarlo.`,
    );
  }
  for (const name of ENCODER_OUTPUTS) {
    const declared = declaredLastDim(session, name);
    if (declared !== null) assertScalarOutput(declared, name, DECLARED_SOURCE);
  }
  const inputs = session.inputNames;
  if (!inputs || inputs.length !== 1) {
    throw new Error(
      `Este fichero no es el encoder de la barra: se esperaba una única entrada y trae ` +
        `${inputs?.length ?? 0} (${inputs?.join(', ') || 'ninguna'}). Borra los modelos ` +
        `descargados y vuelve a intentarlo.`,
    );
  }
  const tokens = lastFixedDim(session.inputMetadata, inputs[0]);
  if (tokens !== null && tokens !== block) {
    throw new Error(
      `La entrada ${inputs[0]} del encoder toma ${tokens} tokens y la barra le da ${block}: el ` +
        `fichero no es el que espera la barra. Borra los modelos descargados y vuelve a ` +
        `intentarlo.`,
    );
  }
  return { block, outputs: [VALUE_OUTPUT, BLUNDER_OUTPUT] };
}
```

Cuatro comprobaciones sobre un fichero de treinta megabytes que la página acaba de descargar de
internet. La frase que las justifica: **el número del registro es lo que pedimos, el fichero dice lo
que acepta**.

`outputNames.length !== ENCODER_OUTPUTS.length` no solo comprueba que estén las dos, también que **no
haya una tercera**. Un fichero exportado con la cabeza de resultado dentro tendría tres salidas y
funcionaría, pero no sería el fichero que se midió, y la barra estaría leyendo dos de tres salidas de
un grafo distinto.

La comprobación de una **sola entrada** existe porque `inputFeeds` construye un tensor y lo entrega a
`inputNames[0]`. Un grafo con dos entradas recibiría una y dejaría la otra a lo que decidiera
`onnxruntime`, que suele ser un error dentro de la inferencia con un mensaje ilegible.

La comprobación de la longitud es la que distingue este caso del decoder, y lo dice el docstring:
`squares` **no es una ventana de contexto que se pueda recortar** sino una disposición fija de 69
ranuras. Un fichero que declare otra longitud no es el encoder para el que esta página tokeniza.

Y los `null` de `declaredLastDim` y `lastFixedDim` se tratan como «no se sabe» y no como cero: una
dimensión simbólica no se puede comprobar aquí, así que se deja pasar y el trabajador comprueba cada
secuencia que envía. Es la diferencia entre una comprobación que falta y una comprobación que miente.

Los cuatro mensajes acaban con **la acción que resuelve el problema**: «Borra los modelos descargados
y vuelve a intentarlo». El caso más probable de todos es un fichero viejo en la Cache API del
navegador después de una exportación nueva, y decir cómo salir de ahí vale más que decir qué pasó.

```ts title="src/lib/contract.ts"
/** Throws when an encoder output carries more than one number for the position being evaluated. */
export function assertScalarOutput(width: number, name: string, source: string): void {
  if (width === 1) return;
  throw new Error(
    `La salida ${name} del encoder no es un único valor: ${source} da ${width}. No se dibuja la ` +
      `barra con este fichero; borra los modelos descargados y vuelve a intentarlo.`,
  );
}

/** Throws when a head answers outside the range its own activation can produce. */
export function assertInRange(value: number, name: string, [low, high]: readonly [number, number]) {
  if (Number.isFinite(value) && value >= low && value <= high) return;
  throw new Error(
    `La salida ${name} del encoder (${value}) se sale del rango [${low}, ${high}] que su cabeza ` +
      `puede producir: el fichero no es el que espera la barra.`,
  );
```

## El segundo worker, y por qué es un segundo worker

```ts title="src/workers/encoder.worker.ts"

// Cache API and answers `evaluate` with the two numbers the bar draws — the value from White's
// point of view and the probability that the last move threw the game away.
```

«Two workers, two queues, two sessions; the browser schedules them». La razón técnica es concreta:
ONNX Runtime **no puede reentrar en `run`**, y crea sesiones de una en una. Si el encoder y el decoder
compartieran trabajador, cada evaluación esperaría a que el modelo terminara de elegir su jugada y
cada jugada esperaría a la evaluación. En una demo donde el jugador mueve, el modelo contesta y la
barra se actualiza, eso son dos esperas encadenadas por cada jugada.

Con dos trabajadores hay dos colas independientes y el navegador las planifica. Cuesta un poco más de
memoria —dos entornos de ORT— y quita una clase entera de bloqueos.

El orden de estas líneas es todo el cuidado del fichero. La sesión y el contrato se ponen a `null`

```ts title="src/workers/encoder.worker.ts"
/** The single number one head answered for this position, checked on the way out. */
function scalar(output: ort.InferenceSession.OnnxValueMapType, name: string): number {
  const tensor = output[name];
  if (!tensor) throw new Error(`el encoder no ha devuelto la salida ${name}`);
  const raw = tensor.data;
  if (!(raw instanceof Float32Array)) {
    throw new Error(`la salida ${name} del encoder no es float32 (${tensor.type})`);
  }
  // The declared shape is `[batch]` and often symbolic, so the real width is only knowable here.
  assertScalarOutput(raw.length, name, RUN_SOURCE);
  return raw[0];
}

async function evaluate(request: Extract<EncoderRequest, { type: 'evaluate' }>): Promise<void> {
  const answer = await serial(async () => {
    const current = session;
    const live = contract;
    if (!current || !live) throw new Error('el encoder todavía no está cargado');
    if (request.ids.length !== live.block) {
      throw new Error(
        `la posición trae ${request.ids.length} tokens y el encoder espera ${live.block}`,
      );
    }
    const feeds = inputFeeds(current, request.ids);
    const started = performance.now();
    const output = await current.run(feeds);
    const inferMs = performance.now() - started;
    const value = scalar(output, live.outputs[0]);
    const blunder = scalar(output, live.outputs[1]);
    assertInRange(value, live.outputs[0], VALUE_RANGE);
    assertInRange(blunder, live.outputs[1], BLUNDER_RANGE);
    return { value, blunder, inferMs };
  });
```

```tsx title="src/islands/App.tsx"
/**
 * Evaluates a position the board settled on. The worker serialises its own runs, so a burst of
 * moves only queues; what is decided here is *which* answer the bar ends up drawing, and that is
 * not simply the newest one — `supersedes` explains why the player's own move wins over the reply
 * that follows it milliseconds later.
 *
 * A failed `evaluate` is a failed **run**, not a failed session: the bar is emptied (a frozen
 * number about a position nobody is looking at any more is worse than no number) and the reason
 * is shown in the panel, but the session stays `ready`, so the next position simply tries again.
 */
async function evaluatePosition(state: GameState) {
  const source = encoder;
  if (!source || encoderStatus.value !== 'ready') return;
  const asked = generation;
  const fen = state.fen;
  const ply = state.history.length;
  const move = ply > 0 ? state.history[ply - 1] : null;
  // The side that has just moved is the one that is *not* to move now.
  const byHuman = ply > 0 && state.turn !== human.value;
  try {
    const answer = await source.evaluate(fenToTokens(fen));
    if (asked !== generation) return;
    const next: Evaluation = { value: answer.value, blunder: answer.blunder, move, ply, byHuman };
    if (!supersedes(next, evaluation.value)) return;
    encoderError.value = null;
    evaluation.value = next;
  } catch (cause) {
    if (asked !== generation) return;
    encoderError.value = cause instanceof Error ? cause.message : String(cause);
    evaluation.value = null;
  }
}
```

## La regla que decide qué se queda en pantalla

{/* prettier-ignore */}
```tsx title="src/islands/EvalBar.tsx"
import type { Signal } from '@preact/signals';

/** What the encoder answered for the position the bar is drawing. */
export interface Evaluation {
  /** `tanh(cp / 400)` from White's point of view, in [-1, 1]. */
  value: number;
  /** Probability that the move that led here threw the game away (already a probability). */
  blunder: number;
  /** SAN of that move, or null in the starting position. The alert has to be able to name it. */
  move: string | null;
  /** Half-moves played to reach the position; how two evaluations are ordered. */
  ply: number;
  /** True when `move` was the player's own, false when it was the opponent's (or there is none). */
  byHuman: boolean;
}

/**
 * Whether `next` should replace `current` on the bar.
 *
 * The rule is deliberately **not** "the newest answer wins". Playing a move hands the turn to the
 * opponent within milliseconds, so the newest answer is always about the opponent's reply, and a
 * bar that always drew the newest one could structurally only ever accuse the opponent: the
 * player would never be told about their own blunder, which is the one thing a learning demo is
 * for. So an evaluation of a position the player created stays up until the player creates a
 * newer one, and a position the *opponent* created only ever replaces another one of its kind —
 * the opening position, or the opponent's first move when the human plays black.
 *
 * Positions from an older game never arrive here: `App` drops them by generation before asking.
 */
export function supersedes(next: Evaluation, current: Evaluation | null): boolean {
  if (!current) return true;
  if (next.ply < current.ply) return false;
  return next.byHuman || !current.byHuman;
}
```

**Cuatro líneas de código y trece de explicación, y las trece hacen falta.** Este es el razonamiento
de producto más bonito del módulo.

El comportamiento evidente sería «gana la respuesta más nueva». Y sería estructuralmente incapaz de
hacer lo único que la demo pretende: el jugador mueve, el modelo contesta en unos milisegundos, y la
evaluación de la posición del jugador se ve reemplazada de inmediato por la de la posición del
oponente. **La barra solo podría acusar al rival.** Al jugador nunca se le diría que acaba de meter la
pata, que es para lo que existe una demo de aprendizaje.

La regla entonces es: una evaluación de una posición que **creó el jugador** se queda hasta que el
jugador cree otra, y una posición que creó el rival solo reemplaza a otra de su especie —la posición
inicial, o la primera jugada del rival cuando el humano lleva negras—.

El `if (next.ply < current.ply) return false` es la guarda de orden: aunque una respuesta llegue tarde,
no puede retroceder la barra a una posición anterior.

Y la consecuencia de esta regla es la que obliga al contador de generación: la posición en pantalla
normalmente no es la del tablero, así que no se puede detectar lo obsoleto comparando posiciones. Las
dos decisiones están encadenadas.

  La regla operativa: **antes de escribir «gana el último», pregúntate qué eventos llegan siempre
  después de qué otros.** Si hay una clase de evento que estructuralmente pisa a otra, «el último

Aparece igual en un asistente que comenta el texto mientras se escribe —la última pulsación pisa el
comentario de la frase anterior—, en un validador que se dispara en cada cambio de campo, y en
cualquier panel que muestre «el estado actual» de algo que se mueve más rápido de lo que alguien
puede leer.

El `Object.is(rounded, -0)` es el detalle que más gracia tiene y no es una curiosidad: en coma
flotante, `-0.001` redondeado a dos decimales es `-0`, y `(-0).toFixed(2)` da la cadena `"-0.00"`.
Una barra que dice «−0.00» está reclamando una ventaja para un bando que no la tiene. `Object.is` es
la única comparación que distingue `-0` de `0` en JavaScript: `-0 === 0` es `true`.

`advantage` es la función que hace la barra **legible sin ver los colores**. Es la regla 7 de las
islas del curso llevada a la demo: si una interfaz dibuja un signo con un color, el DOM tiene que
decirlo también con palabras. Aquí, además, está separada en una función pura y por tanto tiene test.

```tsx title="src/islands/EvalBar.tsx"
/**
 * The encoder's evaluation bar: vertical beside the board on a desktop, horizontal under the
 * board below 900 px (`src/styles/base.css`; the component draws the same markup either way and
 * the media query decides). Nothing is rendered until the encoder has answered, so the single
 * screen of `docs/05-web-demo.md` is untouched for a player who never turns the bar on.
 *
 * Three rules it follows on purpose:
 *
 *   * the number is printed with its sign and the label says who is ahead, because a bar whose
 *     only cue is which end is filled is unreadable for someone who cannot tell the colours
 *     apart (and for anyone on a screen reader);
 *   * the alert **names the move it refers to**: the blunder head answers about the move that led
 *     to this position, not about the position, and an alert that does not say which move is an
 *     accusation with no defendant. Without a move played there is nothing to name and no alert.
 *     Which move that is follows `supersedes` above: normally the player's own last move;
 *   * the fill is animated with a 140 ms transition, and `prefers-reduced-motion: reduce` turns
 *     every transition off globally in `base.css`.
 *
 * The fill percentage travels in a CSS custom property set as a `style` attribute. The CSP allows
 * style *attributes* (`style-src-attr 'unsafe-inline'`, which cm-chessboard already needs to drag
 * a piece) while `style-src` itself stays hashed, so nothing is relaxed for this bar.
 */
export default function EvalBar({ evaluation }: Props) {
  const current = evaluation.value;
  if (!current) return null;
  const alert = current.blunder > BLUNDER_THRESHOLD && current.move !== null;
  const reading = `${formatValue(current.value)} · ${advantage(current.value)}`;
  const about = current.move ? ` tras ${current.move}` : '';
```

La segunda de las tres reglas es la que hay que llevarse: **la alerta nombra la jugada a la que se
refiere**. La cabeza de errores no dice «esta posición es mala», dice «la jugada que llevó aquí tiró
la partida», y una alerta que no dice cuál es una acusación sin acusado. De ahí el
`current.move !== null` en la condición: sin jugada jugada no hay nada que nombrar y no hay alerta.

El párrafo del CSP es la restricción de seguridad que condiciona cómo se dibuja el relleno. La
política de la demo mantiene `style-src` con hashes —nada de estilos en línea— pero permite
`style-src-attr 'unsafe-inline'`, que cm-chessboard ya necesita para arrastrar una pieza. Así que el
porcentaje viaja en una custom property puesta como **atributo** `style`, y la barra no relaja nada
que no estuviera ya relajado.

Cuarenta y cinco líneas de marcado con **tres** decisiones de accesibilidad y una de pruebas.

**Dos caminos para el mismo número.** El `aria-label` del `role="img"` se lee cuando la barra se
enfoca o se recorre, y **no se vuelve a anunciar** cuando el número cambia; el `<p>` con
`aria-live="polite"` es el que anuncia el cambio. Los dos hacen falta: sin el primero, quien recorra
la página con un lector no sabe qué es ese elemento; sin el segundo, quien lo tenga a la vista no se
entera de que cambió.

**La región viva existe siempre, vacía cuando no hay nada que decir.** El comentario dice el motivo y
es uno de los errores de accesibilidad más comunes: una región `aria-live` **tiene que preexistir al
texto que anuncia**. Una que se crea junto con su contenido se pierde de forma rutinaria, porque el
lector de pantalla no estaba observando ese nodo. De ahí el `<p>` permanente y el
`.evalbar__alert:empty` que colapsa el marco para que una alerta vacía no dibuje nada.

**`data-blunder` y `data-alert` en el DOM.** Son atributos de estado para que la suite de extremo a
extremo pueda comprobar las dos ramas —con alerta y sin alerta— sin depender de qué modelo esté
cargado ni de si la barra está pintada de rojo. Es la regla 6 de las islas del curso, aplicada a la
demo.

Y `data-raw={current.value.toFixed(4)}` guarda el valor con cuatro decimales al lado del que se
muestra con dos. Es lo que permite a un test comprobar el número exacto que el modelo devolvió sin
depender del redondeo de la presentación.

<Exercise n="01" title="Por qué la alerta no se enciende nunca en la demo publicada">
  La barra compara `blunder > 0.5` y la cabeza publicada no pasa de 0,31. Así que nadie va a ver una
  alerta jamás. Enumera tres formas de «arreglarlo» y di cuál es legítima y por qué las otras dos no.

<Solution>
  **Bajar `BLUNDER_THRESHOLD` a 0,0663 en el código de la demo.** Es la tentadora y es la peor: ese
  umbral es el que la mitad `tune` eligió para **un** checkpoint concreto, y cada checkpoint tiene el
  suyo (el de casillas salió en 0,04459). Escribirlo en la demo la ataría a un modelo y dejaría de
  valer en cuanto se publicara otro, sin que nada fallara.

**Calibrar la cabeza** —ajustar una temperatura o una regresión isotónica sobre la mitad `tune`— para
que sus probabilidades signifiquen lo que dicen, y dejar el 0,5. Es lo correcto y es trabajo de otro
hito: una cabeza calibrada es una cabeza cuyo 0,5 se puede interpretar, y entonces la demo no
necesita saber nada del checkpoint.

**Que el umbral viaje en los metadatos del fichero ONNX**, como ya viajan `rukh_kind` y
`rukh_heads`, y que la barra lo lea de ahí. Es legítimo y es la solución barata: el umbral es una
propiedad del modelo exportado, así que su sitio es el modelo. La demo seguiría sin saber nada de
ningún checkpoint en particular.

Lo que no vale, en los tres casos, es tocar el umbral **sin publicar cuál es**. Un detector con un
punto de operación que no se declara es un detector que no se puede reproducir.

</Solution>

## Qué has aprendido

Que el lado del navegador de un modelo tiene cuatro problemas que el lado del entrenamiento no tiene,
y los cuatro con su técnica: una implementación gemela del tokenizador que se defiende con un
**fixture generado** desde la de Python y con divergencias documentadas allí donde no se puede tener
identidad; un fichero descargado que se **comprueba contra un contrato** —nombres, número de salidas,
número de entradas, longitud y rango— antes de dibujar nada; dos modelos que no pueden compartir cola,
así que son dos trabajadores; y una barra que tiene que ser legible sin colores, con dos caminos de
anuncio y una región viva que preexiste a su texto.

Y la regla de producto que más se transfiere: **«gana el último» puede ser estructuralmente incapaz de
mostrar lo que importa**. Aquí lo era, y la consecuencia —que la barra sobreviva a las respuestas del
rival— es lo que obliga a descartar lo obsoleto con un contador de generación en vez de comparando
posiciones.
