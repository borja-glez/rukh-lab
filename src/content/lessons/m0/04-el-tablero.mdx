## Qué vas a construir

La pantalla donde al final del curso jugarás contra tu propio modelo, y que en este hito ya funciona
**sin modelo ninguno**. Tablero, lista de jugadas, deshacer, nueva partida, exportar PGN, y un rival
que hace siempre la primera jugada legal.

Que la demo exista antes que el modelo no es un adorno. Fuerza a tomar ya la decisión de arquitectura
que sostiene todo lo demás: **quién decide si una jugada es legal**.

## La decisión: el modelo propone, el navegador filtra

<Figure
  n="01"
  caption="Quién decide qué en la demo: el modelo produce logits (una puntuación bruta por token antes de convertirla en probabilidades); el navegador los filtra con las reglas y muestrea."
>
  <DemoFlow />
</Figure>

El modelo devolverá un <Term id="logits">logit</Term> por token, una puntuación bruta que se convierte
en una distribución de probabilidad sobre todo su <Term id="vocabulario">vocabulario</Term> (unas
1 900 jugadas UCI posibles). Los logits son las notas que cada jurado apunta antes de convertirlas en
porcentajes: sirven para ordenar, no para leerlas como probabilidad; el softmax de M2 es el paso que
las convierte.

`chess.js` calcula cuáles de esas jugadas son legales en la posición actual, el navegador pone a cero
las demás y muestrea entre las que quedan. Así el modelo **nunca hace una jugada ilegal en la demo**,
aunque la proponga.

Y como la propone, se puede medir. El modo "sin máscara" de la demo (a partir de M2) enseña la jugada
cruda que el modelo quería hacer y la marca si es ilegal; la <Term id="legalidad">tasa de
legalidad</Term> sin máscara es la primera columna de la tabla única precisamente porque mide cuánto
ha aprendido las reglas un modelo al que nadie se las ha programado.

<Callout kind="teoria" title="Enmascarar no es hacer trampa">
  Poner a cero la probabilidad de los tokens que no pueden aparecer es una técnica general de
  decodificación (_constrained decoding_): se usa para forzar JSON válido, gramáticas o llamadas a
  herramientas bien formadas en LLMs de texto. La <Term id="mascara">máscara</Term> no cambia lo que
  el modelo sabe; cambia lo que le dejamos decir. Por eso se mide siempre con y sin ella.
</Callout>

## `game.ts`: el estado de la partida, sin efectos

Todo el ajedrez de la demo vive en un módulo de funciones puras. Ni una clase, ni un objeto mutable,
ni una referencia a `window`.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
import { Chess, type Square } from 'chess.js';

export type Color = 'w' | 'b';
export type Promotion = 'q' | 'r' | 'b' | 'n';

export interface Move {
  from: string;
  to: string;
  promotion?: Promotion;

/**

 * the game began at (the initial position unless the state was built with `fromFen`).
 */
export interface GameState {
  start: string;
  fen: string;
  history: string[];
  turn: Color;
  over: boolean;
  result: string | null;
}

export const INITIAL_FEN = 'rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1';
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="1-25" />

`GameState` guarda **la posición inicial y el historial**, y de ahí deriva todo lo demás. El <Term id="fen">FEN</Term>
actual está en el estado, pero como valor calculado: la fuente de verdad
son `start` y `history`.

Esa elección es la que hace que deshacer sea trivial (quitar jugadas del final de una lista) y que
exportar <Term id="pgn">PGN</Term> sea posible (el PGN es el historial, no la posición). Si el estado
fuera solo el FEN, deshacer necesitaría una pila de posiciones y el PGN no se podría reconstruir.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
function fromHistory(start: string, history: string[]): Chess {
  const chess = new Chess(start);
  for (const san of history) chess.move(san);
  return chess;
}

function fromState(state: GameState): Chess {
  return fromHistory(state.start, state.history);
}

function resultOf(chess: Chess): string | null {
  if (chess.isCheckmate()) return chess.turn() === 'w' ? '0-1' : '1-0';
  if (chess.isDraw()) return '1/2-1/2';
  return null;
}

function snapshot(chess: Chess, start: string): GameState {
  return {
    start,
    fen: chess.fen(),
    history: chess.history(),
    turn: chess.turn(),
    over: chess.isGameOver(),
    result: resultOf(chess),
  };
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="27-52" />

El patrón de todo el fichero está en estas dos funciones privadas: **cada operación reconstruye un
`Chess` desde el historial, lo modifica y devuelve una instantánea nueva**. El objeto mutable de
`chess.js` nunca sale del módulo ni se guarda entre llamadas.

Reconstruir la partida desde cero en cada llamada parece derrochador y no lo es: son decenas de
jugadas y `chess.js` las aplica en microsegundos. Lo que compra es que no haya estado compartido, y
con eso desaparece la clase de bug más molesta de una interfaz de ajedrez: el tablero y la lógica
discrepando sobre de quién es el turno.

`resultOf` merece leerse con cuidado, porque es fácil de invertir: si hay jaque mate, **gana el que
NO tiene el turno**. `chess.turn() === 'w'` significa que las blancas están mateadas, y el resultado
es `0-1`.

```ts title="src/lib/game.ts"
/** Destination squares of every legal move from `from` (deduplicated across promotions). */
export function legalTargets(state: GameState, from: string): string[] {
  const chess = fromState(state);
  const moves = chess.moves({ square: from as Square, verbose: true });
  return [...new Set(moves.map((move) => move.to))];
}

/** True when moving `from` to `to` is a legal pawn move that reaches the last rank. */
export function needsPromotion(state: GameState, from: string, to: string): boolean {
  const chess = fromState(state);
  const moves = chess.moves({ square: from as Square, verbose: true });
  return moves.some((move) => move.to === to && move.promotion !== undefined);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="64-76" />

`legalTargets` es la función que dibuja los puntos en el tablero cuando coges una pieza, y el `Set` es
necesario: un peón en la séptima fila tiene **cuatro** jugadas legales a la misma casilla (dama,
torre, alfil, caballo), y sin deduplicar se pintarían cuatro marcadores encima del mismo cuadrado.

`needsPromotion` existe porque la promoción no se puede adivinar desde la jugada: hay que preguntar a
las reglas si esa jugada concreta ofrece elección de pieza, y solo entonces abrir el diálogo.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
/** Applies a move and returns the new state, or `null` when the move is illegal. */
export function applyMove(state: GameState, move: Move): GameState | null {
  const chess = fromState(state);
  try {
    chess.move({ from: move.from, to: move.to, promotion: move.promotion });
  } catch {
    return null;
  }
  return snapshot(chess, state.start);
}

/** True when the human has at least one ply of their own in `history` that undo can remove. */
export function canUndo(state: GameState, human: Color): boolean {
  return state.history.length >= (human === 'b' ? 2 : 1);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="78-92" />

**`applyMove` es donde se decide la legalidad de la demo.** `chess.js` lanza si la jugada no es legal;
la función lo convierte en `null`. Quien llama decide qué hacer con eso, y en M2 es lo que rechazará
una jugada ilegal propuesta por el modelo.

Un `try/catch` que devuelve `null` en vez de propagar es una decisión: aquí una jugada ilegal **no es
un error del programa**, es un caso previsto. Cuando el rival sea un modelo entrenado, será el caso
más frecuente de todos.

`canUndo` tiene el `2` frente al `1` porque jugando con negras la partida empieza con una jugada del
rival: deshacer cuando solo hay esa jugada dejaría el tablero en la posición inicial con las negras a
la espera, que no es "deshacer mi jugada", es "empezar otra partida".

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
/**
 * Undoes moves until it is the human's turn again with at least one human move removed:
 * two plies when it is already the human's turn, one when the opponent is to move.
 * Returns `state` unchanged when the human has not moved yet (as black, the opponent's
 * opening ply stays on the board).
 */
export function undoPair(state: GameState, human: Color): GameState {
  if (!canUndo(state, human)) return state;
  const plies = state.turn === human ? 2 : 1;
  const history = state.history.slice(0, Math.max(0, state.history.length - plies));
  return snapshot(fromHistory(state.start, history), state.start);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="94-105" />

Deshacer quita **una o dos** medias jugadas según de quién sea el turno, y esa es la diferencia entre
un deshacer que funciona y uno que deja el turno al revés. Si es tu turno, la última jugada fue del
rival y hay que quitar las dos (la suya y la tuya). Si es el turno del rival —porque acabas de mover y
todavía no ha contestado— basta quitar una.

Todo el fichero en cinco líneas de lógica, porque el estado es una lista.

```ts title="src/lib/game.ts"
  Site: 'https://rukh.borjaglez.com',

function today(): string {
  const now = new Date();
  const pad = (value: number) => String(value).padStart(2, '0');
  return `${now.getFullYear()}.${pad(now.getMonth() + 1)}.${pad(now.getDate())}`;
}

/** PGN export with the demo headers merged with `headers` (caller wins). */
export function toPgn(state: GameState, headers: Record<string, string>): string {
  const chess = fromState(state);
  const merged: Record<string, string> = {
    ...DEFAULT_HEADERS,
    Date: today(),
    ...headers,
    Result: headers.Result ?? state.result ?? '*',
  };
  for (const [key, value] of Object.entries(merged)) chess.setHeader(key, value);
  return chess.pgn();
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="107-129" />

El PGN es la forma de sacar una partida de la demo y meterla en cualquier otro sitio (Lichess, un
analizador, `python-chess`). Las cabeceras se mezclan en un orden que importa: los valores por
defecto primero, la fecha, lo que pase quien llama —que gana— y el resultado al final con su cadena
de reservas (`headers.Result ?? state.result ?? '*'`). El `*` es lo que el estándar PGN pone cuando
la partida no ha terminado.

`today()` formatea con puntos (`2026.09.18`), que es el formato del estándar, y no con guiones.

## El rival de mentira

```ts title="src/lib/opponent.ts"
import { Chess } from 'chess.js';
import type { Move } from './game';

export interface Opponent {
  id: string;
  label: string;
  pick(fen: string): Promise<Move>;
}

/** Mock opponent: the first legal move in chess.js `moves({ verbose: true })` order. */
export const firstLegalMove: Opponent = {
  id: 'mock',
  label: 'Primera jugada legal',
  async pick(fen) {
    const chess = new Chess(fen);
    const [move] = chess.moves({ verbose: true });
    if (!move) throw new Error('No legal moves in this position');
    return {
      from: move.from,
      to: move.to,
      promotion: move.promotion as Move['promotion'],
    };
  },
};
```

<Src file="src/lib/opponent.ts" repo="rukh-web" tag="2ee69fd" lines="1-24" />

Veinticuatro líneas, y la mitad son la interfaz. Eso es lo que interesa: `Opponent` tiene un método,
`pick(fen)`, y devuelve una promesa. Es la misma interfaz que en M2 implementará el jugador ONNX con
el modelo cargado en un worker, y en M4 el adaptador de estilo.

Que sea `async` desde el primer día, cuando el rival de mentira responde en microsegundos, no es
sobreingeniería: es lo que evita reescribir toda la interfaz cuando el rival tarde 40 ms y haya que
enseñar un "pensando". El coste hoy es una palabra.

`Primera jugada legal` como rival sirve para probar todo lo demás —tablero, lista, deshacer,
exportar— sin depender de un modelo que todavía no existe. Y es el rival que usa la CI.

El registro de etapas con una sola entrada. `StageKind = 'mock'` es una unión de un solo miembro, que
en M2 pasa a ser `'mock' | 'onnx'`: cuando eso ocurra, TypeScript señalará **todos** los sitios donde
falta tratar el caso nuevo. Una unión de un miembro es más útil que un `string`.

`sizeMb: 0` existe ya porque la demo va a tener que avisar de cuánto pesa lo que va a descargar, y el
campo con valor cero es más honesto que un campo que aparece en M2 y obliga a revisar el código que
lo consume.

```ts title="src/lib/query.ts"
import type { Color } from './game';
import { findStage, STAGES } from './registry';

export interface Query {
  mock: boolean;
  stage: string;
  color: Color;
}

/**
 * Parses the page query string. `mock` is forced by `?mock=1` and is also true when the
 * requested stage is unknown or is itself a mock; in P0 every stage is a mock, so `mock`
 * is always true. `?color=b` makes the human play black.
 */
export function parseQuery(search: string): Query {
  const params = new URLSearchParams(search.startsWith('?') ? search.slice(1) : search);
  const requested = params.get('stage') ?? STAGES[0].id;
  const stage = findStage(requested);
  const mock = params.get('mock') === '1' || stage === undefined || stage.kind === 'mock';
  return {
    mock,
    stage: stage?.id ?? STAGES[0].id,
    color: params.get('color') === 'b' ? 'b' : 'w',
  };
}
```

Los parámetros de la URL son la forma en que el curso enlaza a la demo con una configuración concreta

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="1-30" />

Las señales están **a nivel de módulo**, no dentro del componente. Es deliberado: hay una sola partida
por página, y las tres zonas (tablero, panel, lista) leen la misma. Con estado dentro del componente
habría que pasarlo por props o montar un contexto, y el tablero —que envuelve una librería imperativa—
necesita suscribirse a los cambios sin re-renderizar.

Dos banderas de ocupado y no una, y la diferencia importa: `thinking` es el rival calculando,
`turning` es el tablero animando un cambio de orientación. `busy` es la unión, porque la interfaz
tiene que bloquearse en los dos casos, pero las dos causas se distinguen en pantalla y en los tests.

{/* prettier-ignore */}
```tsx title="src/islands/App.tsx"
function opponentFor(): Opponent {
  // P0: every stage is the mock opponent.
  return firstLegalMove;
}

function opponentToMove(state: GameState): boolean {
  return !state.over && state.turn !== human.value;
}

async function settle() {
  const current = game.value;
  if (!opponentToMove(current) || thinking.value) return;
  thinking.value = true;
  try {
    const move = await opponentFor().pick(current.fen);
    // The position may have been reset (new game, colour change, undo) while the opponent
    // was thinking: drop the stale reply; the `finally` below re-schedules if needed.
    if (game.value.fen !== current.fen) return;
    const next = applyMove(current, move);
    if (next) game.value = next;
  } finally {
    thinking.value = false;
    // Re-run only when a newer position still waits for the opponent (no loop otherwise).
    if (game.value.fen !== current.fen && opponentToMove(game.value)) void settle();
  }
}
```

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="32-57" />

`settle()` es la función con más cuidado del fichero, y todo el cuidado va a un solo problema: **la
respuesta que llega tarde**.

El rival tarda. Mientras tarda, el usuario puede darle a "nueva partida", cambiar de color o deshacer.
Cuando la promesa se resuelve, la jugada que devuelve corresponde a una posición que ya no está en
pantalla, y aplicarla produce el bug más desconcertante de una interfaz de ajedrez: una pieza que se
mueve sola en una partida distinta.

La solución son tres líneas. Se guarda el FEN de partida (`current`), y al volver del `await` se
compara: si cambió, la respuesta se tira. Y en el `finally`, si la posición **nueva** todavía espera al
rival, se vuelve a llamar. Esa condición doble (`fen` distinto **y** le toca al rival) es lo que
impide que la llamada recursiva se convierta en un bucle.

Con el rival de mentira esto nunca se dispara, porque contesta antes de que puedas pulsar nada. En M2,
con un modelo en un worker, se dispara constantemente.

{/* prettier-ignore */}
```tsx title="src/islands/App.tsx"
function playHuman(move: Move): boolean {
  const current = game.value;
  if (busy.value || current.over || current.turn !== human.value) return false;
  const next = applyMove(current, move);
  if (!next) return false;
  game.value = next;
  void settle();
  return true;
}

function startNewGame() {
  game.value = newGame();
  void settle();
}

function chooseColor(color: Color) {
  if (color === human.value || busy.value) return;
  human.value = color;
  startNewGame();
}

function undo() {
  if (busy.value || !canUndo(game.value, human.value)) return;
  game.value = undoPair(game.value, human.value);
  // As black, undo leaves the opponent to move: let it reply.
  void settle();
}

function stageLabel(): string {
  return STAGES.find((entry) => entry.id === stage.value)?.label ?? STAGES[0].label;
}

function exportPgn(): string {
  const white = human.value === 'w' ? HUMAN_LABEL : stageLabel();
  const black = human.value === 'b' ? HUMAN_LABEL : stageLabel();
  return toPgn(game.value, { White: white, Black: black });
}
```

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="59-95" />

Las cinco acciones de la interfaz, y las cinco empiezan comprobando `busy`. No es repetición
descuidada: es el único sitio donde se puede comprobar, porque son los cinco puntos de entrada desde
la interacción del usuario.

`playHuman` devuelve `boolean` porque es el `onMove` que recibe el tablero, y el tablero necesita saber
si la jugada se aceptó para deshacer la animación si no.

Las tres acciones que cambian la posición terminan en `void settle()`. `startNewGame` también, aunque
parezca innecesario: si el humano juega con negras, la partida nueva empieza con el rival moviendo.

El `void` delante de la llamada asíncrona no es decorativo: le dice a TypeScript (y a quien lea) que
la promesa se ignora a propósito. Es lo que la regla `no-floating-promises` de ESLint exige, y la
regla existe porque una promesa ignorada por descuido se come los errores.

**Aquí es donde la legalidad llega a la pantalla.** `moveInputStarted` se dispara al coger una pieza:
si la partida terminó o no es tu turno, se devuelve `false` y la pieza no se levanta. Si es tu turno,
se piden las casillas legales a `legalTargets` y se pintan como puntos. Una pieza sin jugadas legales
tampoco se levanta.

`validateMoveInput` se dispara al soltar: devolver `false` hace que cm-chessboard devuelva la pieza a
su casilla. Es literalmente la misma decisión que en M2 filtrará las jugadas del modelo, tomada en el
mismo sitio.

La promoción es el caso feo, y merece verlo: hay que abrir un diálogo, que es **asíncrono**, mientras
la librería espera una respuesta **sincrónica**. Se devuelve `true` (acepta la jugada) y el diálogo
corrige después: si el usuario elige pieza y `onMove` la acepta, el estado cambia y el efecto de
posición redibuja; si cancela o la jugada se rechaza, se fuerza `setPosition` al FEN actual, que
devuelve el peón a su sitio.

librería sin tipos propios completos: es "el primer parámetro del primer parámetro de
`enableMoveInput`", es decir, el tipo del evento, extraído de la firma en vez de duplicado a mano.

El `effect` de signals es lo que sustituye al re-render: cada vez que cambia `game.value.fen`, se
llama a `setPosition`. Con eso quedan cubiertas de una vez la respuesta del rival, el deshacer, la
partida nueva y los efectos colaterales de tu propia jugada (la torre del enroque, el peón capturado
al paso, la pieza de promoción), que el tablero no mueve por su cuenta.

El `queueMicrotask` es un detalle con una razón muy concreta: cuando tú mueves, cm-chessboard mueve la
pieza **él mismo** justo después del callback de validación. Si `setPosition` se llamara de inmediato,
lo haría antes de ese movimiento y animaría la jugada dos veces. Diferido un microtask, la librería ya
ha movido y `setPosition` solo anima la diferencia que queda.

`data-busy` en el elemento padre es la señal que esperan los tests de extremo a extremo. Sin ella, un
test que pulsa dos jugadas seguidas pierde la segunda, porque cm-chessboard ignora la entrada mientras
anima. Poner en el DOM un estado que solo existía en la cabeza de la librería es lo que convierte un
test intermitente en uno determinista.

Dos problemas de concurrencia contra la misma librería, y las dos soluciones merecen conocerse porque
aparecen cada vez que se envuelve algo imperativo.

**El primero**: cm-chessboard rechaza un `setOrientation` mientras otro está en la cola. Si el usuario
pulsa "negras" y "blancas" rápido, el segundo se pierde y el tablero queda del revés. La solución es
una **cadena de promesas** (`turn = turn.then(...)`) que serializa las peticiones, y una comprobación
al final: si el color deseado cambió mientras girábamos, se vuelve a llamar. `turning.value` es la
bandera que bloquea la interfaz mientras eso pasa, y de ahí viene el segundo booleano de `busy`.

**El segundo**: el efecto que activa la entrada lee `game.value.over`, y un efecto de signals se
re-ejecuta cuando cambia **cualquier** señal que lea. Leer `game.value.over` directamente lo haría
re-ejecutarse en cada jugada, y cada re-ejecución llama a `disableMoveInput`/`enableMoveInput` en
medio de una animación. `computed(() => game.value.over)` crea una señal derivada que **solo notifica
cuando el booleano cambia**, y con eso el efecto se ejecuta dos veces por partida en vez de sesenta.

Ese uso de `computed` como filtro de igualdad es el modismo que hay que recordar de este fichero.

## Qué has aprendido

La demo funciona antes de que exista el modelo, y por el camino se ha tomado la decisión que más
consecuencias tiene en el resto del curso: **el modelo propone y el navegador filtra**. La legalidad
la decide `chess.js` en el cliente, el modelo solo ordena candidatos, y las dos cosas se miden por
separado.

También has visto tres patrones que se repiten cada vez que se envuelve algo imperativo en algo
reactivo: la respuesta que llega tarde y hay que tirar, la cola de promesas que serializa las órdenes
a la librería, y el `computed` que evita que un efecto se re-ejecute sesenta veces por partida.

**Cómo se mide**: `pnpm test` en verde (estado del juego y rival), `pnpm e2e` en verde en los tres
tamaños de pantalla (jugar una partida completa, deshacer, exportar PGN, axe sin violaciones), y la
demo con `?mock=1` permite jugar y ganar en ordenador y en móvil.
