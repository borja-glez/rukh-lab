## La decisión: el modelo propone, el navegador filtra

<Figure
  n="01"
  caption="Quién decide qué en la demo: el modelo produce logits (una puntuación bruta por token antes de convertirla en probabilidades); el navegador los filtra con las reglas y muestrea."
>
  <DemoFlow />
</Figure>

El modelo devolverá un <Term id="logits">logit</Term> por token: una puntuación bruta para cada
jugada de su <Term id="vocabulario">vocabulario</Term> (unas 1 900 jugadas UCI posibles). `chess.js`
calcula cuáles son legales en la posición actual, el navegador pone a cero las demás y muestrea entre
las que quedan. Así el modelo nunca hace una jugada ilegal en la demo, aunque la proponga.

Y como la propone, se puede medir. El modo «sin máscara» (a partir de M2) enseña la jugada cruda que
el modelo quería hacer y la marca si es ilegal; esa <Term id="legalidad">tasa de legalidad</Term> es
la primera columna de la tabla única.

<Transfer
  concept="Decodificación restringida"
  where="Forzar JSON válido, una gramática o llamadas a herramientas bien formadas en un LLM de texto."
>
  La <Term id="mascara">máscara</Term> es una técnica general de decodificación (_constrained
  decoding_): poner a cero la probabilidad de los tokens que no pueden aparecer. Es lo que hacen las
  salidas estructuradas de las APIs de LLM, que en cada paso solo permiten los tokens que mantienen
  el JSON válido. La máscara no cambia lo que el modelo sabe, sino lo que le dejas decir: con ella
  mides si el sistema funciona; sin ella, cuánto ha aprendido el modelo.
</Transfer>

## `game.ts`: el estado de la partida, sin efectos

Todo el ajedrez de la demo vive en un módulo de funciones puras, sin clases, sin objetos mutables y
sin `window`.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
import { Chess, type Square } from 'chess.js';

export type Color = 'w' | 'b';
export type Promotion = 'q' | 'r' | 'b' | 'n';

export interface Move {
  from: string;
  to: string;
  promotion?: Promotion;
}

/**
 * Immutable snapshot of a game. `history` is the SAN move list played from `start`, the FEN
 * the game began at (the initial position unless the state was built with `fromFen`).
 */
export interface GameState {
  start: string;
  fen: string;
  history: string[];
  turn: Color;
  over: boolean;
  result: string | null;
}

export const INITIAL_FEN = 'rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1';
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="1-25" />

`GameState` guarda **la posición inicial y el historial**, y de ahí deriva todo lo
demás; el <Term id="fen">FEN</Term> actual es un valor calculado. Así deshacer es quitar jugadas del final de
una lista, y exportar <Term id="pgn">PGN</Term> es posible, porque el PGN es el historial. Con solo
el FEN, deshacer necesitaría una pila de posiciones y el PGN no se podría reconstruir.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
function fromHistory(start: string, history: string[]): Chess {
  const chess = new Chess(start);
  for (const san of history) chess.move(san);
  return chess;
}

function fromState(state: GameState): Chess {
  return fromHistory(state.start, state.history);
}

function resultOf(chess: Chess): string | null {
  if (chess.isCheckmate()) return chess.turn() === 'w' ? '0-1' : '1-0';
  if (chess.isDraw()) return '1/2-1/2';
  return null;
}

function snapshot(chess: Chess, start: string): GameState {
  return {
    start,
    fen: chess.fen(),
    history: chess.history(),
    turn: chess.turn(),
    over: chess.isGameOver(),
    result: resultOf(chess),
  };
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="27-52" />

El patrón de todo el fichero está en estas funciones privadas: cada operación reconstruye un `Chess`
desde el historial, lo modifica y devuelve una instantánea nueva. El objeto mutable de `chess.js`
nunca sale del módulo.

Reconstruir la partida en cada llamada parece un derroche, pero son decenas de jugadas que `chess.js`
aplica en microsegundos. A cambio no hay estado compartido, y desaparece el bug más molesto de una
interfaz de ajedrez: el tablero y la lógica discrepando sobre de quién es el turno.

`resultOf` es fácil de invertir: si hay jaque mate, gana el que no tiene el turno.
`chess.turn() === 'w'` significa que las blancas están mateadas, y el resultado es `0-1`.

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="54-62" />

`fromFen` pasa `chess.fen()` como `start` y no el `fen` recibido: `chess.js` normaliza el FEN
(completa los campos que falten), y guardar la versión normalizada evita que `start` y `fen` difieran

```ts title="src/lib/game.ts"
/** Destination squares of every legal move from `from` (deduplicated across promotions). */
export function legalTargets(state: GameState, from: string): string[] {
  const chess = fromState(state);
  const moves = chess.moves({ square: from as Square, verbose: true });
  return [...new Set(moves.map((move) => move.to))];
}

/** True when moving `from` to `to` is a legal pawn move that reaches the last rank. */
export function needsPromotion(state: GameState, from: string, to: string): boolean {
  const chess = fromState(state);
  const moves = chess.moves({ square: from as Square, verbose: true });
  return moves.some((move) => move.to === to && move.promotion !== undefined);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="64-76" />

`legalTargets` dibuja los puntos del tablero cuando coges una pieza. El `Set` hace falta porque un
peón en séptima tiene cuatro jugadas legales a la misma casilla (una por pieza de promoción).
`needsPromotion` pregunta a las reglas si esa jugada concreta ofrece elección de pieza, y solo
entonces se abre el diálogo.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
/** Applies a move and returns the new state, or `null` when the move is illegal. */
export function applyMove(state: GameState, move: Move): GameState | null {
  const chess = fromState(state);
  try {
    chess.move({ from: move.from, to: move.to, promotion: move.promotion });
  } catch {
    return null;
  }
  return snapshot(chess, state.start);
}

/** True when the human has at least one ply of their own in `history` that undo can remove. */
export function canUndo(state: GameState, human: Color): boolean {
  return state.history.length >= (human === 'b' ? 2 : 1);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="78-92" />

**`applyMove` es donde se decide la legalidad de la demo.** `chess.js` lanza si la jugada no es
legal, y la función lo convierte en `null`: una jugada ilegal no es un error del programa sino un
caso previsto, y en M2 es lo que rechazará las jugadas ilegales del modelo.

`canUndo` pide dos medias jugadas con negras porque la partida empieza con una jugada del rival:
deshacerla sería empezar otra partida.

{/* prettier-ignore */}
```ts title="src/lib/game.ts"
/**
 * Undoes moves until it is the human's turn again with at least one human move removed:
 * two plies when it is already the human's turn, one when the opponent is to move.
 * Returns `state` unchanged when the human has not moved yet (as black, the opponent's
 * opening ply stays on the board).
 */
export function undoPair(state: GameState, human: Color): GameState {
  if (!canUndo(state, human)) return state;
  const plies = state.turn === human ? 2 : 1;
  const history = state.history.slice(0, Math.max(0, state.history.length - plies));
  return snapshot(fromHistory(state.start, history), state.start);
}
```

<Src file="src/lib/game.ts" repo="rukh-web" tag="2ee69fd" lines="94-105" />

Deshacer quita una o dos <Term id="ply">medias jugadas</Term> según de quién sea el turno. Si es tu

```ts title="src/lib/game.ts"
const DEFAULT_HEADERS: Record<string, string> = {
  Event: 'Rukh demo',
  Site: 'https://rukh.borjaglez.com',

function today(): string {
  const now = new Date();
  const pad = (value: number) => String(value).padStart(2, '0');
  return `${now.getFullYear()}.${pad(now.getMonth() + 1)}.${pad(now.getDate())}`;
}

/** PGN export with the demo headers merged with `headers` (caller wins). */
export function toPgn(state: GameState, headers: Record<string, string>): string {
  const chess = fromState(state);
  const merged: Record<string, string> = {
    ...DEFAULT_HEADERS,
    Date: today(),
    ...headers,
    Result: headers.Result ?? state.result ?? '*',
  };
  for (const [key, value] of Object.entries(merged)) chess.setHeader(key, value);
  return chess.pgn();
}
```

El PGN saca una partida de la demo hacia cualquier otro sitio (Lichess, un analizador,

## El rival de mentira

{/* prettier-ignore */}
```ts title="src/lib/opponent.ts"
import { Chess } from 'chess.js';
import type { Move } from './game';

export interface Opponent {
  id: string;
  label: string;
  pick(fen: string): Promise<Move>;
}

/** Mock opponent: the first legal move in chess.js `moves({ verbose: true })` order. */
export const firstLegalMove: Opponent = {
  id: 'mock',
  label: 'Primera jugada legal',
  async pick(fen) {
    const chess = new Chess(fen);
    const [move] = chess.moves({ verbose: true });
    if (!move) throw new Error('No legal moves in this position');
    return {
      from: move.from,
      to: move.to,
      promotion: move.promotion as Move['promotion'],
    };
  },
};
```

<Src file="src/lib/opponent.ts" repo="rukh-web" tag="2ee69fd" lines="1-24" />

Lo que interesa es la interfaz: `Opponent` tiene un método, `pick(fen)`, que devuelve una promesa.
Es la misma que en M2 implementará el jugador ONNX, con el modelo en un worker. Que sea `async` desde
el primer día, cuando el rival responde en microsegundos, evita reescribir la interfaz cuando tarde
40 ms y haya que enseñar un «pensando».

Este rival sirve para probar todo lo demás sin depender de un modelo que todavía no existe, y es el
que usa la CI.

El registro de etapas, con una sola entrada. `StageKind = 'mock'` es una unión de un miembro que en
M2 pasa a ser `'mock' | 'onnx'`; entonces TypeScript señalará todos los sitios donde falta tratar el

avisar de cuánto pesa lo que descarga.

```ts title="src/lib/query.ts"
import type { Color } from './game';
import { findStage, STAGES } from './registry';

export interface Query {
  mock: boolean;
  stage: string;
  color: Color;
}

/**
 * Parses the page query string. `mock` is forced by `?mock=1` and is also true when the
 * requested stage is unknown or is itself a mock; in P0 every stage is a mock, so `mock`
 * is always true. `?color=b` makes the human play black.
 */
export function parseQuery(search: string): Query {
  const params = new URLSearchParams(search.startsWith('?') ? search.slice(1) : search);
  const requested = params.get('stage') ?? STAGES[0].id;
  const stage = findStage(requested);
  const mock = params.get('mock') === '1' || stage === undefined || stage.kind === 'mock';
  return {
    mock,
    stage: stage?.id ?? STAGES[0].id,
    color: params.get('color') === 'b' ? 'b' : 'w',
  };
}
```

<Src file="src/lib/query.ts" repo="rukh-web" tag="2ee69fd" lines="1-25" />

Los parámetros de la URL son la forma en que el curso enlaza a la demo con una configuración
concreta (`?mock=1`, y más adelante `?stage=dpo&elo=1500`). La función nunca falla: una etapa
desconocida cae a la primera de `STAGES` y activa el modo de mentira, así que un enlace con un
parámetro obsoleto sigue funcionando. `mock` es cierto si lo pides, si la etapa no existe o si la
etapa es un mock; por lo último, en M0 siempre lo es.

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="1-30" />

Las señales de Preact son valores observables: quien lee una se entera cuando cambia, sin que el
componente se vuelva a pintar. Aquí están a nivel de módulo porque hay una sola partida por página y
las tres zonas (tablero, panel, lista) leen la misma. El tablero, que envuelve una librería imperativa,
necesita suscribirse a los cambios sin re-renderizar.

`thinking` es el rival calculando y `turning` el tablero girando. La interfaz se bloquea en los dos
casos (`busy`), pero las dos causas se distinguen en pantalla y en los tests.

{/* prettier-ignore */}
```tsx title="src/islands/App.tsx"
function opponentFor(): Opponent {
  // P0: every stage is the mock opponent.
  return firstLegalMove;
}

function opponentToMove(state: GameState): boolean {
  return !state.over && state.turn !== human.value;
}

async function settle() {
  const current = game.value;
  if (!opponentToMove(current) || thinking.value) return;
  thinking.value = true;
  try {
    const move = await opponentFor().pick(current.fen);
    // The position may have been reset (new game, colour change, undo) while the opponent
    // was thinking: drop the stale reply; the `finally` below re-schedules if needed.
    if (game.value.fen !== current.fen) return;
    const next = applyMove(current, move);
    if (next) game.value = next;
  } finally {
    thinking.value = false;
    // Re-run only when a newer position still waits for the opponent (no loop otherwise).
    if (game.value.fen !== current.fen && opponentToMove(game.value)) void settle();
  }
}
```

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="32-57" />

Todo el cuidado de `settle()` va a un solo problema: **la respuesta que llega tarde**. Mientras el
rival piensa, puedes darle a "nueva partida", cambiar de color o deshacer. Cuando la promesa se
resuelve, su jugada corresponde a una posición que ya no está en pantalla, y aplicarla produce una
pieza que se mueve sola en una partida distinta.

La solución es corta. Se guarda el FEN de partida (`current`) y, al volver del `await`, si cambió, la
respuesta se tira. En el `finally`, si la posición nueva todavía espera al rival, se vuelve a llamar;
la condición doble (`fen` distinto y le toca al rival) impide que eso se convierta en un bucle. Con el
rival de mentira nunca se dispara; con un modelo en un worker, constantemente.

{/* prettier-ignore */}
```tsx title="src/islands/App.tsx"
function playHuman(move: Move): boolean {
  const current = game.value;
  if (busy.value || current.over || current.turn !== human.value) return false;
  const next = applyMove(current, move);
  if (!next) return false;
  game.value = next;
  void settle();
  return true;
}

function startNewGame() {
  game.value = newGame();
  void settle();
}

function chooseColor(color: Color) {
  if (color === human.value || busy.value) return;
  human.value = color;
  startNewGame();
}

function undo() {
  if (busy.value || !canUndo(game.value, human.value)) return;
  game.value = undoPair(game.value, human.value);
  // As black, undo leaves the opponent to move: let it reply.
  void settle();
}

function stageLabel(): string {
  return STAGES.find((entry) => entry.id === stage.value)?.label ?? STAGES[0].label;
}

function exportPgn(): string {
  const white = human.value === 'w' ? HUMAN_LABEL : stageLabel();
  const black = human.value === 'b' ? HUMAN_LABEL : stageLabel();
  return toPgn(game.value, { White: white, Black: black });
}
```

<Src file="src/islands/App.tsx" repo="rukh-web" tag="2ee69fd" lines="59-95" />

Las acciones que el usuario puede disparar empiezan comprobando `busy`: son los puntos de entrada, y
es ahí donde hay que comprobarlo. `playHuman` devuelve `boolean` porque el tablero necesita saber si
la jugada se aceptó para devolver la pieza si no.

Las acciones que cambian la posición terminan en `void settle()`, también `startNewGame`: con negras,
la partida nueva empieza con el rival moviendo. El `void` dice que la promesa se ignora a propósito,
como exige la regla `no-floating-promises` de ESLint, porque una promesa ignorada por descuido se come
los errores.

## `Board.tsx`: envolver una librería imperativa

cm-chessboard dibuja el tablero en SVG, es responsive, funciona con ratón y con el dedo, y es
**imperativa**: se le dan órdenes, no se le pasa un estado. Envolverla en un componente reactivo es
el trabajo de este fichero, el más difícil de la demo. Es un intérprete entre dos personas que hablan
distinto: el resto de la demo dice «la partida ahora es esta», y el componente lo traduce a las
órdenes sueltas que la librería entiende («mueve esta pieza», «gira el tablero»), en el orden y al
ritmo que ella acepta.

{/* prettier-ignore */}
```tsx title="src/islands/Board.tsx"
import { computed, effect, type Signal } from '@preact/signals';
import { useEffect, useRef } from 'preact/hooks';
import { legalTargets, needsPromotion, type Color, type GameState, type Move } from '../lib/game';

interface Props {
  game: Signal<GameState>;
  human: Signal<Color>;
  /** Set while the board animates an orientation change. */
  turning: Signal<boolean>;
  /** Applies the human move; returns false when it is rejected. */
  onMove: (move: Move) => boolean;
}
```

Los `import()` son dinámicos porque cm-chessboard toca el DOM al importarse, y un `import` estático

Aquí la legalidad llega a la pantalla. `moveInputStarted` se dispara al coger una pieza: si la
partida terminó, no es tu turno o la pieza no tiene jugadas legales, devuelve `false` y la pieza no
se levanta; si no, pinta como puntos las casillas de `legalTargets`. `validateMoveInput` se dispara
al soltar, y devolver `false` hace que la pieza vuelva a su casilla.

La promoción es el caso feo: el diálogo es asíncrono y la librería espera una respuesta síncrona. Se
devuelve `true` y el diálogo corrige después: si eliges pieza y `onMove` la acepta, el efecto de
posición redibuja; si cancelas o se rechaza, `setPosition` al FEN actual devuelve el peón a su sitio.

parámetro de `enableMoveInput`": el tipo del evento, extraído de la firma en vez de copiado a mano.

El `effect` de signals sustituye al re-render: cada vez que cambia `game.value.fen`, llama a
`setPosition`. Eso cubre de una vez la respuesta del rival, el deshacer, la partida nueva y los
efectos colaterales de tu jugada (la torre del enroque, el peón capturado al paso, la pieza de
promoción).

El `queueMicrotask` existe porque, cuando tú mueves, cm-chessboard mueve la pieza él mismo justo
después del callback de validación. Llamado de inmediato, `setPosition` animaría la jugada dos veces;
diferido, solo anima la diferencia que queda.

`data-busy` es la señal que esperan los tests de extremo a extremo: sin ella, un test que pulsa dos
jugadas seguidas pierde la segunda, porque la librería ignora la entrada mientras anima. Sacar al DOM
un estado interno de la librería convierte un test intermitente en uno determinista.

Aquí hay dos problemas de concurrencia contra la misma librería, y sus soluciones aparecen cada vez
que se envuelve algo imperativo.

cm-chessboard rechaza un `setOrientation` mientras otro está en la cola: si pulsas "negras" y
"blancas" rápido, el segundo se pierde y el tablero queda del revés. Una cadena de promesas
(`turn = turn.then(...)`) serializa las peticiones y, al final, si el color deseado cambió mientras
giraba, vuelve a llamar.

Un efecto de signals se re-ejecuta cuando cambia cualquier señal que lea. Si leyera `game.value.over`
directamente, se re-ejecutaría en cada jugada y cortaría animaciones con `disableMoveInput`.
`computed(() => game.value.over)` crea una señal derivada que **solo notifica cuando el booleano
cambia**: el efecto corre dos veces por partida en vez de sesenta. Ese `computed` como filtro de
igualdad es lo que hay que recordar de este fichero.

## Qué has aprendido

La demo funciona antes de que exista el modelo, y por el camino se ha tomado la decisión que más
consecuencias tiene en el resto del curso: **el modelo propone y el navegador filtra**. La legalidad
la decide `chess.js` en el cliente, el modelo solo ordena candidatos, y las dos cosas se miden por
separado.

También has visto tres patrones de envolver algo imperativo en algo reactivo: tirar la respuesta que
llega tarde, serializar órdenes con una cola de promesas y filtrar un efecto con `computed`. La
respuesta tardía te la volverás a encontrar en cualquier interfaz que hable con un LLM en streaming:
el usuario cambia de conversación y la respuesta anterior sigue llegando.

**Cómo se mide**: `pnpm test` en verde (estado del juego y rival), `pnpm e2e` en verde en los tres
tamaños de pantalla (jugar una partida completa, deshacer, exportar PGN, axe sin violaciones), y la
demo con `?mock=1` permite jugar y ganar en ordenador y en móvil.

Con esto se cierra M0, y el club está montado. El aprendiz todavía no existe, pero ya tiene todo lo
que necesita para aprender y para que se le pueda medir: un local donde cualquiera reproduce el
entorno con un comando, un árbitro calibrado, un cuaderno que apunta cada ejecución con su código y
su configuración, una biblioteca con su ficha de catálogo y un tablero que no admite jugadas
ilegales. El repositorio está en el tag `p0` y la descarga de datos está corriendo.
