## Qué vas a construir

El recorte de datos con el que se entrena todo el curso, y —más importante— la prueba de qué entró
en él. El centro es una consulta SQL que se puede leer **antes** de descargar nada.

Lichess publica todo lo que se juega en su servidor. Los volcados mensuales, las copias en Hugging
Face (`Lichess/standard-chess-games`, más de 6 700 millones de partidas), los seis millones de puzles
y los casi 400 millones de posiciones evaluadas con Stockfish están bajo <Term id="cc0">CC0</Term>:
dominio público. Es la razón por la que este curso no necesita pedir permiso a nadie.

Un mes reciente ocupa unos 73 GB en <Term id="parquet">parquet</Term>. No vamos a descargarlo.

Cada clave es una decisión que condiciona lo que el modelo va a aprender, y conviene tenerlas claras
antes de leer el código que las aplica:

<div class="table-wrap" tabindex="0" role="region" aria-label="Tabla con desplazamiento horizontal">

| Filtro                                     | Por qué                                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `min_elo: 1800` (a los dos jugadores)      | Calidad: por debajo de 1800 abundan los errores groseros y el modelo los imitaría. Los Elo de Lichess son Glicko-2; a este nivel la diferencia con Elo clásico es irrelevante. |
| `min_base_seconds: 180`                    | `TimeControl` es `base+incremento`. Excluye bullet, donde se juega a ciegas contra el reloj. Blitz (3+0) y superiores tienen jugadas pensadas.                                 |
| `terminations: ["Normal", "Time forfeit"]` | Excluye abandonos, desconexiones y partidas anuladas por trampas (`Rules infraction`, `Abandoned`).                                                                            |
| `min_plies: 20`                            | Una partida de cinco jugadas no enseña nada. **No se aplica aquí**: se aplica en M1, y el código de abajo explica por qué.                                                     |
| `exclude_variants: true`                   | Chess960, crazyhouse o atomic tienen otras reglas y romperían la <Term id="legalidad">legalidad</Term> que queremos medir.                                                     |
| `months: ["2025-01", "2025-02"]`           | Dos meses dan entre tres y seis millones de partidas, unos 2-3 GB de texto UCI. Y el _split_ se hará **por mes**, no al azar: enero entrena, febrero valida.                   |

</div>

Ese último punto es el que evita la <Term id="fuga-de-datos">fuga</Term> más tonta de este dominio.
Si se partiera al azar, las partidas de los mismos jugadores con las mismas aperturas caerían a los
dos lados, y la validación mediría "¿reconoces a este jugador?" en vez de "¿sabes jugar?".

```python title="src/rukh/data/manifest.py"
from datetime import UTC, datetime

    path: str
    sha256: str = Field(pattern=r"^[0-9a-f]{64}$")
    bytes: int = Field(ge=0)

    """Provenance record for a fetched dataset slice."""

    model_config = ConfigDict(extra="forbid")

    dataset: str
    months: list[str]
    filters: dict[str, object]
    counts: dict[str, int]
    files: list[FileHash]
    created_at: datetime = Field(default_factory=lambda: datetime.now(UTC))
    rukh_version: str = __version__
```

<Src file="src/rukh/data/manifest.py" tag="p0" lines="1-33" />

Los tres campos del medio hacen el trabajo, y son la diferencia entre un dataset y un dataset del que
se puede responder.

`filters` son los parámetros con los que el paso **corrió de verdad**, no los que dice el README.
`counts` es cuántas filas salieron por mes, que es lo que convierte "descartamos las partidas cortas"
en algo comprobable en vez de afirmado. Y `files` es un sha256 por salida, que es lo que convierte
"el mismo dataset" en una afirmación que un test puede tumbar.

Dos detalles pequeños con consecuencias:

`sha256: str = Field(pattern=r"^[0-9a-f]{64}$")` valida la **forma** del hash. Parece innecesario
—lo escribe nuestro propio código— y no lo es: el día que alguien construya un manifiesto a mano o
lo edite para "arreglar" algo, el modelo lo rechaza. Un manifiesto con un hash inventado es peor que
no tener manifiesto, porque miente con autoridad.

`datetime.now(UTC)` y no `datetime.now()`. Una fecha sin zona horaria en un fichero que se va a
comparar entre máquinas es una fecha que no se puede comparar.

## `fetch.py`: la consulta, el plan y la descarga

```python title="src/rukh/data/fetch.py"
"""Fetch a filtered slice of ``Lichess/standard-chess-games`` with DuckDB over ``hf://``.

Only the games that pass the filters are materialized locally (predicate pushdown on the
remote parquet files). The ply count (``min_plies``) is not applied here: it is enforced in P1
once ``movetext`` has been converted to UCI with python-chess, because counting plies from SAN
with comments (``%clk``, ``%eval``) in SQL is unreliable. The manifest therefore records it as
``min_plies_deferred``. Variant exclusion by ``Event`` is a coarse first pass that P1 refines.
"""

from __future__ import annotations

import hashlib
import re
from pathlib import Path

from pydantic import BaseModel, ConfigDict, Field, field_validator

from rukh import paths
from rukh.config import BaseConfig
from rukh.data.manifest import FileHash, Manifest

MONTH_RE = re.compile(r"^(\d{4})-(0[1-9]|1[0-2])$")
```

<Src file="src/rukh/data/fetch.py" tag="p0" lines="1-22" />

El docstring es el sitio donde vive la decisión más importante del fichero, y merece leerse como
prosa y no como comentario: **`min_plies` no se aplica aquí**. Contar medias jugadas
(<Term id="ply">plies</Term>) desde el `movetext` en SQL es poco fiable, porque el texto trae
comentarios (`%clk`, `%eval`) que hay que quitar y una notación <Term id="san">SAN</Term> que hay que
parsear. Se aplicará en M1, con `python-chess`, después de convertir a <Term id="uci">UCI</Term>. Y
—esta es la parte que importa— el manifiesto lo dirá: el filtro se guarda como
`min_plies_deferred`, no como `min_plies`, para que nadie lea el manifiesto y crea que ya se aplicó.

Un filtro que se documenta como aplicado y no lo está es exactamente la clase de error que un
manifiesto existe para no cometer.

`MONTH_RE` valida `YYYY-MM` con los meses reales: `(0[1-9]|1[0-2])` rechaza `2025-13` y `2025-00`,
que un `\d{2}` aceptaría.

```python title="src/rukh/data/fetch.py"


class FetchConfig(BaseConfig):
    """What to fetch and how to filter it."""

    dataset: str = "Lichess/standard-chess-games"
    months: list[str] = Field(min_length=1)
    min_elo: int = Field(default=1800, ge=0)
    min_base_seconds: int = Field(default=180, ge=0)
    terminations: list[str] = Field(default=["Normal", "Time forfeit"], min_length=1)
    min_plies: int = Field(default=20, ge=0)
    exclude_variants: bool = True
    out_dir: str = "data/raw"
    limit: int | None = Field(default=None, ge=1)

    @field_validator("months")
    @classmethod
    def _check_months(cls, months: list[str]) -> list[str]:
        for month in months:
            if not MONTH_RE.match(month):
                raise ValueError(f"month {month!r} must look like YYYY-MM")
        return months
```

<Src file="src/rukh/data/fetch.py" tag="p0" lines="23-44" />

Hereda de `BaseConfig`, así que una clave que no esté aquí es un error. Y cada campo lleva su
restricción: `ge=0` en los tres umbrales, `min_length=1` en las dos listas, `ge=1` en `limit`.

Esas restricciones parecen defensivas y son pedagógicas: dicen qué valores tienen sentido.
`min_length=1` en `terminations` porque una lista vacía produciría `Termination IN ()`, que es SQL
inválido. `ge=1` en `limit` porque `LIMIT 0` no devuelve nada y casi siempre es una errata, no una
intención. `Field(default=[...])` con una lista mutable como valor por defecto es seguro en pydantic
—copia el valor por instancia— y sería un error clásico en una `dataclass`.

El `field_validator` de `months` valida cada mes con la expresión regular. Nótese que la regex
**también** se usa después para partir el mes en año y mes; validar y parsear con el mismo patrón
evita que se separen.

<Src file="src/rukh/data/fetch.py" tag="p0" lines="45-60" />

La existencia de este modelo es la decisión de diseño del fichero: **el plan es un objeto, no un
efecto secundario**. `run(cfg, dry_run=True)` devuelve exactamente el mismo `FetchPlan` que
`run(cfg, dry_run=False)` va a ejecutar, así que lo que imprime el ensayo no puede diferir de lo que
hace la descarga. Un `--dry-run` que construye su propia descripción es un `--dry-run` que
eventualmente miente.

El detalle de las rutas relativas en POSIX está explicado en el docstring y vale para todo el
proyecto: el manifiesto y el plan se publican, y una ruta absoluta de Windows dentro de un fichero
que va a Hugging Face es ruido que además delata la máquina de quien lo generó.

```python title="src/rukh/data/fetch.py"


def _split_month(month: str) -> tuple[str, str]:
    match = MONTH_RE.match(month)
    if match is None:
        raise ValueError(f"month {month!r} must look like YYYY-MM")
    return match.group(1), match.group(2)


def _source(cfg: FetchConfig, month: str) -> str:
    year, mm = _split_month(month)
    return f"hf://datasets/{cfg.dataset}/data/year={year}/month={mm}/*.parquet"


def _sql_string(value: str) -> str:
    return "'" + value.replace("'", "''") + "'"
```

<Src file="src/rukh/data/fetch.py" tag="p0" lines="61-76" />

`_source` construye la URL `hf://`, que es el protocolo con el que DuckDB lee parquet remoto del Hub
sin descargarlo entero. La ruta refleja el particionado del dataset: `data/year=2025/month=01/`.

`_sql_string` duplica las comillas simples. Es higiene: los valores que se interpolan
en la SQL vienen de una configuración, no de un usuario anónimo, pero un nombre de dataset con un
apóstrofo rompería la consulta de una forma que cuesta diagnosticar. Y el hábito de no interpolar
cadenas en SQL sin escaparlas conviene tenerlo también donde no hay atacante.

Que `_source` sea una función y no una cadena en línea tiene un efecto que se ve en los tests: se
puede sustituir por una que apunte a un parquet local, y con eso el pipeline entero se prueba sin
red.

```python title="src/rukh/data/fetch.py"


def build_query(cfg: FetchConfig) -> str:
    """Build the DuckDB SQL that selects the filtered games, one ``read_parquet`` per month.

    ``TRY_CAST`` drops rows whose base time is not an integer (correspondence games export
    ``TimeControl = '-'``). ``hive_partitioning = false`` stops DuckDB from injecting ``year``
    and ``month`` columns from the path, which would collide with the explicit ``month`` alias.
    """
    conditions = [
        f"WhiteElo >= {cfg.min_elo} AND BlackElo >= {cfg.min_elo}",
        f"TRY_CAST(split_part(TimeControl, '+', 1) AS INTEGER) >= {cfg.min_base_seconds}",
        "Termination IN (" + ", ".join(_sql_string(t) for t in cfg.terminations) + ")",
    ]
    if cfg.exclude_variants:
        conditions.append("Event NOT ILIKE '%variant%'")
    where = "\n    AND ".join(conditions)
    selects = [
        "SELECT *, "
        + _sql_string(month)
        + " AS month\n"
        + f"FROM read_parquet({_sql_string(_source(cfg, month))}, hive_partitioning = false)\n"
        + f"WHERE {where}"
        for month in cfg.months
    ]
    sql = "\nUNION ALL\n".join(selects)
    if cfg.limit is not None:
        sql += f"\nLIMIT {cfg.limit}"
    return sql
```

<Src file="src/rukh/data/fetch.py" tag="p0" lines="77-105" />

El constructor de la consulta, y los dos detalles del docstring son de los que cuestan una tarde
cuando no se conocen.

**`TRY_CAST` y no `CAST`.** Las partidas por correspondencia llegan con `TimeControl = '-'`. Un
`CAST('-' AS INTEGER)` **aborta la consulta entera**: seis mil millones de filas y una que no se
puede convertir, y no obtienes nada. Con `TRY_CAST` esa fila da `NULL`, `NULL >= 180` es falso, y la
partida se descarta, que es justo lo que queremos. La diferencia entre las dos funciones es la
diferencia entre un filtro y un fallo.

**`hive_partitioning = false`.** DuckDB reconoce los nombres de carpeta `year=2025/month=01` de la
ruta y, si no se lo impides, los inyecta como columnas `year` y `month`. La consulta ya añade su
propia columna `month` con el alias (`'2025-01' AS month`), así que habría dos columnas con el mismo
nombre: DuckDB renombra una a `month_1` y el resultado tiene un `month` que es `01` y un `month_1` que
es `2025-01`, o al revés según la versión. Hay un test que comprueba exactamente eso, y está más
abajo.

La columna `month` se añade a mano en el `SELECT` porque el `split` del curso es por mes, y después de
unir los dos meses con `UNION ALL` hace falta saber de cuál viene cada partida.

El `LIMIT` se pone al final y es opcional. Sirve para explorar: la misma consulta con `limit: 1000`
baja mil partidas en segundos, y es lo que se usa en M1 para mirar distribuciones antes de
comprometerse con el recorte completo.

```python title="src/rukh/data/fetch.py"


def plan(cfg: FetchConfig) -> FetchPlan:
    """Describe the query, months, output directory, relative output files and manifest."""
    out_dir = _out_dir(cfg)
    out_paths = []
    for month in cfg.months:
        year, mm = _split_month(month)
        target = out_dir / f"year={year}" / f"month={mm}" / "games.parquet"
        out_paths.append(target.relative_to(out_dir).as_posix())
    return FetchPlan(
        query=build_query(cfg),
        months=list(cfg.months),
        out_dir=out_dir.as_posix(),
        out_paths=out_paths,
        manifest_path=(out_dir / "manifest.json").relative_to(out_dir).as_posix(),
    )
```

La salida reproduce el particionado del origen: `year=2025/month=01/games.parquet`. No es estética.
Un directorio con ese formato lo lee DuckDB (y pandas, y polars) como una tabla particionada, así que
M1 puede consultar los dos meses juntos o uno solo con la misma expresión.

El `relative_to(out_dir).as_posix()` es lo que mantiene la promesa del `FetchPlan`: nada de rutas
absolutas en lo que se publica.

```python title="src/rukh/data/fetch.py"


def _sha256(path: Path) -> str:
    digest = hashlib.sha256()
    with path.open("rb") as fh:
        for chunk in iter(lambda: fh.read(1 << 20), b""):
            digest.update(chunk)
    return digest.hexdigest()
```

Por trozos de un mega (`1 << 20`) y no `path.read_bytes()`: estos parquet pesan gigabytes y leerlos
enteros en memoria para hashearlos es innecesario. El `iter(callable, sentinel)` es el modismo de la
biblioteca estándar para "llama a esto hasta que devuelva `b''`".

```python title="src/rukh/data/fetch.py"


def run(cfg: FetchConfig, dry_run: bool = False) -> FetchPlan:
    """Plan the fetch and, unless ``dry_run``, execute it month by month.

    With ``dry_run=True`` nothing touches the network or the disk. Otherwise each month is
    materialized as ``<out_dir>/year=YYYY/month=MM/games.parquet`` (so ``limit`` applies per
    month) and a ``manifest.json`` with filters, counts and file hashes is written last. The
    manifest stores file paths relative to ``out_dir`` and ``min_plies`` as
    ``min_plies_deferred`` because plies are only filtered in P1, after UCI conversion.
    """
    fetch_plan = plan(cfg)
    if dry_run:
        return fetch_plan

    import duckdb

    out_dir = Path(fetch_plan.out_dir)
    counts: dict[str, int] = {}
    files: list[FileHash] = []
    con = duckdb.connect()
    try:
        for month, out_path in zip(cfg.months, fetch_plan.out_paths, strict=True):
            target = out_dir / out_path
            target.parent.mkdir(parents=True, exist_ok=True)
            month_query = build_query(cfg.model_copy(update={"months": [month]}))
            target_sql = _sql_string(target.as_posix())
            con.execute(f"COPY ({month_query}) TO {target_sql} (FORMAT PARQUET)")
            row = con.execute(
                f"SELECT count(*) FROM read_parquet({target_sql}, hive_partitioning = false)"
            ).fetchone()
            counts[month] = int(row[0]) if row else 0
            files.append(
                FileHash(path=out_path, sha256=_sha256(target), bytes=target.stat().st_size)
            )
    finally:
        con.close()

    filters = cfg.model_dump(exclude={"dataset", "months", "out_dir", "min_plies"})
    filters["min_plies_deferred"] = cfg.min_plies
    manifest = Manifest(
        dataset=cfg.dataset,
        months=list(cfg.months),
        filters=filters,
        counts=counts,
        files=files,
    )
    manifest_path = out_dir / fetch_plan.manifest_path
    manifest_path.parent.mkdir(parents=True, exist_ok=True)
    manifest_path.write_text(manifest.model_dump_json(indent=2) + "\n", encoding="utf-8")
    return fetch_plan
```

<Src file="src/rukh/data/fetch.py" tag="p0" lines="136-186" />

La función que descarga, y seis decisiones dentro.

**`if dry_run: return fetch_plan`** en la tercera línea. El ensayo no es un camino alternativo: es el
mismo camino, cortado antes del primer efecto. Por eso no puede divergir.

**Un `COPY` por mes**, no uno con la consulta entera. La consulta completa tiene el `UNION ALL` de
todos los meses, y si se ejecutara de una vez el `limit` se aplicaría al total en vez de por mes, y
el resultado no se podría partir por mes. Se reconstruye la consulta de cada mes con
`cfg.model_copy(update={"months": [month]})`, que devuelve una copia del modelo con un campo
cambiado y deja el original intacto.

**`zip(..., strict=True)`.** Si `cfg.months` y `fetch_plan.out_paths` tuvieran longitudes distintas
—porque alguien cambió `plan()` y no esto—, un `zip` normal recortaría en silencio y se descargarían
menos meses de los pedidos. Con `strict=True` es un `ValueError`. En Python 3.10+ no hay motivo para
escribir un `zip` sin él cuando las dos secuencias deben tener el mismo tamaño.

**El conteo se lee del fichero escrito**, no del resultado del `COPY`. Es una comprobación de verdad:
cuenta las filas que hay **en disco**, así que un `COPY` que escribiera mal daría un número
incoherente en vez de pasar inadvertido.

**El `try/finally` alrededor de la conexión.** Una excepción a mitad de un mes (la red se cae, el
disco se llena) cierra la conexión igual. Lo que **no** hay es limpieza de ficheros a medias: si
falla, quedan los meses ya escritos y **no** queda manifiesto. Eso es deliberado y es la propiedad
útil: el manifiesto se escribe al final, así que su presencia significa "esto terminó". Un directorio
con parquet y sin `manifest.json` es una descarga interrumpida, y se ve de un vistazo.

**`exclude={"dataset", "months", "out_dir", "min_plies"}`** al volcar los filtros. Los tres primeros
no son filtros (van en sus propios campos del manifiesto) y el cuarto se renombra en la línea
siguiente. Es el código que cumple la promesa del docstring.

```bash title="Terminal"
uv run rukh data fetch --config configs/data/lichess-2025-01-02.yaml --dry-run
```

```text
  FROM read_parquet('hf://datasets/Lichess/standard-chess-games/data/year=2025/month=02/*.parquet', hive_partitioning = false)
  WHERE WhiteElo >= 1800 AND BlackElo >= 1800
      AND TRY_CAST(split_part(TimeControl, '+', 1) AS INTEGER) >= 180
      AND Termination IN ('Normal', 'Time forfeit')
      AND Event NOT ILIKE '%variant%'
out_dir:  <repo>/data/raw
outputs:
  year=2025/month=01/games.parquet
  year=2025/month=02/games.parquet
manifest: manifest.json
```

Los cuatro filtros están ahí, legibles, antes de que nada se descargue. Eso es lo que hace que la
tabla de arriba sea una afirmación comprobable y no una descripción.

```python title="tests/unit/test_fetch.py"
def _write_hive_source(rukh_home: Path, monkeypatch: pytest.MonkeyPatch) -> Path:
    """Write the fake rows under the real ``year=YYYY/month=MM`` layout; point ``_source`` at it."""
    import duckdb

    from rukh.data import fetch as fetch_module

    source_dir = rukh_home / "source" / "year=2025" / "month=01"
    source_dir.mkdir(parents=True)
    duckdb.sql(FAKE_ROWS).write_parquet((source_dir / "part-0.parquet").as_posix())
    monkeypatch.setattr(
        fetch_module, "_source", lambda cfg, month: (source_dir / "*.parquet").as_posix()
    )
    return source_dir


def _read_output(path: Path) -> tuple[list[str], list[tuple[object, ...]]]:
    import duckdb

    rel = duckdb.sql(f"SELECT * FROM read_parquet('{path.as_posix()}', hive_partitioning = false)")
    return list(rel.columns), rel.fetchall()
```

Aquí está la técnica. `_write_hive_source` escribe las seis filas como un parquet local **bajo la

verdad, sobre parquet de verdad: lo único falso es de dónde sale el fichero.

Que la estructura de carpetas sea la real no es un detalle: es lo que permite que el test detecte el
problema del `hive_partitioning`, que solo aparece cuando la ruta tiene el formato `clave=valor`.

**Que el filtro filtra**: `len(rows) == 1`, la única de las seis filas que pasa.

revienta la consulta**: `TRY_CAST` la convierte en `NULL` y el filtro la descarta. Ese test es la
única cosa que impide que alguien cambie `TRY_CAST` por `CAST` porque "queda más limpio", y descubra

El primero es el que importa: **el viaje de ida y vuelta por JSON es idempotente**. Un manifiesto
serializado, leído y vuelto a serializar da byte por byte lo mismo. Sin esa propiedad, un manifiesto
no sirve para comparar dos descargas, que es su único trabajo: cualquier diferencia de formato
—el orden de las claves, cómo se escribe la fecha— produciría diferencias falsas.

`created_at=datetime(2026, 9, 18, 12, 0, tzinfo=UTC)` con una fecha fija: un modelo con
`default_factory=datetime.now` no se puede comparar consigo mismo si cada instancia trae una fecha
distinta. `sha256="ab" * 32` son 64 caracteres hexadecimales, el mínimo que pasa el patrón.

## La descarga de verdad

```bash title="Terminal"
uv run rukh data fetch --config configs/data/lichess-2025-01-02.yaml
```

Tarda entre una y dos horas en la máquina de referencia y depende sobre todo de tu conexión: DuckDB
lee los parquet remotos, aplica los filtros y escribe solo lo que pasa. Se lanza al terminar esta
lección y se recoge en M1, donde el manifiesto tendrá los conteos por mes.

Mientras corre, la lección siguiente no necesita datos: es el tablero de la demo, que en este hito
funciona sin modelo.

<Callout kind="roto" title="Lo que este código todavía no tiene">
  `FetchConfig` no tiene `max_elo`, y en M4 hará falta. Al entrenar el modelo condicionado por Elo
  se descubrió que `min_elo: 1800` aplicado a los dos jugadores dejaba **doce tokens de Elo sin un
  solo gradiente**: no había ninguna partida por debajo de 1800 en el corpus, así que los tokens que
  representan esos tramos nunca aparecían. La solución fue traer también la mitad baja del eje con
  un `max_elo`, y de paso una propiedad que un test puede comprobar sin tocar la red: `low.max_elo +
  1 == high.min_elo`, es decir, que las dos mitades embaldosen el rango sin solaparse ni dejar
  hueco. Aquí no está porque aquí no estaba: el `fetch.py` de M4 tiene 350 líneas y M4 las enseña.
</Callout>

## Qué has aprendido

El recorte de datos y, sobre todo, la disciplina que lo acompaña: los filtros se leen antes de
descargar, se aplican desde un único sitio, y lo que se aplicó de verdad queda en un manifiesto con
conteos y hashes. El filtro que **no** se aplica se llama distinto en el manifiesto para que nadie
crea que sí.

**Cómo se mide**: el `--dry-run` imprime la SQL con los cuatro filtros; `uv run pytest -m unit -q`
pasa los veintitantos tests de `fetch` y `manifest`, incluidos los dos que ejecutan el pipeline
completo sobre un parquet local; y cuando la descarga termine, `data/raw/manifest.json` tendrá
`counts` por mes, un `sha256` por fichero y `min_plies_deferred: 20`.

ya sabe las reglas aunque no haya modelo ninguno.
